## 1. GDR（General Decision Record）

**GDR-META-028: status に `Accepted` / `Rejected` を加えて 5 値化し、「有効 / 失効」の 2 区分・supersede の status 行記法・失効への切替時点を正式化する**

- **status:** Proposed
- **scope:** meta, spec
- **決定:** status を以下の 5 値とし、AI・ツールが機械的に扱えるよう**有効（effective）/ 失効（inactive）**の 2 区分を定義する:

  | status | 区分 | 意味 |
  |---|---|---|
  | `Proposed` | 有効（未確定） | 提案中。合意に至っていない |
  | `Accepted` | 有効 | 合意済み・未実装 |
  | `Implemented` | 有効 | 実装済み（コード・設定・運用に反映された） |
  | `Superseded` | 失効 | 新しい GDR に置き換えられた |
  | `Rejected` | 失効 | **起票された提案そのものが採用されなかった** |

  **遷移:** `Proposed → Accepted → Implemented`（通常）、`Proposed → Rejected`（不採用）、**`Accepted → Rejected`（合意後の撤回 — 実装段階で前提が崩れた等。却下理由にその旨を書く）**、`Accepted / Implemented → Superseded`（置換）。`Accepted` への更新は合意（ビルドアップサイクルの「合意」フェーズ）の時点で行う。`Rejected` と `Superseded` は終端状態で、そこから他の値へは遷移しない。

  **supersede の記法と切替時点:** 相互リンクは **status 行に書く** — 旧: `- **status:** Superseded by GDR-UI-003`、新: `- **status:** Accepted (supersedes GDR-UI-001)`（実装後は `Implemented (supersedes GDR-UI-001)`）。status 行は「先頭トークンが status 値、以降の括弧・`by` 句が置換リンク」と読む。旧レコードを `Superseded` にするのは**新レコードが `Accepted` になった時点**とし、新が `Proposed` の間は旧を有効のまま残す（確定した有効判断が常にどちらか一方に存在する）。

  **撤回時の復帰:** `supersedes` を持つ新レコードが `Accepted → Rejected` で撤回された場合、旧レコードの status を置換前の値に戻し、注記で経緯を残す（例: `- **status:** Implemented（GDR-INFRA-003 の撤回により復帰）`）。旧の判断内容は変わっていないため、「判断の本質が変わる更新」ではなく軽微な訂正として扱う（新 GDR 不要）。`Superseded` を終端とする規則の唯一の例外である。

  **`Rejected` の範囲と再提案:** 決定案が棄却された記録に限る。「X はしない」こと自体を今後の方針として拘束したい場合は、否定形の決定を持つ GDR を別途起票する（こちらは通常どおり `Accepted` / `Implemented`）。`Rejected` には理由配下のサブ箇条書き `- **却下理由:** ...` を必須とする。却下した案を再検討条件の成立などで再提案する場合は、**新 GDR を起票し `関連: derived-from GDR-X-NNN` で経緯をつなぐ**（`supersedes` は使わない — 置換ではなく再起票のため）。

  **二段保管:** 失効 2 値の両方に適用する。退避のタイミングは、`Superseded` は**新レコードが `Implemented` になった時点**（`Accepted` の間は旧を元の位置に置き、INDEX にも両方を残す — 実装はまだ旧に従っており、撤回時の復帰も status 行の訂正だけで済む）、`Rejected` は確定時点とする。INDEX の 1 行サマリは `GDR-OLD-NNN（要約） — Superseded by GDR-NEW-MMM → archived` / `GDR-X-NNN（要約） — Rejected（却下理由の要約） → archived`
- **理由:** 失効判断の誤参照を防ぐには、「どのレコードが失効しているか」と「いま確定している判断はどれか」が status 値だけで判定できなければならない。現行 3 値には 3 つの欠落がある — (1) 起票されたがレビューで却下された判断の行き場がなく、`Proposed` のまま放置される（AI からは検討中の有効な案に見える）か、削除されて却下理由が消える。(2) 合意済みかどうかを GDR 本文から判定できない（合意の事実は T2 実行計画にしかなく、実プロジェクトでは GDR が `notes/91_gdr/gdr/` に T2 と分離して置かれる）。(3) 旧を `Superseded` にする時点が未定義で、合意時に即失効させると「旧は失効・新は未確定」という**確定判断の空白**が生じる。`Accepted` の追加と「新が `Accepted` になった時点で旧を失効」の規則で (2) (3) が同時に解消する。ただしこの規則だけでは、合意後に新が撤回される異常系で旧が失効したまま残り、空白が再発する — 撤回経路（`Accepted → Rejected`）と旧の復帰、退避を新の `Implemented` 時点まで遅らせる規則はこの異常系を閉じるためのもので、退避を遅らせることで復帰はファイル移動なしの status 行訂正で済む。supersede 記法は 01 §3 に例示（`Superseded by` / `Supersedes`）はあるが書く場所が未規定で、機械抽出が安定しない
  - **代替案 A:** 4 値のまま（`Accepted` なし）、旧の `Superseded` 化を新が `Implemented` になった時点まで遅らせる → 空白 (3) は解消するが、合意済み判定 (2) が残り、「T2 等で合意が確認できれば前提にしてよい」という参照先依存の規則が必要になる。起票時はこの案の系統（`Accepted` 不採用）を選んでいたが、セルフレビューで (2) の見落としが判明し却下
  - **代替案 B:** 却下案は採用 GDR の「代替案」サブ箇条書きにのみ残す（現行運用）→ 採用 GDR と対にならない提案（レビューで合意に至らず、代わりの決定も出なかった提案 GDR）を記録できない。代替案として書ける場面では引き続き代替案で書き、**独立 GDR として起票済みのものだけ** `Rejected` にする、という併用で採用
  - **代替案 C:** `supersedes` / `superseded-by` を任意フィールド「関連」に移す → GDR-META-025 で「supersede 系は status 行」と決めており、status と置換関係は同時に変わるため同じ行にある方が更新漏れが起きにくい。却下
- **影響:**
  - 01 §3 の status 表・書式、T2 / 00_GETTING_STARTED / リポジトリ直下 `CLAUDE.md`（GDR 書式節）の status 行を 5 値に更新する
  - 02 §5.2 の判断更新ルールに「旧の失効は新の `Accepted` 時点」「撤回時の復帰」「二段保管は失効 2 値・Superseded の退避は新の `Implemented` 時点」「Rejected の再提案は derived-from」を反映する
  - `/gdr-flow` の合意フェーズに「`Proposed → Accepted` 更新 + 置換対象の旧を `Superseded` 化」を追加し、`/gdr-docs` の実装完了時の更新を `Accepted → Implemented` + 旧の退避に改める（`Proposed` のまま実装コミットが対応している場合は合意漏れとして警告）。いずれもリポジトリ外配備
  - 06 可視化ガイドと `/gdr-map` の status 視覚語彙に `Accepted` / `Rejected` を追加する
  - 007 gdr-index のパーサ・lint 仕様に追随が必要（§4.4 の申し送り）
  - 既存レコードへの遡及影響なし（旧側の `Superseded by GDR-X` 記法は既存どおり。新側の `(supersedes …)` は前例がないため、既存レコードの新側リンク欠落は lint 警告で拾う）
- **再検討条件:**
  - `Accepted` への更新漏れで合意済み GDR が `Proposed` のまま残る事例が繰り返し発生 → 合意フェーズでの更新をコマンド側で強制する仕組みを検討
  - `Rejected` の記録率が低く、却下判断が再議論される事例が発生 → 起票フェーズでの却下記録の強制を検討
  - 撤回による旧の復帰が頻発する → 旧の失効時点を新の `Implemented` まで遅らせる方式（代替案 A の系統）との比較をやり直す

**GDR-META-029: AI は失効レコードを判断の根拠にしない — 直接参照では後継を末端までたどり、検索基盤では既定で有効のみ + 失効ヒットは後継へのリダイレクトとして返す**

- **status:** Proposed
- **scope:** meta, pol
- **決定:** AI の GDR 参照規則を次のとおり定める。
  1. **根拠にしてよいのは確定した有効レコード（`Accepted` / `Implemented`）のみ。** 失効レコード（`Superseded` / `Rejected`）を実装・提案の根拠として引用しない。`Accepted (supersedes X)` を根拠にする場合は、実装が未反映で**コードはまだ X に従っている**ことを前提に置く
  2. **失効レコードに到達したら後継をたどる。** `Superseded by` を**末端の有効レコードまで**たどり、そのレコードを根拠にする。後継が見つからない・循環する場合は根拠にせず、整合性の破損として人間に報告する
  3. **`Rejected` は「採らない理由」としてのみ引用する。** 同じ案が再提案されたときに「GDR-X-NNN で却下済み（却下理由: …）」と示す用途に限る
  4. **`Proposed` は未確定として扱う。** 引用時は「未確定（Proposed）」と明示し、それを前提とした実装へ進まない（合意されれば `Accepted` になるため、status だけで判定できる）

  検索基盤（007 gdr-index）では、`gdr_search` の**既定フィルタを有効レコードのみ**とする。ただし失効レコードがクエリに一致した場合は結果から黙って落とさず、**「GDR-X-001（失効）→ 現行: GDR-X-003」のリダイレクト行**として返す。全件検索は `include_inactive=true` の明示指定時のみ。`gdr_get` は失効レコードに対し、本文の前に失効バナーと後継チェーンの末端 ID を付与する
- **理由:** 記録が増えるほど、覆された古い判断がキーワードに一致する確率は上がり、AI がそれを現行の判断と誤認して動く危険が増える。これは「記録すること」より深刻な GDR の実運用上の急所である。ただし失効レコードを単純に検索から除外すると別の失敗が起きる — 旧用語（例:「セッションを Memcached に」）で検索して何もヒットしなければ、AI は「未決定」と判断して既決事項を再議論する（02 §3.2 の反復ループ）。リダイレクト行はこの両方を防ぐ: 旧判断は根拠として提示されないが、現行判断への到達路は残る。規則を AI の振る舞いとして先に定めるのは、007 が未実装（フェーズ 0）の現在、AI は INDEX とファイルを直接読んでおり、ツールより先に規律が必要なため
  - **代替案 A:** 検索時に失効レコードを完全除外 → 旧用語での検索が空振りし、再議論を誘発する。却下
  - **代替案 B:** 全件返し、status 表示だけに委ねる → 要約形式の検索結果では status 列の見落としが起きやすく、検索上位に失効レコードが来ると AI がそのまま引用する。却下
  - **代替案 C:** 失効レコードの本文を物理削除 → 「なぜ変えたか」の履歴が消え、GDR の目的 1 に反する。二段保管（退避）で十分。却下
- **影響:**
  - 02 §6「AI に求められる振る舞い」に「参照の規律」行を追加する
  - `/gdr-flow`・`/gdr-kaizen` の起票フェーズで過去 GDR を参照する手順に、上記 4 規則を適用する（コマンド定義は `~/.claude/commands/` 配下 — リポジトリ外配備）
  - 007 の `gdr_search` / `gdr_get` / `lint` 仕様に追随が必要（§4.4 の申し送り）
- **再検討条件:**
  - 後継たどりで循環・断絶が繰り返し見つかる → lint による supersede チェーン検査の常時実行（`/gdr-docs` への統合）を検討
  - リダイレクト行が検索結果を圧迫する規模（1 クエリで失効ヒットが多数）→ リダイレクトの集約表示（同一後継への複数リダイレクトを 1 行化）を検討

**GDR-META-030: 任意フィールド「理由の出所」（`human` / `ai-reviewed` / `ai`）を追加し、AI 起票時は記入を必須にする**

- **status:** Proposed
- **scope:** meta, spec, pol
- **決定:** GDR-META-025 の任意フィールドに**「理由の出所」**を追加する。値は閉集合の 3 値で、信頼度の順序は `human > ai-reviewed > ai`:

  | 値 | 意味 |
  |---|---|
  | `human` | 理由の核心が人間の発言・文書に由来する（AI は整形のみ）。発言の短い引用または出典を括弧で添える: `human（ユーザー発言「DB 化する際に timestamp はしっかり管理したい」）` |
  | `ai-reviewed` | AI が起案し、人間がレビュー・合意の工程で内容を確認した |
  | `ai` | AI の推論のみで人間が未確認（既存コードからの遡及記録、自律実行中の判断等） |

  **書式:** 先頭トークンが値、以降の括弧内は注記（`human` では引用・出典が必須、他の値では任意）。括弧は全角・半角どちらも可。

  **混在時:** レコードの値は、理由を構成する部分のうち**最も弱い値**とする。人間由来の部分は注記の引用で示す。レビュー・合意を経た時点で `ai` の部分は `ai-reviewed` に上がる（例: `human` + 未確認の `ai` → `ai`、合意後 → `ai-reviewed`）。

  仕様上は任意フィールドとし既存レコードに遡及しないが、**AI が GDR を起票・更新する場合は記入を必須**とする。欠落は「不明」とみなし、信頼度判断では `ai` と同等に扱う。合意時の `ai` → `ai-reviewed` 更新は軽微な追記扱い（新 GDR 不要）で、`Proposed → Accepted` 更新と同じタイミングで行う。あわせて、**AI は理由が不明な判断に理由を補完しない** — 根拠が確認できない場合は理由欄に「不明（記録時点で根拠未確認）」と書き、出所は `ai` とする
- **理由:** AI に記録を書かせると、理由や却下した代替案を**後付けでもっともらしく生成**しがちであり、しかも生成された理由は人間由来の理由と見分けがつかない。02 §3.2 は GDR がハルシネーションを「◎ 構造的に強く抑止する」としているが、これは理由欄が**実在する根拠で埋まる**ことを前提にしており、その前提自体が検証されていない。出所を区別しておけば、後に判断を見直す人間・AI が「この理由は誰かが実際にそう考えたのか、AI の推定なのか」を判断でき、再検討時の信頼度付けができる。任意フィールドにするのは「6 必須フィールド不変」（GDR-META-025）を守るためで、AI 起票時必須とすることで記入率の問題は回避する（人間が手で書く GDR はそもそも出所が `human` 自明）
  - **代替案 A:** 7 番目の必須フィールドにする → 既存全レコードが書式違反になり、GDR-META-025 の後方互換方針に反する。AI 起票時必須で実効性は同等。却下
  - **代替案 B:** 理由・代替案の箇条書きごとに出所を付ける → 精度は上がるが記述が煩雑になり、読み手の負担が大きい。レコード単位 + 最弱値規則 + `human` の引用添付で当面十分。再検討条件行き
  - **代替案 C:** 2 値（`human` / `ai`）→ レビュー・合意を経た AI 起案（現状の大半）と、人間が一度も見ていない AI 推定の区別がつかない。信頼度の差が最も大きいのはこの境界であるため 3 値とする。却下
- **影響:**
  - 01 §3.1 任意フィールド表に 1 行追加、T2 テンプレートに記入例を追加する
  - 02 §3.2 ハルシネーション行の記述を「出所の区別と組み合わせて効果を発揮」に改め、§6 に「出所の明示」行を追加する
  - `/gdr-flow`・`/gdr-kaizen`・`/gdr-docs`（合意・完了時の `ai` → `ai-reviewed` 更新）のコマンド定義に記入規則を追加する（リポジトリ外配備）
  - 007 gdr-index の `records` に `rationale_source` 列を追加する申し送り（§4.4）
- **再検討条件:**
  - 最弱値規則のために `human` 由来の核心が埋もれ、単一値では誤解を招く事例が繰り返し発生 → 箇条書き単位の出所（代替案 B）を再検討
  - `ai-reviewed` のレビューが形骸化（未読合意）している兆候 → 値の意味の見直し、または合意時の確認観点の明文化

## 2. 現状

外部レビュー（GDR の骨格 — 全意思決定の記録 / INDEX → 本文の二段参照 / SQLite FTS5 の検索 + ID 取得 / `/gdr-flow`・`/gdr-bug-report`・`/gdr-kaizen` — に対する評価）で、「実運用で効いてくるのは記録することより、古い決定を AI に誤って拾わせないこと」という指摘を受けた。これを起点に現行仕様を点検した結果:

1. **status が判断の確定状態を表しきれていない** — status は `Proposed / Implemented / Superseded` の 3 値で、(a) 起票されたがレビューで採用されなかった判断を表す値がない（`Proposed` のまま残れば AI には有効な案に見え、削除すれば却下理由が失われる）、(b) 合意済み・未実装を表す値がなく、合意の有無を GDR 本文から判定できない
2. **supersede リンクの記法と切替時点が未規定** — 01 §3 は「相互リンクを貼ること」と例（`Superseded by` / `Supersedes`）を示すのみで、どのフィールドに書くか、旧をいつ失効させるかを定めていない。機械的に後継をたどる前提が成立せず、失効のタイミング次第で確定判断の空白が生じる
3. **失効レコードを AI がどう扱うかの規則がない** — 二段保管（006）によりセッション開始時の読み込みからは外れるが、grep・明示参照・将来の検索（007 `gdr_search` は status 引数が任意で既定値なし）では失効レコードが普通にヒットし、それを根拠にしてはならないという規律がどこにも書かれていない
4. **理由の出所が区別されていない** — 理由・代替案が人間の発言由来か AI の推定かを記録する手段がない。02 §3.2 はハルシネーション抑止を ◎ としているが、AI が理由を後付けで生成するケースを考慮していない
5. **すでに対処済みのもの（本提案で触らない）** — 日本語検索の精度は 007 GDR-META-021（FTS5 trigram + 2 文字語の LIKE フォールバック + ローカル embedding のハイブリッド）で扱っている。インデックス → 本文の二段参照は 007 GDR-META-022（`gdr_search` は要約、全文は `gdr_get`）で確立済み

## 3. 改善案

3 つの GDR で「status の区分と遷移」「参照の規律」「理由の信頼度」を定義する。書式変更は **status 値の追加 2 つと任意フィールドの追加 1 つ**で、6 必須フィールドは不変・既存レコードへの遡及影響はない。

1. **status 5 値化・有効 / 失効の区分・失効の切替時点**（GDR-META-028）— 失効と確定が status 値だけで判定でき、確定判断の空白が生じない
2. **参照の規律とリダイレクト**（GDR-META-029）— 失効判断を根拠にせず、しかし現行判断への到達路は残す
3. **理由の出所**（GDR-META-030）— 人間由来の理由と AI の推定を見分けられる

### 4.2. AI の参照フロー

```
GDR を参照する
  │
  ├─ status = Implemented / Accepted ─→ 根拠として引用可
  ├─ status = Proposed ───────────────→ 「未確定」と明示して引用。前提にした実装はしない
  ├─ status = Superseded by X ────────→ X へ移動して再判定（末端の有効レコードまで）
  │                                       └─ 断絶・循環 → 根拠にせず人間に報告
  └─ status = Rejected ───────────────→ 「採らない理由」としてのみ引用
```

旧の失効を新の `Accepted` 時点に揃えているため、後継たどりの末端が `Proposed` になるのは整合性の破損（旧を早すぎる時点で失効させた）であり、上記の「断絶」として人間に報告する。末端が `Rejected` になる場合も同様（撤回時の旧の復帰漏れ）。

### 4.3. 理由の出所の運用

| 場面 | 記入する値 |
|---|---|
| ユーザーが理由を述べ、AI が GDR 化した | `human`（発言の短い引用を添える） |
| AI が起票し、`レビュー：` → `レビュー反映：` → 合意を経た | 起票時 `ai` → 合意時（`Accepted` 更新と同時）に `ai-reviewed` |
| AI が既存コード・過去文書から判断を遡及記録した | `ai`（人間が確認したら `ai-reviewed`） |
| 理由が確認できない | 理由欄に「不明（記録時点で根拠未確認）」、出所は `ai` |
| 人間由来の核心と AI の補足が混在 | 最も弱い値（未確認なら `ai`、合意後 `ai-reviewed`）。人間由来の部分は注記で引用 |

- `human` の引用は「誰かが実際にそう言った」ことの証跡であり、要約・言い換えではなく**発言の断片そのもの**を書く
- 引用は判断の核心を示す断片（1 文程度）に限り、個人名は役割（「ユーザー」「レビュアー」）に置き換える

### 4.4. gdr-index（007 提案）との整合 — 申し送り

本提案は 007 の実装に**依存しない**（参照規律は AI の振る舞いとして今日から成立する）が、007 実装時に以下の追随が必要になる:

1. **パーサ** — status 行を「先頭トークン = status 値、`by GDR-X` / `(supersedes GDR-X)` = 置換リンク」として分解し、`links` に `supersedes` / `superseded_by` を正規化する。`Accepted` / `Rejected` を正当な status 値として受け付ける。`Supersedes` / `supersedes` の大文字小文字、全角・半角括弧は区別しない
2. **`records` への列追加** — `effective`（Proposed / Accepted / Implemented = 1、Superseded / Rejected = 0 の派生列。**検索の既定に含めるか**を表す列であり、根拠にしてよいかは GDR-META-029 規則 1 のとおり status で判定する）、`rationale_source`（欠落は NULL = 不明）
3. **`gdr_search` の既定** — `WHERE effective = 1` を既定とし、失効ヒットは後継チェーン末端 ID を解決してリダイレクト行で返す。`include_inactive` 引数を追加。リダイレクト行の正確な書式は実装時に確定する
4. **`gdr_get`** — 失効レコードに失効バナー + 後継末端 ID を前置
5. **lint** — (a) Superseded の後継 ID 欠落・後継側の `supersedes` 欠落（相互リンク不整合）、(b) supersede チェーンの循環・断絶・末端が `Proposed` または `Rejected`（復帰漏れ）、(c) `Rejected` の `却下理由` 欠落、を警告する

007 本文は編集しない（起票済み文書の遡及編集を避ける）。007 の実装フェーズ着手時に本節を参照すること。

### 7.1. 観察された傾向

1. **外部レビュー起点の提案** — 本提案は、フレームワーク外部からの評価（懸念点 1「陳腐化した決定を AI が拾うリスク」/ 懸念点 3「『なぜ』の出どころ」）を起点にした kaizen である。指摘のうち日本語検索精度・二段参照はすでに 007 で扱われていたため新 GDR にせず（§2-5）、未対処の 2 点だけを GDR 化した
2. **指摘の単純適用を避けた点** — 「失効レコードは既定で検索から除外」という指摘をそのまま採ると、旧用語での検索が空振りして再議論を誘発する（反復ループ）。除外ではなく**リダイレクト**にしたのが本提案の主な設計上の付加（GDR-META-029）
3. **レビュー工程での検出（状態の集合 vs 状態の遷移）** — 起票時は status を「値の集合」としてだけ設計し、`Accepted`（外部レビューも挙げていた値）を ROI 判断で見送った。セルフレビューで**遷移のタイミング**（旧をいつ失効させるか、合意をどこで判定するか）を問うた結果、見送りの根拠が「合意は T2 に記録済み」という GDR 単体では参照できない情報に依存していたことが判明し、ユーザー判断で追加に転じた。ROI による圧縮が、本提案の目的（確定判断を status だけで判定できること）自体を損なう場合は圧縮しすぎである、という実例
4. **正常系から異常系へ（2 回目のセルフレビュー）** — 1 回目で導入した「新の合意時点で旧を失効」規則を、合意後の撤回という異常系まで追うと、1 回目で塞いだ空白が再び開くことが分かった。撤回経路と復帰規則を足し、退避を新の `Implemented` 時点まで遅らせることで、新しい status 値・語彙を増やさずに閉じた。状態遷移の設計は、正常系・撤回・置換・再提案の全経路で不変条件（確定した有効判断がちょうど 1 つ）を確かめて初めて完了する
5. **ドッグフーディング** — 本提案の 3 GDR 自身に「理由の出所」を付けた。懸念の起点は外部レビュー（人間が持ち込んだ文書）、`Accepted` 追加はユーザーの選択だが、決定内容と理由の組み立ての大半は AI 起案で人間未確認のため、最弱値規則どおり `ai` とした。合意時に `ai-reviewed` へ更新する。また本提案の GDR は、仕様（タスク 1.1）の更新より先に `Accepted` を使う最初のレコードになる（自己適用）
