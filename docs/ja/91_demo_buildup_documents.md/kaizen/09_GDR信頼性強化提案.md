## 1. GDR（General Decision Record）

**GDR-META-028: status に `Rejected` を加えて 4 値化し、「有効 / 失効」の 2 区分と supersede の status 行記法を正式化する**

- **status:** Proposed
- **scope:** meta, spec
- **決定:** status を以下の 4 値とし、AI・ツールが機械的に扱えるよう**有効（effective）/ 失効（inactive）**の 2 区分を定義する:

  | status | 区分 | 意味 |
  |---|---|---|
  | `Proposed` | 有効（未確定） | 提案中。合意・実装に至っていない |
  | `Implemented` | 有効 | 実装済み |
  | `Superseded` | 失効 | 新しい GDR に置き換えられた |
  | `Rejected` | 失効 | **GDR として起票されたが、レビュー・合意で採用されなかった** |

  supersede の相互リンクは **status 行に書く**記法として正式化する — 旧: `- **status:** Superseded by GDR-UI-003`、新: `- **status:** Implemented (supersedes GDR-UI-001)`。status 行の先頭トークンが status 値、括弧内が置換リンク。`Rejected` は理由配下のサブ箇条書き `- **却下理由:** ...` を必須とする。二段保管（INDEX に 1 行サマリ + 本文を `_archive/` へ退避）は失効 2 値の両方に適用する。`Accepted`（合意済み・未実装）は追加しない
- **理由:** 失効判断の誤参照を防ぐには、まず「どのレコードが失効しているか」が status 値だけで判定できなければならない。現行 3 値では、GDR として起票されたがレビューで却下された判断の行き場がなく、`Proposed` のまま放置される（AI からは「検討中の有効な案」に見える）か、削除されて「なぜ採らなかったか」が消える（GDR の目的 3「同じ議論の繰り返しを防ぐ」に反する）。supersede 記法は 01 §3 に例示（`Superseded by` / `Supersedes`）はあるが**書く場所が未規定**で、機械抽出が安定しない
  - **代替案 A:** `Accepted` も追加して 5 値化 → ビルドアップサイクルでは合意 → 実装の間隔が短く（同一セッション〜数日）、合意の事実は T2 実行計画のタスク 0.1 で記録済み。区分（有効 / 失効）にも影響しない。状態を増やす運用コストに見合わないため再検討条件行き
  - **代替案 B:** 却下案は採用 GDR の「代替案」サブ箇条書きにのみ残す（現行運用）→ 採用 GDR が存在しないまま却下された提案（「この機能は作らない」と決めたが、作らないこと自体を GDR にしなかった場合等）を記録できない。却下は既存記法で済む場面では引き続き代替案で書き、**独立 GDR として起票済みのものだけ** `Rejected` にする、という併用で採用
  - **代替案 C:** `supersedes` / `superseded-by` を任意フィールド「関連」に移す → GDR-META-025 で「supersede 系は status 行」と決めたばかりであり、status と置換関係は同時に変わるため同じ行にある方が更新漏れが起きにくい。却下
- **影響:**
  - 01 §3 の status 表・書式、T2 / 00_GETTING_STARTED の status プレースホルダを 4 値に更新する
  - 06 可視化ガイドの status 視覚語彙に `Rejected`（記号 ✖ / classDef）を追加する
  - 007 gdr-index のパーサ・lint 仕様に追随が必要（§4.4 の申し送り）
  - 既存レコードへの遡及影響なし（既存の `Superseded by GDR-X` 記法は新記法そのもの）
- **再検討条件:**
  - 合意済みだが未実装の GDR が長期滞留し、`Proposed` の未確定性と区別したい事例が繰り返し発生 → `Accepted` 追加（代替案 A）を再検討
  - `Rejected` の記録率が低く、却下判断が再議論される事例が発生 → 起票フェーズでの却下記録の強制を検討
- **日時:** 2026-09-28T04:42:08+09:00
- **関連:** derived-from §2-1, derived-from §2-2, refines GDR-META-025
- **理由の出所:** ai（合意時に更新。懸念の起点は外部レビュー文書 — §2 冒頭）


**GDR-META-029: AI は失効レコードを判断の根拠にしない — 直接参照では後継を末端までたどり、検索基盤では既定で有効のみ + 失効ヒットは後継へのリダイレクトとして返す**

- **status:** Proposed
- **scope:** meta, pol
- **決定:** AI の GDR 参照規則を次のとおり定める。
  1. **根拠にしてよいのは有効レコードのみ。** 失効レコード（Superseded / Rejected）を実装・提案の根拠として引用しない
  2. **失効レコードに到達したら後継をたどる。** `Superseded by` を**末端の有効レコードまで**たどり、そのレコードを根拠にする。後継が見つからない・循環する場合は根拠にせず、整合性の破損として人間に報告する
  3. **`Rejected` は「採らない理由」としてのみ引用する。** 同じ案が再提案されたときに「GDR-X-NNN で却下済み（却下理由: …）」と示す用途に限る
  4. **`Proposed` は未確定として扱う。** 引用時は「未確定（Proposed）」と明示し、合意なしにそれを前提とした実装へ進まない

  検索基盤（007 gdr-index）では、`gdr_search` の**既定フィルタを有効レコードのみ**とする。ただし失効レコードがクエリに一致した場合は結果から黙って落とさず、**「GDR-X-001（失効）→ 現行: GDR-X-003」のリダイレクト行**として返す。全件検索は `include_inactive=true` の明示指定時のみ。`gdr_get` は失効レコードに対し、本文の前に失効バナーと後継チェーンの末端 ID を付与する
- **理由:** 記録が増えるほど、覆された古い判断がキーワードに一致する確率は上がり、AI がそれを現行の判断と誤認して動く危険が増える。これは「記録すること」より深刻な GDR の実運用上の急所である。ただし失効レコードを単純に検索から除外すると別の失敗が起きる — 旧用語（例:「セッションを Memcached に」）で検索して何もヒットしなければ、AI は「未決定」と判断して既決事項を再議論する（02 §3.2 の反復ループ）。リダイレクト行はこの両方を防ぐ: 旧判断は根拠として提示されないが、現行判断への到達路は残る。規則を AI の振る舞いとして先に定めるのは、007 が未実装（フェーズ 0）の現在、AI は INDEX とファイルを直接読んでおり、ツールより先に規律が必要なため
  - **代替案 A:** 検索時に失効レコードを完全除外 → 旧用語での検索が空振りし、再議論を誘発する。却下
  - **代替案 B:** 全件返し、status 表示だけに委ねる → 要約形式の検索結果では status 列の見落としが起きやすく、検索上位に失効レコードが来ると AI がそのまま引用する。却下
  - **代替案 C:** 失効レコードの本文を物理削除 → 「なぜ変えたか」の履歴が消え、GDR の目的 1 に反する。二段保管（退避）で十分。却下
- **影響:**
  - 02 §6「AI に求められる振る舞い」に「参照の規律」行を追加する
  - `/gdr-flow`・`/gdr-kaizen` の起票フェーズで過去 GDR を参照する手順に、上記 4 規則を適用する（コマンド定義は `~/.claude/commands/` 配下 — リポジトリ外配備）
  - 007 の `gdr_search` / `gdr_get` / `lint` 仕様に追随が必要（§4.4 の申し送り）
- **再検討条件:**
  - 後継たどりで循環・断絶が繰り返し見つかる → lint による supersede チェーン検査の常時実行（`/gdr-docs` への統合）を検討
  - リダイレクト行が検索結果を圧迫する規模（1 クエリで失効ヒットが多数）→ リダイレクトの集約表示（同一後継への複数リダイレクトを 1 行化）を検討
- **日時:** 2026-09-28T04:42:08+09:00
- **関連:** depends-on GDR-META-028, derived-from §2-3
- **理由の出所:** ai（合意時に更新。懸念の起点は外部レビュー文書 — §2 冒頭）


**GDR-META-030: 任意フィールド「理由の出所」（`human` / `ai-reviewed` / `ai`）を追加し、AI 起票時は記入を必須にする**

- **status:** Proposed
- **scope:** meta, spec, pol
- **決定:** GDR-META-025 の任意フィールドに**「理由の出所」**を追加する。値は閉集合の 3 値:

  | 値 | 意味 |
  |---|---|
  | `human` | 理由の核心が人間の発言・文書に由来する（AI は整形のみ）。発言の短い引用または出典を括弧で添える: `human（ユーザー発言「DB 化する際に timestamp はしっかり管理したい」）` |
  | `ai-reviewed` | AI が起案し、人間がレビュー・合意の工程で内容を確認した |
  | `ai` | AI の推論のみで人間が未確認（既存コードからの遡及記録、自律実行中の判断等） |

  仕様上は任意フィールドとし既存レコードに遡及しないが、**AI が GDR を起票・更新する場合は記入を必須**とする。欠落は「不明」とみなし、信頼度判断では `ai` と同等に扱う。合意時に `ai` → `ai-reviewed` へ更新するのは軽微な追記扱い（新 GDR 不要）。あわせて、**AI は理由が不明な判断に理由を補完しない** — 根拠が確認できない場合は理由欄に「不明（記録時点で根拠未確認）」と書き、出所は `ai` とする
- **理由:** AI に記録を書かせると、理由や却下した代替案を**後付けでもっともらしく生成**しがちであり、しかも生成された理由は人間由来の理由と見分けがつかない。02 §3.2 は GDR がハルシネーションを「◎ 構造的に強く抑止する」としているが、これは理由欄が**実在する根拠で埋まる**ことを前提にしており、その前提自体が検証されていない。出所を区別しておけば、後に判断を見直す人間・AI が「この理由は誰かが実際にそう考えたのか、AI の推定なのか」を判断でき、再検討時の信頼度付けができる。任意フィールドにするのは「6 必須フィールド不変」（GDR-META-025）を守るためで、AI 起票時必須とすることで記入率の問題は回避する（人間が手で書く GDR はそもそも出所が `human` 自明）
  - **代替案 A:** 7 番目の必須フィールドにする → 既存全レコードが書式違反になり、GDR-META-025 の後方互換方針に反する。AI 起票時必須で実効性は同等。却下
  - **代替案 B:** 理由・代替案の箇条書きごとに出所を付ける → 精度は上がるが記述が煩雑になり、読み手の負担が大きい。レコード単位 + `human` の引用添付で当面十分。再検討条件行き
  - **代替案 C:** 2 値（`human` / `ai`）→ レビュー・合意を経た AI 起案（現状の大半）と、人間が一度も見ていない AI 推定の区別がつかない。信頼度の差が最も大きいのはこの境界であるため 3 値とする。却下
- **影響:**
  - 01 §3.1 任意フィールド表に 1 行追加、T2 テンプレートに記入例を追加する
  - 02 §3.2 ハルシネーション行の記述を「出所の区別と組み合わせて効果を発揮」に改め、§6 に「出所の明示」行を追加する
  - `/gdr-flow`・`/gdr-kaizen`・`/gdr-docs`（合意・完了時の `ai` → `ai-reviewed` 更新）のコマンド定義に記入規則を追加する（リポジトリ外配備）
  - 007 gdr-index の `records` に `rationale_source` 列を追加する申し送り（§4.4）
- **再検討条件:**
  - レコード内で出所が混在し、単一値では誤解を招く事例が繰り返し発生 → 箇条書き単位の出所（代替案 B）を再検討
  - `ai-reviewed` のレビューが形骸化（未読合意）している兆候 → 値の意味の見直し、または合意時の確認観点の明文化
- **日時:** 2026-09-28T04:42:08+09:00
- **関連:** refines GDR-META-025, derived-from §2-4
- **理由の出所:** ai（合意時に更新。懸念の起点は外部レビュー文書 — §2 冒頭）

## 2. 現状

外部レビュー（GDR の骨格 — 全意思決定の記録 / INDEX → 本文の二段参照 / SQLite FTS5 の検索 + ID 取得 / `/gdr-flow`・`/gdr-bug-report`・`/gdr-kaizen` — に対する評価）で、「実運用で効いてくるのは記録することより、古い決定を AI に誤って拾わせないこと」という指摘を受けた。これを起点に現行仕様を点検した結果:

1. **却下された GDR の行き場がない** — status は `Proposed / Implemented / Superseded` の 3 値で、GDR として起票されたがレビューで採用されなかった判断を表す値がない。`Proposed` のまま残れば AI には有効な案に見え、削除すれば却下理由が失われる
2. **supersede リンクの記法が未規定** — 01 §3 は「相互リンクを貼ること」と例（`Superseded by` / `Supersedes`）を示すのみで、どのフィールドに書くかを定めていない。機械的に後継をたどる前提が成立しない
3. **失効レコードを AI がどう扱うかの規則がない** — 二段保管（006）によりセッション開始時の読み込みからは外れるが、grep・明示参照・将来の検索（007 `gdr_search` は status 引数が任意で既定値なし）では失効レコードが普通にヒットし、それを根拠にしてはならないという規律がどこにも書かれていない
4. **理由の出所が区別されていない** — 理由・代替案が人間の発言由来か AI の推定かを記録する手段がない。02 §3.2 はハルシネーション抑止を ◎ としているが、AI が理由を後付けで生成するケースを考慮していない
5. **すでに対処済みのもの（本提案で触らない）** — 日本語検索の精度は 007 GDR-META-021（FTS5 trigram + 2 文字語の LIKE フォールバック + ローカル embedding のハイブリッド）で扱っている。インデックス → 本文の二段参照は 007 GDR-META-022（`gdr_search` は要約、全文は `gdr_get`）で確立済み

## 3. 改善案

3 つの GDR で「status の区分」「参照の規律」「理由の信頼度」を定義する。書式変更は **status 値の追加 1 つと任意フィールドの追加 1 つ**で、6 必須フィールドは不変・既存レコードへの遡及影響はない。

1. **status 4 値化と有効 / 失効の区分**（GDR-META-028）— 失効が status 値だけで判定できる
2. **参照の規律とリダイレクト**（GDR-META-029）— 失効判断を根拠にせず、しかし現行判断への到達路は残す
3. **理由の出所**（GDR-META-030）— 人間由来の理由と AI の推定を見分けられる

- **理由の出所:** ai-reviewed

### 4.2. AI の参照フロー

```
GDR を参照する
  │
  ├─ status = Implemented ─────────→ 根拠として引用可
  ├─ status = Proposed ────────────→ 「未確定」と明示して引用。合意なしに前提にしない
  ├─ status = Superseded by X ─────→ X へ移動して再判定（末端の有効レコードまで）
  │                                    └─ 断絶・循環 → 根拠にせず人間に報告
  └─ status = Rejected ────────────→ 「採らない理由」としてのみ引用
```

### 4.3. 理由の出所の運用

| 場面 | 記入する値 |
|---|---|
| ユーザーが理由を述べ、AI が GDR 化した | `human`（発言の短い引用を添える） |
| AI が起票し、`レビュー：` → `レビュー反映：` → 合意を経た | 起票時 `ai` → 合意時に `ai-reviewed` へ更新 |
| AI が既存コード・過去文書から判断を遡及記録した | `ai`（人間が確認したら `ai-reviewed`） |
| 理由が確認できない | 理由欄に「不明（記録時点で根拠未確認）」、出所は `ai` |

- `human` の引用は「誰かが実際にそう言った」ことの証跡であり、要約・言い換えではなく**発言の断片そのもの**を書く
- 1 レコード内で出所が混在する場合は**弱い方**（`human` と `ai` が混在 → `ai-reviewed` 以下）を記入し、人間由来の部分は引用で示す

### 4.4. gdr-index（007 提案）との整合 — 申し送り

本提案は 007 の実装に**依存しない**（参照規律は AI の振る舞いとして今日から成立する）が、007 実装時に以下の追随が必要になる:

1. **パーサ** — status 行を「先頭トークン = status 値、`by GDR-X` / `(supersedes GDR-X)` = 置換リンク」として分解し、`links` に `supersedes` / `superseded_by` を正規化する。`Rejected` を正当な status 値として受け付ける
2. **`records` への列追加** — `effective`（Proposed / Implemented = 1、Superseded / Rejected = 0 の派生列）、`rationale_source`（欠落は NULL = 不明）
3. **`gdr_search` の既定** — `WHERE effective = 1` を既定とし、失効ヒットは後継チェーン末端 ID を解決してリダイレクト行で返す。`include_inactive` 引数を追加
4. **`gdr_get`** — 失効レコードに失効バナー + 後継末端 ID を前置
5. **lint** — (a) Superseded の後継 ID 欠落・後継側の `supersedes` 欠落（相互リンク不整合）、(b) supersede チェーンの循環・断絶、(c) `Rejected` の `却下理由` 欠落、を警告する

007 本文は編集しない（起票済み文書の遡及編集を避ける）。007 の実装フェーズ着手時に本節を参照すること。

## 5. 検討課題

1. **`Accepted` を追加するか**
   - 解決策: 追加しない。有効 / 失効の区分に影響せず、合意の事実は T2 実行計画で記録済み。長期滞留が問題化したら再検討
   - → GDR-META-028 の代替案 A / 再検討条件として確定
2. **既存レコードへの「理由の出所」遡及**
   - 解決策: 遡及しない。欠落 = 不明として扱う規則で足りる。重要な判断を見直す機会に、人間が確認して記入する
   - → GDR-META-030 の決定に明記済み
3. **本リポジトリ自身の既存 GDR（META-001〜027）に `Rejected` 相当が埋もれていないか**
   - 解決策: 実装フェーズ 1 の作業中に INDEX / kaizen 01〜08 を一巡し、`Proposed` のまま放置されている GDR を洗い出す。見つかった場合の status 変更はユーザー判断とする
   - → フェーズ 1 のタスクとして追加済み
4. **`human` の引用が長文化・個人情報を含むリスク**
   - 解決策: 引用は判断の核心を示す断片（1 文程度）に限る。個人名は役割（「ユーザー」「レビュアー」）に置き換える
   - → §4.3 の運用に反映済み
