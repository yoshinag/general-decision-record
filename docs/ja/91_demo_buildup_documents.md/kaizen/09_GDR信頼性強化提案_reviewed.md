第 1 回で導入した「旧は新の `Accepted` 時点で失効」規則を、**異常系（合意後に新が頓挫する）**と**退避のタイミング**まで追いかけた。

---

## A. 実装着手前に反映が必要

### A-1. 合意後に新 GDR が頓挫すると、確定判断の空白が再発する（最重要）

GDR-META-028 の遷移は `Proposed → Accepted → Implemented` と `Proposed → Rejected` のみで、**`Accepted` になった後に取りやめる経路がない**。しかし 02 §5.3「実装が判断を検証する」のとおり、合意後の実装で前提が崩れて新判断を放棄することは普通に起きる。

```
旧 002: Superseded by GDR-INFRA-003   ← 新の Accepted 時点で失効済み
新 003: Accepted → 実装中に頓挫        ← 行き先の status がない
コードの実態: 旧 002 のまま
```

新を `Rejected` にしても、旧は `Superseded` のまま残り、後継たどりの末端が失効レコードになる。**第 1 回で塞いだ「確定判断の空白」が異常系で再発する。**

→ 次の 2 点を 028 に追加する:
1. 遷移に **`Accepted → Rejected`**（合意後の撤回）を加える。却下理由に「実装段階で撤回」の旨を書く
2. 撤回された新が `supersedes` を持っていた場合、**旧の status を置換前の値に戻し**、注記で経緯を残す（例: `- **status:** Implemented（GDR-INFRA-003 の撤回により復帰）`）。旧の判断内容は変わっていないため、「判断の本質が変わる更新」ではなく軽微な訂正として扱ってよい

### A-2. 二段保管（退避）のタイミングが未定義で、A-1 の復帰を難しくする

§4.1 の遷移図は「新 003 実装 →（旧は退避済み）」としており、旧の退避を `Superseded` 化と同時と読める。この場合、A-1 の復帰時に `_archive/` から本文を戻す作業が発生し、しかも退避中は `notes/_archive/` が AI のデフォルト読み込み対象外であるため、**新が `Accepted` の間（実装はまだ旧のまま）に旧の中身を AI が参照できない**。

→ 退避は**新が `Implemented` になった時点**と定める。`Accepted` の間は旧を `Superseded` にしつつ元の位置に置き、INDEX にも両方を残す。§4.1 の遷移図・INDEX 例、02 §5.2 更新タスク（2.1）に反映する。`Rejected` の退避はその時点で行ってよい（復帰の対象にならないため）。

### A-3. `Rejected` の再提案経路が未定義

§4.1 の却下例は再検討条件（「設定項目が 10 以下に整理された場合」）を持つ。条件が満たされたとき、どう再提案するかが定義されていない。遷移に `Rejected → …` はなく、`supersedes` は失効レコードを置き換える用途ではない。

→ 「`Rejected` は終端状態。再提案は**新 GDR を起票し、`関連: derived-from GDR-UI-004` で経緯をつなぐ**（`supersedes` は使わない）」と明記する。GDR-META-025 の既存語彙で足りるため、新しい語彙は不要。

### A-4. タスク一覧に 3 値前提の箇所の漏れがある

grep で 3 値（`Proposed / Implemented / Superseded`）を前提にしている箇所を洗い出した結果、次がタスクに含まれていない:

| 箇所 | 内容 | 追加先 |
|---|---|---|
| リポジトリ直下 `CLAUDE.md` | 「GDR 書式」節の status 行が 3 値 | タスク 1.2 |
| `~/.claude/commands/gdr-docs.md` | 実装完了時の更新が `Proposed → Implemented` 固定 | タスク 3.1（`Accepted → Implemented` に。`Proposed` のままのレコードに実装コミットが対応していたら、合意漏れとして警告） |
| `~/.claude/commands/gdr-map.md` | 構造ビューの status 記号が 3 種 | タスク 3.1（2.2 と同期） |

## G. 全体評価

**第 1 回の構造（`Accepted` の追加と「新の合意時点で旧を失効」）は正しいが、正常系しか検証していなかった。** 合意後の撤回という異常系で、第 1 回で塞いだ空白が再び開く（A-1）。退避を `Implemented` 時点まで遅らせれば（A-2）、復帰はファイルの移動なしで status 行の訂正だけで済み、撤回経路のコストはほぼゼロになる。

いずれも新しい status 値・語彙を増やさずに閉じられる。反映後は、正常系・撤回・置換・却下からの再提案の 4 経路すべてで「確定した有効判断が常にちょうど 1 つ存在する」ことを §4.1 の図で示せる状態になり、合意に進めてよい。
