## A. 実装着手前に反映が必要

### A-1. supersede の「切り替え時点」が未定義で、`Accepted` 不採用と衝突する（最重要）

GDR-META-028 は status 値と記法を定めたが、**旧レコードをいつ `Superseded` にするか**を定めていない。現行運用（合意時に新 GDR を起票し、旧を即 Superseded）のままだと次の窓が生じる:

```
旧 GDR-X-001: Superseded by GDR-X-002   ← 失効（根拠にできない）
新 GDR-X-002: Proposed                   ← 未確定（029 規則 4: 合意なしに前提にしない）
```

この間、029 の参照フローで後継をたどると末端が「未確定」になり、**有効な確定判断がどこにも存在しない**状態になる。しかもコード上の現実はまだ旧判断のまま。

さらに、合意後・実装前の新 GDR は `Proposed` のままであり、029 規則 4「合意なしに前提にしない」を AI が守ろうとしても、**GDR 本文だけでは合意済みかどうかを判定できない**（合意の事実は T2 タスク 0.1 にしかなく、実プロジェクトでは GDR が `notes/91_gdr/gdr/` に T2 と分離して置かれることが多い）。

→ 選択肢（反映時にユーザー判断が必要）:

| 案 | 内容 | コスト |
|---|---|---|
| **案 1（推奨）** | `Accepted`（合意済み・未実装）を追加して 5 値化。旧の `Superseded` 化は新が **`Accepted` になった時点**。029 規則 4 は「`Proposed` は前提にしない / `Accepted` は前提にしてよい」と単純化 | status 更新が 1 回増える（合意時）。028 代替案 A を採用に転じる |
| 案 2 | 4 値のまま、旧の `Superseded` 化を新が **`Implemented` になった時点**に遅らせる。新は `Proposed (supersedes X)` として並存 | 合意済み判定の問題（規則 4）は残り、「T2 等で合意が確認できれば前提にしてよい」という参照先依存の規則が必要 |

起票時に `Accepted` を不採用とした根拠（「合意 → 実装が短い」「合意は T2 に記録済み」）は、後者が GDR 単体で判定できない点を見落としていた。案 1 を推奨する。

### A-2. `Rejected` と「しないと決めた GDR」の区別が曖昧

GDR は「何をしないか」も決定として記録できる（01 §3）。「機能 X は作らない」は `Implemented` な否定決定であって `Rejected` ではない。ところが 028 代替案 B の例（「この機能は作らない」と決めたが…）は否定決定の事例であり、`Rejected` の用途説明として誤っている。

→ 定義を明確化する:
- `Rejected` = **起票された提案そのものが採用されなかった**（決定案が棄却された記録）
- 「しない」こと自体を今後の方針として拘束したい場合は、否定形の決定を持つ GDR を別途起票する（`Implemented`）
- 代替案 B の例を「レビューで合意に至らなかった提案 GDR」に差し替える

### A-3. 「理由の出所」の値書式が曖昧（括弧・注記）

- 本文 3 レコードが `ai（合意時に更新。懸念の起点は…）` と注記付きで書いているが、括弧の用法は `human` の引用としてしか定義されていない
- status 行の置換リンクは半角 `(supersedes …)`、出所の注記は全角 `（…）` と混在している

→ 「**先頭トークンが値、以降の括弧内は注記**。`human` では引用必須、他の値では任意」と一般化し、括弧は全角・半角どちらも許容（パーサは両方受ける）と明記する。status 行側も同じ規則で説明できるようにそろえる。

### A-4. 出所が混在する場合の規則が論理的に破綻している

§4.3「`human` と `ai` が混在 → `ai-reviewed` 以下」は、人間のレビューの有無と無関係に `ai-reviewed` が出てくるため誤り（`ai-reviewed` はレビューを経たことの表明）。

→ 順序 `human > ai-reviewed > ai` を定義し、「**レコードの値 = 含まれる部分のうち最も弱い値**。レビュー・合意を経た時点で `ai` の部分は `ai-reviewed` に上がる」とする。例: `human` + 未確認の `ai` → `ai`、合意後 → `ai-reviewed`。

### A-5. 失効 2 値の INDEX 1 行サマリ書式が `Rejected` 側で未定義

028 は二段保管を失効 2 値に適用するとしたが、INDEX の 1 行形式は Superseded 用（`— Superseded by GDR-NEW-MMM → archived`）しかない。

→ `GDR-X-NNN（要約） — Rejected（却下理由の要約） → archived` を併記する。

## G. 全体評価

**方向性は妥当、ただし状態遷移の設計に 1 つ穴がある。** 失効判断の誤参照防止（除外ではなくリダイレクト）と理由の出所（3 値・AI 起票時必須）は、外部指摘を単純適用せずに ROI の範囲で具体化できている。書式の破壊的変更もない。

一方、status を「値の集合」としてだけ設計し、**遷移のタイミング**（いつ旧を失効させるか、合意をどこで判定するか）を検討していなかった。その結果、`Accepted` を見送った根拠が成り立たなくなっている（A-1）。これは「古い判断を AI に拾わせない」という本提案の目的そのものに関わるため、反映必須。A-1 の判断次第で 028 / 029 の書き直し量が変わるので、最初に決める。
