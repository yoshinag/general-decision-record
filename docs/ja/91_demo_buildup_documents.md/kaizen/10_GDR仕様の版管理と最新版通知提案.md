## 1. GDR（General Decision Record）

**GDR-META-031: GDR 仕様に `vMAJOR.MINOR` の版を付け、「採用時に必須の移行があるか」で桁を上げ分け、git タグと CHANGELOG で発行する**

- **status:** Implemented
- **scope:** meta, pol
- **決定:** 上流リポジトリの GDR 仕様（01 / 02 / guide / templates / Claude Code セットアップ仕様）に **`vMAJOR.MINOR`** の版を付ける。桁は**導入先が採用するときに必須の移行作業があるか**で決める:
  - **MAJOR** — 採用時に必須の移行項目がある。書式違反化（必須フィールドの追加・改名、status 値の廃止 等）に加え、**既存の値の意味の変更**（既存レコードを書き換えないと新しい規則の下で誤って解釈されるもの）を含む
  - **MINOR** — 必須の移行項目がない（新しい任意フィールド・コマンド・ガイドの追加など、既存レコードがそのまま同じ意味で有効な変更）
  - 文言修正・誤字・例の差し替えなど、導入先に移行作業が生じない変更は版を上げない

  発行は **git タグ `vX.Y`** と **`CHANGELOG.md` のエントリ**で行う。エントリには次の 4 項目を必須とする: (1) 互換性（MAJOR / MINOR）、(2) 変更の要約と根拠 kaizen / GDR、(3) 導入先の移行項目を **必須 / 推奨 / 任意** に区分したもの、(4) user-level config（`~/.claude/`）の更新要否。

  **初版と次版:** 009 実装前の最終仕様変更（`0eea056` — 008 実装完了時点）を **v1.0** とし、遡及してタグを打つ。009（status の意味変更を含む）と本提案の実装完了を合わせて **v2.0** として発行する
- **理由:** 導入先の `_reference/` は上流の決定のコピーであり、上流が変わった瞬間に陳腐化する。009 が個々の GDR に対して解こうとしている「陳腐化した決定を AI に拾わせない」問題が、フレームワーク自身の配布で未解決のまま残っている — 版がなければ「古い」を判定する基準そのものが存在しない。桁を「必須移行の有無」で決めるのは、導入先が知りたいのは「何が変わったか」より「**自分は何をしなければならないか**」であり、版番号だけでその問いに答えられるため。起票時は「既存レコードが書式として有効なら MINOR」と定義していたが、009 の `Proposed` は書式を変えずに**意味を狭めた**（旧: 実運用では合意済み・未実装も含む / 新: 合意に至っていない）ため、採用時に棚卸しをしないと合意済みの判断が未確定として扱われる。書式だけの定義ではこの種の変更が MINOR に紛れ込み、「MINOR なら安全に上げられる」という版番号の約束が破れる。PATCH を持たないのは、移行作業を生まない変更で通知を出すとノイズになり、通知の信頼性が下がるため
  - **代替案 A:** 版を付けず、コミットハッシュで追跡する → 「どれだけ古いか」「移行が必要か」がハッシュからは読めない。却下
  - **代替案 B:** SemVer の 3 桁（PATCH あり）→ PATCH は移行作業ゼロの変更であり、通知・宣言の対象にならない。桁を増やすだけの効果しかない。却下
  - **代替案 C:** 日付版（`2026.09`）→ 互換性が読めない。却下
  - **代替案 D:** MAJOR を書式違反化に限り、MINOR にも必須移行を許す（009 は v1.1）→ 版番号から移行の要否が読めなくなる。セルフレビューで検討し、ユーザー判断（「案1: 必須移行ありなら MAJOR」）で却下
- **影響:**
  - `CHANGELOG.md`（現状は公開日 1 行のみ）を v1.0 の要約（kaizen 001〜008 の到達点）から書き直す
  - 仕様変更を含む kaizen は、完了処理で「版を上げるか・どちらの桁か」を判定する工程が増える（`/gdr-docs` の整理観点に追加）
  - タグは push しない限りローカルに留まる — 公開はユーザー操作
- **再検討条件:**
  - MAJOR が頻発し、導入先が追随を放棄する兆候 → 複数の変更を束ねて発行する運用、または互換モード（GDR-META-034）で吸収できる変更の MINOR 扱いを再検討
  - 英語版など多言語化で仕様本文が複数系統になる → 版を言語共通にするか言語別にするかを再検討
- **日時:** 2026-09-28T04:55:34+09:00

**GDR-META-032: 導入先は前提定義書に準拠する仕様の版を宣言し、版の採用・更新は GDR-META として記録する**

- **status:** Implemented
- **scope:** meta, spec
- **決定:** T1 前提定義書 §1「プロジェクト情報」に次の 1 行を追加する:

  ```
  GDR 仕様: v2.0（上流 {commit 短縮ハッシュ} / 取得 {YYYY-MM-DD}）
  ```

  この行を**導入先が準拠する版の唯一の宣言**とする。宣言には 2 つの役割がある — (1) 最新版との差の検出（GDR-META-033）、(2) **AI がどの版の規則で GDR を解釈するかの決定**（GDR-META-034）。`_reference/` のスナップショットはこの版に対応するものを置く。版の変更は前提定義書を直接編集せず、**GDR-META を発行**して「vX → vY を採用。移行した項目 / 見送った推奨・任意項目とその理由」を記録し、その GDR を根拠に宣言行を更新する（scope / PREFIX 改廃と同じ規律）。MAJOR の採用では、必須の移行項目を完了してから宣言行を更新する（宣言が先行すると、未移行のレコードが新しい規則で解釈される）。宣言のない導入先は **v1.0** として扱う。初回導入時は GDR-META-001 の決定に採用版を含める（03 初回プロンプトガイドの手順として示す）
- **理由:** 陳腐化の判定には「導入先がどの版に従っているか」が必要で、それは導入先の**決定**である — 上流が新しい版を出しても、導入先が旧版のまま運用し続けることは正当な選択になりうる。決定であれば GDR で記録するのが方法論の一貫性であり、見送った移行項目と理由が残ることで、後から「なぜこのプロジェクトは Accepted を使っていないのか」に答えられる。さらに宣言は、user-level config の規則をどの版で解釈するかの切り替えスイッチにもなる（GDR-META-034）— 宣言の更新を必須移行の完了後に限るのはこのため
  - **代替案 A:** `_reference/VERSION` ファイルに記録する → スナップショットの「事実」と導入先の「採用判断」が混同される（スナップショットは更新したが移行は未判断、という状態を表せない）。却下
  - **代替案 B:** 版の更新を GDR 化せず宣言行の直接編集で済ませる → 見送った移行項目の理由が残らない。scope / PREFIX 改廃を GDR-META 経由とした既存規律とも不整合。却下
- **影響:**
  - T1 テンプレート §1 に宣言行を追加する（T0 サンプルは「最小の型」を示す役割のため変更しない）
  - 03 初回プロンプトガイド・`~/.claude/CLAUDE.md` の初回導入手順に「宣言行の記入と GDR-META-001 への採用版の記載」を追加する
  - 既存の導入先は宣言がないため v1.0 として扱われ、`/gdr-upgrade`（GDR-META-033）で初回宣言を行う
- **再検討条件:**
  - 導入先が複数の上流（フォーク等）を参照する事例が発生 → 宣言行に上流の識別子を加える
- **日時:** 2026-09-28T04:55:34+09:00
- **関連:** depends-on GDR-META-031, derived-from §2-3
- **理由の出所:** ai-reviewed（合意: ユーザー「010, ok」）


**GDR-META-033: 最新版の検出は `/gdr-*` コマンド・短縮キーワードの実行時に宣言版と user-level config の「現行版」を比較して行い、移行は標準コマンド `/gdr-upgrade` で行う。自動移行はしない**

- **status:** Implemented
- **scope:** meta, pol
- **決定:**
  - **検出（受動・ネットワーク不要）:** `~/.claude/CLAUDE.md` の GDR 方法論セクションに**「GDR 仕様の現行版: vX.Y」**の 1 行を置く。AI は GDR 導入済みプロジェクトで **`/gdr-*` コマンドまたは短縮キーワードを実行するとき**、前提定義書の `GDR 仕様` 行を読み（セッション内で 1 回。GDR-META-034 の解釈版の決定と同じ手順）、現行版と比較する。導入先が古い・未宣言であれば**セッション内で 1 回だけ**「GDR 仕様 vX.Y が利用可能（このプロジェクト: vA.B）。`/gdr-upgrade` で差分と移行項目を確認できます」と通知する。作業は中断しない。前提定義書は標準の `notes/91_gdr/00_CONTEXT_DEFINITIONS.md` を優先し、旧慣行（`notes/gdr/` / `documents/`）も探す
  - **確認と移行（能動・ネットワークあり）:** 標準コマンド **`/gdr-upgrade`**（短縮キーワードなし — `/gdr-docs` と同じ扱い）を新設する。動作: (1) 上流の最新タグを取得し、user-level config の現行版とも比較（config 自体が古ければその旨を報告。`gh` 未認証時は raw の CHANGELOG 取得にフォールバック）、(2) 導入先の宣言版から最新までの CHANGELOG エントリを提示、(3) 移行項目を必須 / 推奨 / 任意で一覧化し、どれを実施するかをユーザーに確認、(4) `_reference/` を対象版で取り直し、(5) GDR-META を起票（GDR-META-032）、(6) 必須項目がなければ宣言行を更新して 1 コミット。必須項目がある場合は、その作業を通常のビルドアップサイクル（改善提案 or `/gdr-flow`）で行い、**完了後に宣言行を更新する**
  - **自動移行はしない。** 版を上げずに留まる選択（旧版のまま運用）も GDR-META として記録できる
- **理由:** 「最新はこれ」を導入先に伝える最も確実な経路は、全プロジェクトの起動時に読み込まれる user-level config である — コマンド定義・CLAUDE.md を更新した時点で、導入済みの全プロジェクトが次のセッションから新しい版を知る。検出の契機を GDR のコマンド・キーワード実行時に限るのは、前提定義書を毎セッション読む規則はなく、確実に比較が走る地点を明示する必要があるため（起票時は「前提定義書は AI が元々読む文書」としていたが、これは誤りだった）。契機を絞っても、GDR を使う作業であれば必ず通過するので検出漏れは実用上起きない。user-level config 自体が古い場合はこの経路では検出できないため、ネットワーク確認は明示的に呼ぶ `/gdr-upgrade` 側に置き、常時のコスト（毎セッションの API 呼び出し）を避ける。自動移行をしないのは、移行の採否が導入先の判断（GDR-META-032）であり、既存 GDR の書き換えを伴う作業を AI が無断で行うと「文書と実装を混ぜない」「判断は合意を経る」の両原則に反するため
  - **代替案 A:** SessionStart hook で毎回上流の最新タグを取得する → user-level config が古い場合も検出できるが、全セッションでネットワーク呼び出しが発生し、hook の配置という追加のセットアップが要る。再検討条件行き
  - **代替案 B:** 通知を出さず、ユーザーが気づいたときに `/gdr-upgrade` を呼ぶ → 現状と同じく「知る術がない」問題が残る。却下
  - **代替案 C:** 古い版を検出したら自動で移行する → 採否の判断を奪い、既存レコードの無断書き換えを招く。却下
  - **代替案 D:** 短縮キーワード（`更新：` 等）を既定 7 種目として追加する → 版の更新は数か月に一度の保守操作で、ビルドアップサイクルの節目ではない。既定キーワードはサイクル必須操作に限る現行方針（GDR-META-026）を維持。却下
- **影響:**
  - `~/.claude/CLAUDE.md` に現行版の行と検出・通知の規則を追加、`~/.claude/commands/gdr-upgrade.md` を新設する（リポジトリ外配備）
  - 05 セットアップガイドの「配置するファイル」を「9 ファイル + 任意 1 ファイル」に更新し、`/gdr-upgrade` の仕様と「上流の版が上がったら user-level config の現行版も更新する」手順を追記する
  - 上流で版を発行する手順（タグ → CHANGELOG → user-level config の現行版更新）が 1 セットになる。現行版の更新を忘れると通知が出ないため、発行手順のチェックリストに含める
- **再検討条件:**
  - user-level config の更新漏れ（現行版が古いまま）で通知が出ない事例が実際に発生 → SessionStart hook による上流確認（代替案 A）を再検討
  - 通知が「毎セッション出てうるさい」と感じられる → 見送りを GDR-META で記録した導入先では、その版については通知しない規則を追加

**GDR-META-034: user-level config の版依存の規則は、導入先の宣言版に従って解釈する（互換モード）。未宣言は v1.0 として扱う**

- **status:** Implemented
- **scope:** meta, pol
- **決定:** user-level config（`~/.claude/CLAUDE.md` / `commands/gdr-*.md`）に書く規則のうち、特定の版で導入・変更されたものには**版条件**を付ける（例: 「v2.0 以上: `Proposed` は未確定として前提にしない。v1.x: `Proposed` は合意済み・未実装を含みうる」）。AI は GDR-META-033 の手順で読んだ宣言版に対応する規則で GDR を解釈・操作する。宣言のない導入先は **v1.0** として扱う。上流リポジトリ自身は常に最新版で扱う。互換モードで保持する旧版の規則は**直前の MAJOR まで**とし、それより古い宣言の導入先には「互換規則の提供範囲外」として `/gdr-upgrade` を強く推奨する通知を出す（動作は最も古い保持版の規則で行う）
- **理由:** user-level config は全プロジェクトに即時に届く — これは最新版を知らせる経路（GDR-META-033）であると同時に、**新しい規則を旧版の導入先に先に強制してしまう経路**でもある。実際に 009 の配備で、3 値運用の導入先において `/gdr-docs` が `Proposed → Implemented` を「合意漏れ」として止め、合意済みの GDR が根拠から外れる後方互換性の破れが発生した（§2-6）。規則を宣言版で切り替えれば、上流は後方互換を気にせず規則を進化させられ、導入先は自分のタイミングで版を上げられる — 版の宣言を「知らせるため」だけでなく「**どの版で解釈するか**」を決めるものに格上げするのが、版管理の本来の価値である。保持範囲を直前の MAJOR までに限るのは、版ごとに互換規則が積み上がると user-level config の保守コストと読み込みトークンが増え続けるため
  - **代替案 A:** 互換モードを持たず、上流の変更は常に後方互換に限る → 009 のような意味の変更（誤参照を防ぐために必要だった）が不可能になり、フレームワークが進化できない。却下
  - **代替案 B:** 版ごとに user-level config を丸ごと切り替える（`~/.claude/gdr/v1/` / `v2/`）→ 規則の大半は版に依存せず、全体の複製は保守対象を倍にする。差分の規則だけに版条件を付ける方が小さい。却下
  - **代替案 C:** 互換規則を無期限に保持する → 古い版の規則が蓄積し続ける。直前の MAJOR まで + 範囲外の通知で十分。却下
- **影響:**
  - 009 の配備時に入れた暫定の「旧版互換」規則（`~/.claude/CLAUDE.md` / `gdr-docs` / `gdr-flow` / `gdr-kaizen`、条件は「`GDR 仕様: v2.0` 以上の宣言があるか」）を、本 GDR の版条件の書式に置き換える
  - 上流で版依存の規則を追加・変更するときは、旧版の規則を版条件付きで残す作業が発行手順（§4.5）に加わる
- **再検討条件:**
  - 版条件の分岐が規則の読みやすさを大きく損なう → 版依存の規則を 1 つの節（「版ごとの差分」）に集約する書式を検討
  - 導入先が長期間旧版に留まり、互換規則の打ち切りが実害になる → 保持範囲の延長を検討
- **日時:** 2026-09-28T05:10:53+09:00

## 2. 現状

009 のレビュー中に、ユーザーから「すでに適応されたプロジェクトにこれが最新だと伝える術はないか？」「そういう機能性を持つべきではないか？」という問いがあった。点検した結果:

1. **上流の仕様に版がない** — git タグはなく、`CHANGELOG.md` は公開日（2026-04-16）の 1 行のみ。001〜008 で仕様は何度も変わったが、どの時点の仕様かを名指す手段がない
2. **変更が導入先に何を要求するかが書かれていない** — 例えば 009 は既存レコードの書式を壊さないが、`Proposed` の意味を狭めており、採用時には棚卸しが要る。それを判断できる情報が上流のどこにもない
3. **導入先がどの版に従っているか分からない** — `_reference/` は Method C で取得した編集禁止スナップショットだが、取得時点の上流コミットを記録しておらず、前提定義書（T1）にも版の項目がない
4. **最新版を知る経路と取り込む手順がない** — 00 / 03 / 05 のいずれのガイドにも、導入後に上流の変更を取り込む手順がない。ただし、user-level config（`~/.claude/CLAUDE.md` / `commands/`）は全プロジェクトの起動時に読み込まれるため、**AI の振る舞いに関する変更はすでに全導入先へ即時に届いている** — 届かないのはプロジェクトごとの成果物（`_reference/`・プロジェクト直下 `CLAUDE.md`・前提定義書・既存レコード）だけである
5. **自己矛盾** — 009 は「陳腐化した決定を AI に根拠として使わせない」を主題にしているが、導入先の `_reference/` はまさに陳腐化しうる上流の決定のコピーであり、フレームワーク自身がこの原則を満たしていない
6. **逆方向の問題: 新しい規則が旧版の導入先に先に届く（本提案のセルフレビューで検出）** — §2-4 の「即時に届く」性質は、互換性を壊す経路でもある。009 の実装で user-level config を 5 値前提に更新した結果、3 値運用の導入先では `/gdr-docs` が `Proposed → Implemented` を「合意漏れ」として止め、参照の規律が合意済みの `Proposed` を根拠から外す状態になった。2026-09-28 に暫定の「旧版互換」規則を user-level config に入れて回避済み（§5-5）

---

## 3. 改善案

「版は宣言する / 差は検出する / 規則は宣言版で解釈する / 移行は決定として残す」の 4 点を、4 つの GDR で本体仕様に組み込む。

1. **上流: 版の発行**（GDR-META-031）— `vMAJOR.MINOR`、桁は必須移行の有無、タグ + CHANGELOG（移行項目の 3 区分）
2. **導入先: 版の宣言**（GDR-META-032）— 前提定義書に 1 行、変更は GDR-META、MAJOR は必須移行の完了後に宣言
3. **検出と移行**（GDR-META-033）— コマンド・キーワード実行時に比較して 1 回通知、`/gdr-upgrade` で差分確認・移行判断・記録
4. **互換モード**（GDR-META-034）— user-level の版依存の規則を宣言版で切り替え、旧版の導入先を壊さない

新しい概念は増やさない。版の採用を GDR として記録するのは、既存の「scope / PREFIX の改廃は GDR-META で」と同じ型である。

## 4. 詳細セクション

### 4.1. 全体像

```
[上流リポジトリ]
  仕様変更の kaizen 完了 → 版の判定（必須移行あり = MAJOR / なし = MINOR / 移行ゼロ = 上げない）
        │

                │ （全プロジェクトの起動時に読み込まれる）
                ▼
[導入先プロジェクト]
  前提定義書: 「GDR 仕様: v1.0（…）」（未宣言も v1.0 扱い）
```

### 4.3. 版の採用を記録する GDR-META の例（導入先）

```markdown

- **status:** Implemented
- **scope:** meta
- **決定:** 準拠する GDR 仕様を v1.0 → v2.0 に更新する。必須項目「Proposed の棚卸し」を実施済み（GDR-API-004 / 007 を Accepted、GDR-UI-002 を Rejected）。推奨項目「CLAUDE.md の status 行更新」を実施し、任意項目「理由の出所の遡及記入」は見送る

```

### 4.4. user-level config に置く規則の骨子

```markdown
- **GDR 仕様の現行版:** v2.0（CHANGELOG: https://github.com/yoshinag/general-decision-record/blob/main/CHANGELOG.md）
- GDR 導入済みプロジェクトで `/gdr-*` コマンド・短縮キーワードを実行するとき、前提定義書の「GDR 仕様」行を

  - 通知: 宣言版が現行版より古い / 未宣言なら、セッション内で 1 回だけ次を通知し、作業は続行する
    「GDR 仕様 v{現行} が利用可能です（このプロジェクト: v{宣言}）。`/gdr-upgrade` で差分と移行項目を確認できます」
- 自動で移行しない。

（版条件付き規則の例）
- status: v2.0 以上 = 5 値（Proposed は未確定、合意で Accepted）/ v1.x = 3 値（Proposed は合意済み・未実装を含みうる）

- 理由の出所: v2.0 以上 = AI 起票時に必須 / v1.x = 求めない
```

### 4.5. 上流で版を発行する手順（チェックリスト）

1. 仕様変更を含む kaizen の完了処理で、版を上げるか・どちらの桁かを判定する（必須移行の有無。移行作業が生じないなら上げない）
2. user-level config の版依存の規則に版条件を付け、旧版の規則を保持する（直前の MAJOR まで — GDR-META-034）
3. `CHANGELOG.md` にエントリを追加する（4 項目必須）
4. `git tag vX.Y`（公開は push — ユーザー操作）
5. user-level config の現行版の行を更新する（**忘れると通知が出ない**）
6. 05 セットアップガイドに記載のコマンド仕様を同期する

## 5. 検討課題

1. **コマンド定義ファイル自体の配布**
   - 現状、`~/.claude/commands/gdr-*.md` はリポジトリに含まれず、05 の仕様から各自が作成する。このため他の利用者は「user-level config を最新版に更新する」作業も手作業になる

   - → 申し送り（§7.2）
2. **複数の導入先を一覧で確認したい（メンテナ用途）**

   - → GDR-META-033 の拡張候補
3. **遡及タグ v1.0 の位置**

   - → フェーズ 1 のタスクとして追加済み
4. **009 との順序**
   - 解決策: 009 は実装済み（65b4f01）。009 には「導入先への配布は 010 で扱う」を申し送りとして追記済み（2a2c317）。本提案の実装完了をもって、009 と合わせて v2.0 を発行する
   - → 実行計画の依存として反映済み
5. **009 配備による後方互換性の破れ（§2-6）の暫定対処**
   - 解決策: 本提案のセルフレビューで検出し、ユーザー判断（「今すぐ暫定対処」）で 2026-09-28 に user-level config へ暫定の「旧版互換」規則を入れた（条件: 前提定義書に `GDR 仕様: v2.0` 以上の宣言があるか。上流リポジトリ自身は新規則）。現時点で宣言済みの導入先はないため、全導入先が 009 以前の動作に戻っている
   - → GDR-META-034 の実装（タスク 2.1）で版条件の書式に置き換える
6. **互換規則の保守コスト**
   - 解決策: 保持は直前の MAJOR まで。それより古い宣言には範囲外の通知を出す
   - → GDR-META-034 の決定として確定

## 7. ふりかえり

> 起票時点（2026-09-28）の記録。実装フェーズの完了ごとに追記する。

### 7.1. 観察された傾向

1. **ユーザーの問いによる位置づけの修正** — AI は当初、版管理と通知を「任意のツール（`/gdr-upgrade` + 任意の hook）」として提示した。ユーザーの「そういう機能性を持つべきではないか？」を受けて、009 の原則（陳腐化した決定を拾わせない）がフレームワーク自身の配布に適用されていないという自己矛盾（§2-5）として捉え直し、本体仕様（T1 の宣言・GDR-META による採用記録）に組み込む形に改めた
2. **既存の型の再利用** — 版の採用を GDR-META で記録する設計は、「scope / PREFIX の改廃は GDR-META で」という既存規律の転用であり、新しい概念を増やしていない。検出経路も、すでに全プロジェクトに届いている user-level config を使っている
3. **逆方向の問題の発見（セルフレビュー）** — 起票時は「最新版を知らせる」方向だけを考えていたが、セルフレビューで、user-level config が即時に届く性質は**新しい規則を旧版の導入先に先に強制する経路**でもあることに気づいた。しかも 009 の配備によって、それが**すでに実際に起きていた**（§2-6）。ユーザー判断で暫定対処を先行させ、版の宣言を「知らせるため」から「どの版で解釈するか」を決めるものに格上げした（GDR-META-034）。009 の 2 回のレビューは 009 の内部整合を検証したが、配備が既存の導入先に与える影響は検証範囲の外にあった — 変更の影響範囲に「すでに導入済みの利用者」を含めることが、フレームワーク自身の変更では必須である
4. **版の定義の修正（書式から移行要否へ）** — 起票時の MINOR の定義（既存レコードが書式として有効）では、009 の「意味の変更」が MINOR に紛れ込むことをレビューで確認し、ユーザー判断で「必須移行があれば MAJOR」に改めた。結果として次版は v1.1 ではなく v2.0 になった

5. **実装からの発見（実装フェーズ 2026-09-28）** — (1) 暫定の「旧版互換」規則（条件: `v2.0` 以上の宣言の有無）は、互換モードの版条件表（`~/.claude/CLAUDE.md` §6）にそのまま吸収できた。暫定対処の時点で「宣言版で切り替える」という恒久対処の形を先取りしていたため、置き換えは表への整理だけで済んだ。(2) 版条件は各コマンドに個別に書かず、`CLAUDE.md` §6 の表を正とし、コマンド側は「§6 の解釈版に従う」と参照するだけにした — 版を上げるたびに書き換える箇所を 1 か所に集約するため。(3) v1.0 の CHANGELOG を書く過程で、kaizen 001〜008 のうち仕様に入ったもの（007 は提案段階で仕様外）を仕分ける必要があり、版の遡及は「どこまでが仕様か」の棚卸しを兼ねた。(4) Getting Started の配置対象リストにも `gdr-upgrade.md` の追加が必要だった — 05 の「配置するファイル」表だけでなく、00 の初回セットアッププロンプトにもコマンド一覧が重複して存在する
