## 1. GDR（General Decision Record）

**GDR-META-031: GDR 仕様に `vMAJOR.MINOR` の版を付け、git タグと CHANGELOG（互換性区分・移行項目つき）で発行する**

- **status:** Proposed
- **scope:** meta, pol
- **決定:** 上流リポジトリの GDR 仕様（01 / 02 / guide / templates / Claude Code セットアップ仕様）に **`vMAJOR.MINOR`** の版を付ける。
  - **MAJOR** — 後方非互換。既存レコード・既存の導入先構成がそのままでは仕様違反になる変更（必須フィールドの追加・改名、status 値の廃止、ディレクトリ構成の必須変更 等）
  - **MINOR** — 後方互換。既存レコードはそのまま有効で、新しい値・任意フィールド・コマンド・ガイドが増える変更（例: 009 の status 5 値化、008 の任意フィールド追加）
  - 文言修正・誤字・例の差し替えなど、導入先に移行作業が生じない変更は版を上げない

  発行は **git タグ `vX.Y`** と **`CHANGELOG.md` のエントリ**で行う。エントリには次の 4 項目を必須とする: (1) 互換性（MAJOR / MINOR）、(2) 変更の要約と根拠 kaizen / GDR、(3) 導入先の移行項目を **必須 / 推奨 / 任意** に区分したもの、(4) user-level config（`~/.claude/`）の更新要否。

  **初版:** 009 着手前の現行仕様（`0eea056` — 008 実装完了時点）を **v1.0** とし、遡及してタグを打つ。009 の実装完了を **v1.1** として最初の通常発行とする
- **理由:** 導入先の `_reference/` は上流の決定のコピーであり、上流が変わった瞬間に陳腐化する。009 が個々の GDR に対して解こうとしている「陳腐化した決定を AI に拾わせない」問題が、フレームワーク自身の配布で未解決のまま残っている — 版がなければ「古い」を判定する基準そのものが存在しない。互換性で上げ分けるのは、導入先が知りたいのは「何が変わったか」より「**自分は何をしなければならないか**」であり、MAJOR / MINOR の区別と移行項目の 3 区分がその問いに直接答えるため。PATCH を持たないのは、移行作業を生まない変更で通知を出すとノイズになり、通知の信頼性が下がるため
  - **代替案 A:** 版を付けず、コミットハッシュで追跡する → 「どれだけ古いか」「移行が必要か」がハッシュからは読めない。却下
  - **代替案 B:** SemVer の 3 桁（PATCH あり）→ PATCH は移行作業ゼロの変更であり、通知・宣言の対象にならない。桁を増やすだけの効果しかない。却下
  - **代替案 C:** 日付版（`2026.09`）→ 互換性が読めない。却下
- **影響:**
  - `CHANGELOG.md`（現状は公開日 1 行のみ）を v1.0 の要約（kaizen 001〜008 の到達点）から書き直す
  - 仕様変更を含む kaizen は、完了処理で「版を上げるか・どちらの桁か」を判定する工程が増える（`/gdr-docs` の整理観点に追加）
  - タグは push しない限りローカルに留まる — 公開はユーザー操作
- **再検討条件:**
  - MINOR の発行頻度が高すぎて導入先が追随を放棄する兆候 → 複数の MINOR を束ねて発行する運用に変更
  - 英語版など多言語化で仕様本文が複数系統になる → 版を言語共通にするか言語別にするかを再検討
- **日時:** 2026-09-28T04:55:34+09:00
- **関連:** derived-from §2-1, derived-from §2-2, relates-to GDR-META-028
- **理由の出所:** ai（要件の起点はユーザー発言「というか、そういう機能性を持つべきではないか？」。合意時に ai-reviewed へ更新）


**GDR-META-032: 導入先は前提定義書に準拠する仕様の版を宣言し、版の採用・更新は GDR-META として記録する**

- **status:** Proposed
- **scope:** meta, spec
- **決定:** T1 前提定義書 §1「プロジェクト情報」に次の 1 行を追加する:

  ```
  GDR 仕様: v1.1（上流 {commit 短縮ハッシュ} / 取得 {YYYY-MM-DD}）
  ```

  この行を**導入先が準拠する版の唯一の宣言**とする。`_reference/` のスナップショットはこの版に対応するものを置く。版の変更は前提定義書を直接編集せず、**GDR-META を発行**して「vX → vY を採用。移行した項目 / 見送った推奨・任意項目とその理由」を記録し、その GDR を根拠に宣言行を更新する（scope / PREFIX 改廃と同じ規律）。宣言のない導入先は**「版不明（v1.0 以前相当）」**として扱う。最初の GDR-META-001（T0 サンプル）の決定に採用版を含める
- **理由:** 陳腐化の判定には「導入先がどの版に従っているか」が必要で、それは導入先の**決定**である — 上流が v1.1 を出しても、導入先が 3 値 status のまま運用し続けることは MINOR の範囲では正当な選択になりうる。決定であれば GDR で記録するのが方法論の一貫性であり、見送った移行項目と理由が残ることで、後から「なぜこのプロジェクトは Accepted を使っていないのか」に答えられる。宣言の置き場所を前提定義書にするのは、AI がセッション開始時に最初に読む文書であり、比較（GDR-META-033）のための追加の読み込みが発生しないため
  - **代替案 A:** `_reference/VERSION` ファイルに記録する → スナップショットの「事実」と導入先の「採用判断」が混同される（スナップショットは更新したが移行は未判断、という状態を表せない）。また前提定義書と別に読む必要がある。却下
  - **代替案 B:** 版の更新を GDR 化せず宣言行の直接編集で済ませる → 見送った移行項目の理由が残らない。scope / PREFIX 改廃を GDR-META 経由とした既存規律とも不整合。却下
- **影響:**
  - T1 テンプレート §1 に宣言行を追加、T0 サンプルの GDR-META-001 に採用版を記載する
  - 03 初回プロンプトガイド・`~/.claude/CLAUDE.md` の初回導入手順に「宣言行の記入」を追加する
  - 既存の導入先は宣言がないため、次の `/gdr-upgrade`（GDR-META-033）実行時に初回宣言を行う
- **再検討条件:**
  - 導入先が複数の上流（フォーク等）を参照する事例が発生 → 宣言行に上流の識別子を加える
- **日時:** 2026-09-28T04:55:34+09:00
- **関連:** depends-on GDR-META-031, derived-from §2-3
- **理由の出所:** ai（合意時に ai-reviewed へ更新）


**GDR-META-033: 最新版の検出は user-level config が持つ「現行版」との比較で行い（ネットワーク不要）、移行は標準コマンド `/gdr-upgrade` で行う。自動移行はしない**

- **status:** Proposed
- **scope:** meta, pol
- **決定:**
  - **検出（受動・ネットワーク不要）:** `~/.claude/CLAUDE.md` の GDR 方法論セクションに**「GDR 仕様の現行版: vX.Y」**の 1 行を置く。AI は GDR 導入済みプロジェクトで GDR 関連の作業（短縮キーワード・`/gdr-*` コマンド・GDR の参照）を最初に行う際、前提定義書の宣言（GDR-META-032）と比較し、導入先が古い・未宣言であれば**セッション内で 1 回だけ**「GDR 仕様 vX.Y が利用可能（現在 vA.B）。`/gdr-upgrade` で差分と移行項目を確認できます」と通知する。作業は中断しない
  - **確認と移行（能動・ネットワークあり）:** 標準コマンド **`/gdr-upgrade`**（短縮キーワードなし — `/gdr-docs` と同じ扱い）を新設する。動作: (1) 上流の最新タグを取得し、user-level config の現行版とも比較（config 自体が古ければその旨を報告）、(2) 導入先の宣言版から最新までの CHANGELOG エントリを提示、(3) 移行項目を必須 / 推奨 / 任意で一覧化し、どれを実施するかをユーザーに確認、(4) `_reference/` を対象版で取り直し、(5) GDR-META を起票（GDR-META-032）して宣言行を更新、(6) 1 コミット。実施を選んだ移行項目の作業そのもの（既存 GDR の status 棚卸し等）は、通常のビルドアップサイクル（改善提案 or `/gdr-flow`）で別途行う
  - **自動移行はしない。** MAJOR の必須項目を実施しない場合は、版を上げずに留まる選択（旧版のまま運用）を GDR-META として記録できる
- **理由:** 「最新はこれ」を導入先に伝える最も確実な経路は、全プロジェクトの起動時に読み込まれる user-level config である — コマンド定義・CLAUDE.md を更新した時点で、導入済みの全プロジェクトが次のセッションから新しい版を知る。比較対象（前提定義書）は AI が元々読む文書なので、検出の追加コストはほぼゼロで、ネットワークにも依存しない。一方、user-level config 自体が古い場合はこの経路では検出できないため、ネットワーク確認は明示的に呼ぶ `/gdr-upgrade` 側に置き、常時のコスト（毎セッションの API 呼び出し）を避ける。自動移行をしないのは、移行の採否が導入先の判断（GDR-META-032）であり、既存 GDR の書き換えを伴う作業を AI が無断で行うと「文書と実装を混ぜない」「判断は合意を経る」の両原則に反するため
  - **代替案 A:** SessionStart hook で毎回上流の最新タグを取得する → user-level config が古い場合も検出できるが、全セッションでネットワーク呼び出しが発生し、hook の配置という追加のセットアップが要る。再検討条件行き
  - **代替案 B:** 通知を出さず、ユーザーが気づいたときに `/gdr-upgrade` を呼ぶ → 現状と同じく「知る術がない」問題が残る。却下
  - **代替案 C:** 古い版を検出したら自動で移行する → 採否の判断を奪い、既存レコードの無断書き換えを招く。却下
  - **代替案 D:** 短縮キーワード（`更新：` 等）を既定 7 種目として追加する → 版の更新は数か月に一度の保守操作で、ビルドアップサイクルの節目ではない。既定キーワードはサイクル必須操作に限る現行方針（GDR-META-026）を維持。却下
- **影響:**
  - `~/.claude/CLAUDE.md` に現行版の行と検出・通知の規則を追加、`~/.claude/commands/gdr-upgrade.md` を新設する（リポジトリ外配備）
  - 05 セットアップガイドの「配置するファイル」を 8 → 9 ファイルに更新し、`/gdr-upgrade` の仕様と「上流の版が上がったら user-level config の現行版も更新する」手順を追記する
  - 上流で版を発行する手順（タグ → CHANGELOG → user-level config の現行版更新）が 1 セットになる。現行版の更新を忘れると通知が出ないため、発行手順のチェックリストに含める
- **再検討条件:**
  - user-level config の更新漏れ（現行版が古いまま）で通知が出ない事例が実際に発生 → SessionStart hook による上流確認（代替案 A）を再検討
  - 通知が「毎セッション出てうるさい」と感じられる → 見送りを GDR-META で記録した導入先では、その版については通知しない規則を追加
- **日時:** 2026-09-28T04:55:34+09:00
- **関連:** depends-on GDR-META-031, depends-on GDR-META-032, derived-from §2-4
- **理由の出所:** ai（要件の起点はユーザー発言「すでに適応されたプロジェクトにこれが最新だと伝える術はないか？」。合意時に ai-reviewed へ更新）

## 2. 現状

009 のレビュー中に、ユーザーから「すでに適応されたプロジェクトにこれが最新だと伝える術はないか？」「そういう機能性を持つべきではないか？」という問いがあった。点検した結果:

1. **上流の仕様に版がない** — git タグはなく、`CHANGELOG.md` は公開日（2026-04-16）の 1 行のみ。001〜008 で仕様は何度も変わったが、どの時点の仕様かを名指す手段がない
2. **変更が導入先に何を要求するかが書かれていない** — 例えば 009 は既存レコードを壊さない（3 値のままでも仕様違反にならない）が、それを判断できる情報が上流のどこにもない
3. **導入先がどの版に従っているか分からない** — `_reference/` は Method C で取得した編集禁止スナップショットだが、取得時点の上流コミットを記録しておらず、前提定義書（T1）にも版の項目がない
4. **最新版を知る経路と取り込む手順がない** — 00 / 03 / 05 のいずれのガイドにも、導入後に上流の変更を取り込む手順がない。ただし、user-level config（`~/.claude/CLAUDE.md` / `commands/`）は全プロジェクトの起動時に読み込まれるため、**AI の振る舞いに関する変更はすでに全導入先へ即時に届いている** — 届かないのはプロジェクトごとの成果物（`_reference/`・プロジェクト直下 `CLAUDE.md`・前提定義書・既存レコード）だけである
5. **自己矛盾** — 009 は「陳腐化した決定を AI に根拠として使わせない」を主題にしているが、導入先の `_reference/` はまさに陳腐化しうる上流の決定のコピーであり、フレームワーク自身がこの原則を満たしていない

## 3. 改善案

「版は宣言する / 差は検出する / 移行は決定として残す」の 3 点を、3 つの GDR で本体仕様に組み込む。

1. **上流: 版の発行**（GDR-META-031）— `vMAJOR.MINOR`、タグ + CHANGELOG（互換性・移行項目の 3 区分）
2. **導入先: 版の宣言**（GDR-META-032）— 前提定義書に 1 行、変更は GDR-META
3. **両者をつなぐ: 検出と移行**（GDR-META-033）— user-level config の現行版と比較して 1 回通知、`/gdr-upgrade` で差分確認・移行判断・記録

新しい概念は増やさない。版の採用を GDR として記録するのは、既存の「scope / PREFIX の改廃は GDR-META で」と同じ型である。

## 4. 詳細セクション

### 4.1. 全体像

```
[上流リポジトリ]
  仕様変更の kaizen 完了 → 版の判定（MAJOR / MINOR / 上げない）
        │
        ├─ git tag v1.1
        ├─ CHANGELOG.md: 互換性 / 要約 / 移行項目（必須・推奨・任意）/ user-level config 更新要否
        └─ user-level config の「GDR 仕様の現行版: v1.1」を更新
                │
                │ （全プロジェクトの起動時に読み込まれる）
                ▼
[導入先プロジェクト]
  前提定義書: 「GDR 仕様: v1.0（…）」
        │
        │ GDR 関連作業の最初に比較 → 差あり
        ▼
  通知（セッション内 1 回）:「GDR 仕様 v1.1 が利用可能（現在 v1.0）」
        │
        │ ユーザーが /gdr-upgrade
        ▼
  上流確認 → CHANGELOG 差分提示 → 移行項目の採否確認 → _reference/ 取り直し
        → GDR-META 起票（採用版・移行 / 見送り）→ 宣言行更新 → 1 コミット
        │
        └→ 実施を選んだ移行作業は通常サイクル（改善提案 / /gdr-flow）で
```

### 4.2. CHANGELOG エントリ例

```markdown
## v1.1 — 2026-10-XX

- **互換性:** MINOR（既存レコードはそのまま有効）
- **要約:** status を 5 値化（Accepted / Rejected を追加）、失効レコードの参照規律、任意フィールド「理由の出所」
  - 根拠: kaizen 009（GDR-META-028〜030）
- **導入先の移行項目:**
  - 必須: なし
  - 推奨: 前提定義書に版を宣言（v1.1 から）/ `Proposed` のまま放置された GDR の棚卸し（合意済み → `Accepted`、不採用 → `Rejected`）/ プロジェクト直下 `CLAUDE.md` の GDR 書式の status 行を 5 値に更新
  - 任意: 既存 GDR への「理由の出所」の記入
- **user-level config:** 更新必要（`gdr-flow` / `gdr-kaizen` / `gdr-docs` / `gdr-map`、`CLAUDE.md` の現行版を v1.1 に）
```

### 4.3. 版の採用を記録する GDR-META の例（導入先）

```markdown
**GDR-META-007: GDR 仕様 v1.1 を採用する**

- **status:** Implemented
- **scope:** meta
- **決定:** 準拠する GDR 仕様を v1.0 → v1.1 に更新する。推奨項目のうち「Proposed 放置の棚卸し」「CLAUDE.md の status 行更新」を実施し、任意項目「理由の出所の遡及記入」は見送る
- **理由:** 失効判断の誤参照防止（v1.1 の主眼）は本プロジェクトの GDR 件数（40 件超）で効果が大きい。理由の出所の遡及は、当時の発言記録が残っておらず正確に書けないため見送る
- **影響:** 前提定義書の宣言行を v1.1 に更新。棚卸しは改善提案として別途起票
- **再検討条件:** v2.0（MAJOR）が発行された場合
- **理由の出所:** human（ユーザー発言「遡及は無理なので新規分からでいい」）
```

### 4.4. 通知の規則（`~/.claude/CLAUDE.md` に置く文言の骨子）

```markdown
- **GDR 仕様の現行版:** v1.1（CHANGELOG: https://github.com/yoshinag/general-decision-record/blob/main/CHANGELOG.md）
- GDR 導入済みプロジェクトで GDR 関連の作業を最初に行う際、前提定義書の「GDR 仕様」行と現行版を比較する。
  古い / 未宣言の場合は、セッション内で 1 回だけ次を通知し、作業は続行する:
  「GDR 仕様 v{現行} が利用可能です（このプロジェクト: v{宣言 or 不明}）。`/gdr-upgrade` で差分と移行項目を確認できます」
- 自動で移行しない。
```

### 4.5. 上流で版を発行する手順（チェックリスト）

1. 仕様変更を含む kaizen の完了処理で、版を上げるか・どちらの桁かを判定する（移行作業が生じないなら上げない）
2. `CHANGELOG.md` にエントリを追加する（4 項目必須）
3. `git tag vX.Y`（公開は push — ユーザー操作）
4. user-level config の現行版の行を更新する（**忘れると通知が出ない**）
5. 05 セットアップガイドに記載のコマンド仕様を同期する

## 5. 検討課題

1. **コマンド定義ファイル自体の配布**
   - 現状、`~/.claude/commands/gdr-*.md` はリポジトリに含まれず、05 の仕様から各自が作成する。このため他の利用者は「user-level config を最新版に更新する」作業も手作業になる
   - 解決策: 本提案の範囲外とする。検出（GDR-META-033）は config が各自作成でも機能し、`/gdr-upgrade` の上流確認で config 自体の古さも報告できる。配布物（例: `dist/claude/`）のファイル化は、他の利用者からの要望が出た時点で別提案とする
   - → 申し送り（§7.2）
2. **複数の導入先を一覧で確認したい（メンテナ用途）**
   - 解決策: 初期実装には含めない。`notes/91_gdr/00_CONTEXT_DEFINITIONS.md` を検索すれば宣言行を一覧できるため、需要が出たら `/gdr-upgrade` の一覧モードとして追加する。007 gdr-index が実装されれば、その `projects` 設定で代替できる
   - → GDR-META-033 の拡張候補
3. **遡及タグ v1.0 の位置**
   - 解決策: 仕様本文（`docs/ja/01_GDR/` 配下）の最終変更である `0eea056` に打つ。009 / 010 の kaizen 文書は仕様本文を変えていないため v1.0 に含めてよい
   - → フェーズ 1 のタスクとして追加済み
4. **009 との順序**
   - 解決策: 009（2 回目のレビュー反映 → 合意 → 実装）を先に完了し、その完了を v1.1 として発行する。009 には「導入先への配布は 010 で扱う」を申し送りとして追記する（009 のレビュー反映時に実施）。010 の実装（宣言行・通知規則・`/gdr-upgrade`）も v1.1 に含める
   - → 実行計画の依存として反映済み

## 7. ふりかえり

> 起票時点（2026-09-28）の記録。実装フェーズの完了ごとに追記する。

### 7.1. 観察された傾向

1. **ユーザーの問いによる位置づけの修正** — AI は当初、版管理と通知を「任意のツール（`/gdr-upgrade` + 任意の hook）」として提示した。ユーザーの「そういう機能性を持つべきではないか？」を受けて、009 の原則（陳腐化した決定を拾わせない）がフレームワーク自身の配布に適用されていないという自己矛盾（§2-5）として捉え直し、本体仕様（T1 の宣言・GDR-META による採用記録）に組み込む形に改めた
2. **既存の型の再利用** — 版の採用を GDR-META で記録する設計は、「scope / PREFIX の改廃は GDR-META で」という既存規律の転用であり、新しい概念を増やしていない。検出経路も、すでに全プロジェクトに届いている user-level config を使っている

### 7.2. 次回への申し送り

- コマンド定義ファイルの配布物化（§5-1）は、他の利用者からの要望が出た時点で別提案とする
- v1.1 発行後、通知の頻度・うるささを観察する（GDR-META-033 の再検討条件）
