## 1. GDR（General Decision Record）

**GDR-META-035: 共有される文書に環境依存の絶対パスを書かない。手元で読むリポジトリ外の資料は「論理名（リポジトリ名 + リポジトリ相対パス）」で参照し、各環境での場所は共有しないローカル対応表で解決する。混入は追跡対象ファイルの検索で確かめる**

- **status:** Accepted
- **scope:** meta, pol
- **決定:**
  - **禁止するもの:** バージョン管理で共有される文書（GDR・前提定義書・INDEX・仕様書・プロジェクト直下の AI 向け指示書など）に、**特定の利用者・端末でしか成り立たないパス**（利用者名を含むホームディレクトリの絶対パス、ドライブ文字、マウントポイント）を書かない。`~/` 始まりのパスと、ツールが定める既定の場所（例: `~/.claude/`）は、どの環境でも同じ意味になるので対象外とする
  - **参照の書き方:** AI・人が**手元で読む**リポジトリ外の資料は、**論理名**で参照する。論理名は `{リポジトリ名} リポジトリの {リポジトリ相対パス}` の形（例: 「`handbook` リポジトリの `notes/01_spec/style_guide.md`」）。公開 URL があれば併記してよい。手元に置かず参照するだけの資料は URL のみでよい。GDR の任意フィールド「関連」には外部資料を書かない（対象は 01 §3.1 のとおり GDR ID と文書内の `§` 参照のみ）— 外部資料は理由・影響などの本文で指す
  - **場所の置き場:** 論理名を各環境の実際の場所に結びつける情報は、**ローカル対応表**（バージョン管理の除外対象にしたファイル。「論理名 → この環境での場所」の表 1 つ）に置く。対応表のファイル名は、前提定義書またはプロジェクト直下の AI 向け指示書の 1 か所で定める
  - **AI の振る舞い:** 論理名の場所が分からないとき（対応表がない・載っていない）、AI は**場所を推測しない**。ユーザーに尋ね、答えをローカル対応表に追記する。探索で見つけたパスを共有される文書に書かない
  - **確認:** 混入していないことは、追跡対象ファイルの検索（`git grep`。§4.3）で確かめる。タイミングは、外部資料への参照を追加・変更したコミットの前と、実装後の文書整理（`/gdr-docs` 相当）のとき。説明用の例に書くパスは、例示用の名前 `alice`（§4.3）を使い、検索の対象から外す
  - **既存文書の扱い:** この規則は以後に書く・更新する文書に適用する。既存文書に残る絶対パスの置き換えは**推奨**の移行項目とし、必須にしない
- **理由:** 絶対パスは書いた環境でしか解決できず、別の端末・共同作業者・CI では辿れない。公開リポジトリでは利用者名やディレクトリ構成も外に出る。一方、リポジトリ外の資料を参照する必要は消えない — AI は次のセッションでもその資料を手元で読める必要がある。「何を参照しているか（論理名）」と「この環境のどこにあるか（場所）」を分ければ、前者は共有して判断の根拠として残し、後者は環境ごとに持てる。論理名をリポジトリ名 + リポジトリ相対パスにするのは、リポジトリ内の位置はどの環境でも同じで、変わるのはクローン先だけだからである。公開 URL を論理名の代わりにしないのは、URL は人には辿れても AI が手元のクローンを読む手がかりにならず、非公開リポジトリでは使えないため。「関連」に外部資料を入れないのは、可視化と横断検索が「関連」を機械的に読む前提（008）であり、自由文の名前が混ざるとノードとして解決できないため。確認を検索で行うのは、絶対パスは AI がファイルを開いた直後に書き写しやすく、書いた環境では正しく動くので目視のレビューでは見落としやすいため — 起点の事例でも、最後に追跡対象ファイル全体を検索して初めて完了とした。既存文書の置き換えを必須にしないのは、絶対パスが残っていても GDR の解釈は変わらないため（GDR-META-031 の「必須の移行」に当たらない）
  - **代替案 A:** 相対パス（`../other-repo/...`）で書く → クローン先の並びが環境ごとに同じという前提が要り、その前提自体が環境依存。却下
  - **代替案 B:** 環境変数（`$HANDBOOK_ROOT/...`）で書く → 読み手（人・AI）が変数を展開できる保証がなく、設定の場所が新たに要る。対応表の方が読むだけで分かる。却下
  - **代替案 C:** 外部資料をリポジトリ内にコピーする → 正本が二重になり、更新が追随しない。編集禁止スナップショットとして取り込む既存の型（`_reference/`）が合う場合はそちらを使う。一般解としては却下
  - **代替案 D:** 特定の AI ツールが自動で読む個人用ファイル（Claude Code の `CLAUDE.local.md`）を対応表として規定する → 起点の事例はこれで解決したが、規則が特定ツールに依存する。規則は「ローカル対応表」とし、ツール固有のファイルは実装例としてセットアップガイドに示す。部分採用
  - **代替案 E:** 公開 URL を優先し、ない場合だけ論理名を使う（起票時の案）→ 手元で読む必要を満たさない。レビューで却下
  - **代替案 F:** pre-commit hook や専用スクリプトで検出を強制する → `git grep` の 1 行で足り、hook の配置やスクリプトの保守に見合わない。導入先が任意で追加するのは妨げない。却下
- **影響:**
  - 03 初回プロンプトガイドに、外部資料の参照規則と「外部資料を参照する場合に前提定義書へ追加する表」（§4.2）を追記する。01 GDR 仕様と T1 テンプレートは変更しない
  - 05 セットアップガイドに、ツール別の実装例（Claude Code では `CLAUDE.local.md` を対応表にできる）、確認用のコマンド例、`/gdr-docs` の整理観点「環境依存パスの確認」を追記する
  - user-level config（`~/.claude/CLAUDE.md` / `commands/gdr-docs.md`）に、参照の書き方・「推測しない」・整理観点を追加する（リポジトリ外配備）
  - 新しい環境で作業を始めるとき、ローカル対応表を作る手順が 1 つ増える
- **再検討条件:**
  - 参照する外部資料が増え、対応表を手で維持するのが負担になる → 対応表の自動生成、または `_reference/` へ取り込む運用への切り替えを検討
  - リポジトリ名だけの論理名が衝突する → 論理名にホスト / 所有者を加える
  - 検索が数か月にわたり混入を 1 件も拾わない、または誤検出の除外の手間が上回る → 確認のタイミングを参照変更時だけに絞る
  - 検索パターンで拾えない書き方（ネットワークドライブ等）が実際に混入する → パターンを導入先が拡張できる形にする

## 2. 現状

ある導入先で、仕様書・INDEX・プロジェクト直下の AI 向け指示書が、**別リポジトリにあるガイド文書を作業端末の絶対パスで参照していた**。これを次のように直した:

- 「この端末での場所」を、バージョン管理の除外対象にした個人用ファイル（Claude Code が自動で読む `CLAUDE.local.md`）へ移し、「文書での呼び方 → この端末での場所」の対応表にした
- 共有される文書は「`○○` リポジトリの `notes/01_spec/…_guide.md`（この端末での場所は対応表を参照）」という書き方に変え、仕様書の冒頭で「以下『ガイド』」と略称を決めて本文は「ガイド §2.4」のように指した
- 除外設定（`.gitignore`）に個人用ファイルを追加し、追跡対象のファイル全体を検索して絶対パスが残っていないことを確かめた
- 別の端末で作業するときは、その端末で対応表を作り直す

この対処は有効だったが、フレームワークには次の欠けがある:

1. **外部資料の参照方法が規定されていない** — GDR 仕様・テンプレート・ガイドのいずれにも、リポジトリ外の資料をどう参照するかの規則がない。AI はファイルを開いた絶対パスをそのまま書きやすい
2. **環境依存の情報を置く場所がない** — 前提定義書・INDEX・指示書はすべて共有される前提で、「この環境だけの情報」を置く場所が定められていない。そのため共有される文書に混入する
3. **対処がツール固有の仕組みに依存している** — 事例では Claude Code の `CLAUDE.local.md`（自動読み込み）を使ったが、GDR は特定の AI ツールに依存しない方法論であり、規則として採るには一般化が要る
4. **混入を確かめる工程がない** — 書いた本人の環境では正しく動くため、レビューでは見落としやすい。事例では最後の検索で初めて「残っていない」ことが確定した

---

## 3. 改善案

「何を参照しているか（論理名）」と「この環境のどこにあるか（場所）」を分ける。1 つの GDR（GDR-META-035）で次を定める:

1. **書かないもの** — 特定の利用者・端末でしか成り立たないパス
2. **参照の書き方** — 手元で読む外部資料は論理名で。公開 URL は併記してよい
3. **場所の置き場** — 共有しないローカル対応表
4. **AI の振る舞い** — 場所を推測せず、尋ねて対応表に追記する
5. **確認** — 追跡対象ファイルの検索を、参照変更時と文書整理時に行う

01 GDR 仕様と T1 テンプレートは変えない。外部資料を「取り込む」なら既存の `_reference/`（編集禁止スナップショット）、取り込まずに「参照する」なら論理名 + ローカル対応表、という使い分けになる。

## 4. 詳細セクション

### 4.1. 全体像

```
[共有される文書]（バージョン管理で追跡）
  前提定義書:  ローカル対応表 = PATHS.local.md
               外部資料 = 「handbook リポジトリの notes/01_spec/style_guide.md」
  仕様書:      「…style_guide.md（以下『ガイド』）」→ 本文は「ガイド §2.4」
  GDR:         理由・影響の本文で論理名（または文書内で決めた略称）を使う
        │
        │ 論理名で引く
        ▼
[ローカル対応表]（バージョン管理の除外対象・環境ごとに作る）
  | 論理名 | この環境での場所 |
  | handbook リポジトリ | /Users/alice/src/handbook |
```

同じ資料を文書内で繰り返し指すときは、初出で略称を決める（「以下『ガイド』」）。略称は書き方の工夫であり、規則の用語は「論理名」と「ローカル対応表」の 2 つである。

### 4.2. ローカル対応表と前提定義書への追記の例

ローカル対応表（共有しない）:

```markdown
# ローカル対応表（この環境専用・共有しない）

| 論理名 | この環境での場所 |
|---|---|
| `handbook` リポジトリ | `/Users/alice/src/handbook` |
```

- リポジトリ単位で書けば、そのリポジトリ内のファイルはすべて「場所 + リポジトリ相対パス」で解決できる。ファイル単位で書くのは、リポジトリでない資料（共有ドライブ上の文書等）に限る
- 除外設定の例: `.gitignore` に `*.local.md`

前提定義書への追記（**外部資料を参照するプロジェクトだけ**。T1 には常設しない）:

```markdown
## 外部資料

ローカル対応表: `PATHS.local.md`（共有しない。環境ごとに作成）

| 論理名 | 用途 |
|---|---|
| `handbook` リポジトリの `notes/01_spec/style_guide.md` | 文体の基準 |
```

**ツール別の実装例**（05 セットアップガイドに置く）:

- Claude Code — `CLAUDE.local.md` が自動で読み込まれるので、これを対応表にすると毎セッション明示的に読ませる必要がない
- 自動読み込みの仕組みがないツール — 共有される指示書に「外部資料の場所は `PATHS.local.md` を読む」と書く。検索やファイル一覧で除外対象のファイルを飛ばすツールでは、パスを明示して読ませる

### 4.3. 確認用のコマンド

```bash
git grep -nP '/(Users|home)/(?!alice\b)|[A-Za-z]:\\Users\\(?!alice\b)'
```

- `git grep` は追跡対象のファイルだけを検索する。ローカル対応表のような除外対象のファイルは、環境依存パスがあって正しいので検索しない
- `git ls-files | xargs grep` の形は使わない。日本語や空白を含むファイル名で壊れる（`git ls-files` が非 ASCII のファイル名をエスケープして出力するため。このリポジトリで確認）
- **例示用の名前は `alice`** とする。規則を説明する文書（本提案、ガイド、導入先の `_reference/`）は例としてパスを書く必要があるので、例は `alice` のホームディレクトリで書き、検索パターンからその名前を除く
- 何も出力されなければ混入なし。出力があれば、論理名への置き換えとローカル対応表への移動で直す

### 4.4. 対応表がない環境での流れ

1. AI が論理名の場所を引こうとして、対応表がない（または載っていない）ことに気づく
2. AI は場所を探索で決めず、ユーザーに尋ねる
3. 答えをローカル対応表に追記する（除外設定がなければ、それも追加する）

## 5. 検討課題

1. **対応表の既定ファイル名**
   - 解決策: 既定を `PATHS.local.md`（除外パターン `*.local.md`）とし、導入先は前提定義書で別名に変えてよい。Claude Code では `CLAUDE.local.md` で代替してよい
   - → タスク 1.1 / 1.2 で確定
2. **外部資料の版**
   - 「ガイド §2.4」のような節番号の参照は、外部資料が改訂されるとずれる
   - 解決策: 節番号まで指す場合に限り、前提定義書の表に参照時点（コミットか日付）を任意で書けるようにするかを、ガイド追記時に決める。必須にはしない
   - → タスク 1.1 で確定
3. **検索パターンの誤検出**
   - パターンの `home` の側は、URL のパス部分にも一致しうる
   - 解決策: 実装時に上流リポジトリと導入先 1 件で試し、必要なら行頭・空白・引用符の直後に限る
   - → タスク 1.2 で確定
4. **上流リポジトリ自身への適用**
   - 2026-10-06 時点で、§4.3 のコマンドは上流リポジトリで何も出力しない（本提案の例は `alice` で書いている）
   - → 対応不要
