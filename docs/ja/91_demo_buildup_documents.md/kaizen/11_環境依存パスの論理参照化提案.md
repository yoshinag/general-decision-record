## 1. GDR（General Decision Record）

**GDR-META-035: 共有される文書に環境依存の絶対パスを書かない。リポジトリ外の資料は「論理名（リポジトリ名 + リポジトリ相対パス）」で参照し、各環境での実際の場所は共有しないローカル対応表で解決する**

- **status:** Proposed
- **scope:** meta, pol
- **決定:** バージョン管理で共有される文書（GDR・前提定義書・INDEX・仕様書・プロジェクト直下の AI 向け指示書など）に、**特定の環境でしか成り立たない絶対パス**（ホームディレクトリ・ユーザー名・ドライブ文字・マウントポイントを含むもの）を書かない。リポジトリ外の資料は次の順で参照する:
  1. **公開 URL** — 誰でも辿れる場所（ホスティング上のファイル・パーマリンク等）がある場合
  2. **論理名** — 公開 URL がない場合。`{リポジトリ名} リポジトリの {リポジトリ相対パス}` の形で書く（例: 「`handbook` リポジトリの `notes/01_spec/style_guide.md`」）

  論理名を各環境の実際の場所に結びつける情報は、**共有しないローカル対応表**（バージョン管理の除外対象にしたファイル）に置く。対応表は「論理名 → この環境での場所」の表 1 つとする。共有される側には「この環境での場所はローカル対応表を参照」とだけ書き、対応表のファイル名は前提定義書（または AI 向け指示書）で 1 か所に定める。

  文書内で同じ外部資料を繰り返し参照する場合は、初出で**呼び名**を宣言し（例: 「…`style_guide.md`（以下『ガイド』）」）、以降は「ガイド §2.4」のように呼び名で指す
- **理由:** 絶対パスは書いた環境でしか解決できず、別の端末・共同作業者・CI では壊れたリンクになる。さらに公開リポジトリではユーザー名やディレクトリ構成が外部に漏れる。一方で、リポジトリ外の資料を参照する必要自体は消えない — AI は次のセッションでもその場所を知っている必要がある。「何を参照しているか（論理名）」と「この環境のどこにあるか（場所）」を分ければ、前者は共有して判断の根拠として残し、後者は環境ごとに持てる。論理名をリポジトリ名 + リポジトリ相対パスにするのは、リポジトリ内の位置はどの環境でも同じで、変わるのはクローン先だけだからである。呼び名の宣言は、長い論理名の繰り返しで本文が読みにくくなるのを防ぐため
  - **代替案 A:** 相対パス（`../other-repo/...`）で書く → クローン先の並びが環境ごとに同じという前提が要り、その前提自体が環境依存。却下
  - **代替案 B:** 環境変数（`$HANDBOOK_ROOT/...`）で書く → 文書の読み手（人・AI）が変数を展開できる保証がなく、設定の場所が新たに必要になる。対応表の方が読むだけで分かる。却下
  - **代替案 C:** 外部資料をリポジトリ内にコピーする → 正本が二重化し、更新が追随しない。編集禁止スナップショットとして取り込む既存の型（`_reference/`）が合う場合はそちらを使う。一般解としては却下
  - **代替案 D:** 特定の AI ツールが自動で読む個人用ファイル（例: Claude Code の `CLAUDE.local.md`）を対応表として規定する → 起点となった事例ではこれで解決したが、フレームワークの規則が特定ツールに依存する。規則は「共有しないローカル対応表」とし、ツール固有のファイルは実装の選択肢としてセットアップガイドに示す。部分採用
- **影響:**
  - 01 GDR 仕様（または 03 初回プロンプトガイド）に「外部資料の参照」の規則を追加する
  - T1 前提定義書に「ローカル対応表のファイル名」と、共有してよい「外部資料の論理名一覧」を置く欄を追加する（場所は書かない）
  - 新しい環境で作業を始めるときに、ローカル対応表を作る手順が 1 つ増える（対応表がない場合、AI は場所を推測せずユーザーに尋ねる）
  - 05 セットアップガイドに、Claude Code では `CLAUDE.local.md` を対応表として使える（自動で読み込まれる）ことを実装例として示す
- **再検討条件:**
  - 参照する外部資料が増え、対応表の手作業での維持が負担になる → 対応表の自動生成（クローン先の走査等）や、資料を `_reference/` へ取り込む運用への切り替えを検討
  - 複数のリポジトリで同名のリポジトリ名が衝突する → 論理名にホスト / 所有者を加える

- **理由の出所:** ai（起点は導入先での対処事例。規則化・一般化は AI の起案で、人間未確認）


**GDR-META-036: 環境依存パスの混入は、共有対象のファイル全体に対する機械的な検索で検出し、文書整理の工程に組み込む**

- **status:** Proposed
- **scope:** meta, pol
- **決定:** 環境依存パスが共有される文書に入っていないことを、**バージョン管理の追跡対象ファイル全体**に対する検索で確かめる（例: `git ls-files | xargs grep -nE '/Users/|/home/[^/]+/|[A-Za-z]:\\\\'`）。確認のタイミングは次の 2 つ:
  1. 外部資料への参照を追加・変更したコミットの前
  2. 実装後の文書整理（`/gdr-docs` 相当の工程）の整理観点の 1 つとして

  検出した場合は GDR-META-035 の手順（論理名への置き換え + ローカル対応表への移動）で直す。コードブロック内の説明用の例は、実在しない名前（`/Users/alice/...` 等）を使い、検出対象から除外できるようにする
- **理由:** 絶対パスは AI がファイルを開いた直後にそのまま書き写しやすく、レビューでも見落としやすい — 書いた本人の環境では正しく動くので不具合として表に出ない。起点の事例でも、修正の最後に「追跡対象のファイル全体を検索して残っていないこと」を確かめて初めて完了とした。検索は数秒で終わり誤検出も少ないため、目視レビューに頼るより確実で安い。範囲を「追跡対象のファイル」に限るのは、ローカル対応表など除外対象のファイルには環境依存パスがあって正しいため
  - **代替案 A:** pre-commit hook で強制する → 導入先ごとに hook の配置が要り、フレームワークの規則としては重い。導入先の判断で追加してよい（任意）。部分採用
  - **代替案 B:** 目視レビューのみ → 上記のとおり見落としやすい。却下
- **影響:**
  - 05 セットアップガイドの `/gdr-docs` の整理観点に「環境依存パスの検出」を追加する
  - 上流リポジトリの `scripts/` に検出用スクリプトを置くか、既存の `check-links.sh` に統合するかを実装時に決める
- **再検討条件:**
  - 検索パターンで拾えない環境依存の書き方（ネットワークドライブ・独自のマウント名等）が実際に混入する → パターンを導入先が拡張できる形にする
  - 誤検出が頻発し、除外の手間が検出の利益を上回る → 確認のタイミングを文書整理時のみに絞る
- **日時:** 2026-10-06T00:00:00+09:00
- **関連:** depends-on GDR-META-035, derived-from §2-4
- **理由の出所:** ai（起点は導入先での確認手順。工程への組み込みは AI の起案で、人間未確認）

## 2. 現状

ある導入先で、仕様書・INDEX・プロジェクト直下の AI 向け指示書が、**別リポジトリにあるガイド文書を作業端末の絶対パスで参照していた**。これを次のように直した:

- 「この端末での場所」を、バージョン管理の除外対象にした個人用ファイル（Claude Code が自動で読む `CLAUDE.local.md`）へ移し、「文書での呼び方 → この端末での場所」の対応表にした
- 共有される文書は「`○○` リポジトリの `notes/01_spec/…_guide.md`（この端末での場所は対応表を参照）」という書き方に変え、仕様書の冒頭で「以下『ガイド』」と呼び名を決めて本文は「ガイド §2.4」のように指した
- 除外設定（`.gitignore`）に個人用ファイルを追加し、追跡対象のファイル全体を検索して絶対パスが残っていないことを確かめた
- 別の端末で作業するときは、その端末で対応表を作り直す

この対処は有効だったが、フレームワークには次の欠けがある:

1. **外部資料の参照方法が規定されていない** — GDR 仕様・テンプレート・ガイドのいずれにも、リポジトリ外の資料をどう参照するかの規則がない。AI はファイルを開いた絶対パスをそのまま書きやすい
2. **環境依存の情報を置く場所がない** — 前提定義書・INDEX・指示書はすべて共有される前提で、「この環境だけの情報」を置く場所が定められていない。そのため共有される文書に混入する
3. **対処がツール固有の仕組みに依存している** — 事例では Claude Code の `CLAUDE.local.md`（自動読み込み）を使ったが、GDR は特定の AI ツールに依存しない方法論であり、規則として採るには一般化が要る
4. **混入を確かめる工程がない** — 書いた本人の環境では正しく動くため、レビューでは見落としやすい。事例では最後の検索で初めて「残っていない」ことが確定した

---

## 3. 改善案

「何を参照しているか（論理名）」と「この環境のどこにあるか（場所）」を分ける。

1. **参照の規則**（GDR-META-035）— 共有される文書は公開 URL か論理名で参照し、場所は共有しないローカル対応表に置く。繰り返し参照は呼び名を宣言する
2. **混入の検出**（GDR-META-036）— 追跡対象ファイル全体の検索を、参照変更時と文書整理時に行う

新しい概念は最小限にとどめる。外部資料を取り込むなら既存の `_reference/`（編集禁止スナップショット）、取り込まずに参照するなら論理名 + ローカル対応表、という使い分けになる。

## 4. 詳細セクション

### 4.1. 全体像

```
[共有される文書]（バージョン管理で追跡）
  前提定義書:  ローカル対応表 = LOCAL_PATHS.local.md
               外部資料の論理名一覧 = 「ガイド: handbook リポジトリの notes/01_spec/style_guide.md」
  仕様書:      「…style_guide.md（以下『ガイド』）」→ 本文は「ガイド §2.4」
  GDR:         「関連: relates-to ガイド §2.4」等、論理名・呼び名で参照
        │
        │ 論理名で引く
        ▼
[ローカル対応表]（バージョン管理の除外対象・環境ごとに作る）
  | 論理名 | この環境での場所 |
  | handbook リポジトリ | /Users/alice/src/handbook |
```

### 4.2. ローカル対応表の例

```markdown
# ローカル対応表（この環境専用・共有しない）

| 論理名 | この環境での場所 |
|---|---|
| `handbook` リポジトリ | `/Users/alice/src/handbook` |
```

- リポジトリ単位で書けば、そのリポジトリ内のファイルはすべて「場所 + リポジトリ相対パス」で解決できる。ファイル単位で書くのは、リポジトリでない資料（共有ドライブ上の文書等）に限る
- 除外設定の例: `.gitignore` に `*.local.md`
- **ツール別の実装例**（05 セットアップガイドに置く）: Claude Code では `CLAUDE.local.md` が自動で読み込まれるため、これを対応表として使うと毎セッション明示的に読む必要がない。自動読み込みの仕組みがないツールでは、共有される指示書に「外部資料の場所は `LOCAL_PATHS.local.md` を読む」と書く

### 4.3. 前提定義書（T1）への追加案

```markdown
## 4. 外部資料

ローカル対応表: `LOCAL_PATHS.local.md`（共有しない。環境ごとに作成）

| 呼び名 | 論理名 / 公開 URL |
|---|---|
| ガイド | `handbook` リポジトリの `notes/01_spec/style_guide.md` |
```

### 4.4. 対応表がない環境での AI の振る舞い

- 論理名の場所が分からない場合、AI は**場所を推測しない**（ホームディレクトリの走査等で見つけたパスを共有される文書に書かない）
- ユーザーに場所を尋ね、ローカル対応表に追記する

## 5. 検討課題

1. **規則の置き場所（01 仕様か、ガイドか）**
   - 01 GDR 仕様は GDR レコードの書式を定める文書で、文書全般の書き方は範囲外とも言える。一方、GDR の理由・関連が外部資料を指すことは多い
   - 解決策（案）: 01 §3.1 の「関連」の対象に「外部資料は論理名・呼び名で」と 1 行加え、手順の詳細は 03 初回プロンプトガイド（導入時に対応表を作る）と T1 に置く
   - → 合意時に確定
2. **対応表の既定ファイル名**
   - 解決策（案）: 既定を `LOCAL_PATHS.local.md`（除外パターン `*.local.md`）とし、導入先は前提定義書で別名に変えてよい。Claude Code では `CLAUDE.local.md` で代替してよい
   - → 合意時に確定
3. **上流リポジトリ自身への適用**
   - 現時点で追跡対象ファイルに `/Users/` を含むものはない（2026-10-06 確認）。検出スクリプトの置き場所（新設 or `check-links.sh` に統合）は実装時に決める
   - → フェーズ 1 のタスク

## 7. ふりかえり

> 起票時点（2026-10-06）の記録。

### 7.1. 観察された傾向

1. **導入先の事例からの一般化** — 導入先で特定ツールの仕組み（`CLAUDE.local.md`）を使って解いた対処を、「論理名と場所の分離」という道具に依存しない規則に引き上げた。ツール固有の部分は実装例としてガイドに残す
2. **既存の型との関係** — 外部資料を「取り込む」なら `_reference/`、「参照する」なら論理名 + ローカル対応表、という 2 つの型の使い分けとして整理できた

### 7.2. 次回への申し送り

- §5-1（規則の置き場所）・§5-2（対応表の既定ファイル名）を合意時に確定する
- 理由の出所は現時点で `ai`。合意時に `ai-reviewed`（または人間の発言があれば `human`）へ更新する
