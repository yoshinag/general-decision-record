# 011. 環境依存パスの論理参照化提案 — セルフレビュー

- **対象:** [11_環境依存パスの論理参照化提案.md](/91_demo_buildup_documents.md/kaizen/11_環境依存パスの論理参照化提案.md)（コミット `3c95226`、GDR-META-035 / 036 とも `Proposed`）
- **レビュー日:** 2026-10-06
- **方法:** 本文の通読、01 §3.1・T1・05・010（GDR-META-031）との突き合わせ、検出コマンドの実行確認

**結論:** 方向（「何を参照しているか」と「この環境のどこにあるか」を分ける）は妥当で、ツール非依存への一般化もできている。ただし、提案どおりの検出コマンドはこのリポジトリで動かず、提案自身が検出に掛かる。ほかに既存仕様との不整合が 2 点、起点が 1 件の事例に対して成果物が多い点がある。A の 7 項目を反映してから合意に進むのがよい。

## A. 実装着手前に反映が必要

### A-1. GDR-META-036 の検出コマンドは、日本語ファイル名のリポジトリで動かない（実行して確認）

決定に例示した `git ls-files | xargs grep -nE '…'` をこのリポジトリで実行すると、全ファイルが `No such file or directory` になる。`git ls-files` は非 ASCII のファイル名を既定で 8 進エスケープして出力し（`core.quotepath`）、`xargs` がそれを実在しないパスとして `grep` に渡すためである。空白を含むファイル名でも同じく壊れる。

- **反映案:** 例示を `git grep -nE '<パターン>'` に替える。追跡対象だけを検索するという意図どおりで、ファイル名の問題が起きない（このリポジトリで動作を確認済み）

### A-2. 提案自身が検出に掛かり、除外の仕組みが決まっていない

`git grep` で検索すると、ヒットするのは 011 自身だけで 5 行ある（検索パターンの例示、§4.1 / §4.2 の `/Users/alice/…`、§5-3 の記述）。GDR-META-036 は「説明用の例は実在しない名前を使い、検出対象から除外できるようにする」とするが、**どう除外するかが書かれていない**。このままでは、規則を説明する文書（上流の 01 / 05、導入先の `_reference/`）が常に検出される。§5-3 の「現時点で `/Users/` を含むものはない」も、011 のコミット後は成り立たない。

- **反映案:** 次のどちらかに決める。前者を推す
  - 例示用の決まった名前（`/Users/alice`、`/home/alice`、`C:\Users\alice`）を規則として定め、検出パターンからその名前を除く
  - 検出結果は「違反」ではなく「確認の候補」とし、人が目で判定する（除外の仕組みを持たない）

### A-3. 「関連」フィールドの対象に外部資料を入れるのは、01 §3.1 と不整合

01 §3.1 は「関連」の対象を **GDR ID または文書内の `§{章}-{番号}` 参照**と定めている。§4.1 の例 `関連: relates-to ガイド §2.4` はこの形式に合わず、§5-1 の案（「関連」の対象に外部資料を加える）は 008 で決めた形式の変更になる。可視化（06）と横断検索（007）は「関連」を機械的に読む前提なので、自由文の呼び名が混ざるとノードとして解決できない。

- **反映案:** 外部資料は「関連」に書かず、理由・影響の本文中で論理名・呼び名を使う。§4.1 の例から該当行を削り、§5-1 は「01 §3 には手を入れない。規則は 03 と T1 に置く」に改める。これで 01 の書式を変えずに済み、版の判定（A-5）も単純になる

### A-4. 「公開 URL を優先、なければ論理名」の順序は、起点の事例の必要と合わない

GDR-META-035 は公開 URL があればそれだけで済む書き方になっている。しかし起点の事例で必要だったのは、**AI が手元のファイルを読めること**である。公開 URL は人には辿れるが、AI が手元のクローンを読む手がかりにならず、非公開リポジトリでは URL 自体が使えない。手元で読む資料は、公開 URL があっても論理名と対応表が要る。

- **反映案:** 順序をやめ、用途で分ける。「AI・人が手元で読む資料は論理名（+ ローカル対応表）。公開 URL は、あれば併記してよい」。手元に置かず参照するだけの資料は URL のみでよい

### A-5. 既存の導入先に対する位置づけ（必須 / 推奨）が書かれていない

タスク 2.1 は「必須移行はない見込み → MINOR」とするが、GDR-META-035 は新しい禁止規則であり、すでに絶対パスを書いている導入先は採用した時点で規則に反する。GDR-META-031 の定義では、必須の移行があれば MAJOR である。MINOR とするなら、その根拠を決定に書く必要がある。

- **反映案:** GDR-META-035 の決定に「規則は以後に書く・更新する文書に適用する。既存文書の置き換えは**推奨**の移行項目とする（絶対パスが残っていても GDR の解釈は変わらないため、必須にしない）」を加える。CHANGELOG の移行区分もこれに合わせる

### A-6. user-level config の更新が実行計画にない

`/gdr-docs` の整理観点は `~/.claude/commands/gdr-docs.md` にあり、4.4 の「AI は場所を推測しない」も AI の振る舞いの規則なので、`~/.claude/CLAUDE.md` に置かないと導入先に届かない。010 ではリポジトリ外への配備を独立したタスク（2.1）にしていたが、011 の実行計画には相当するタスクがない。CHANGELOG の必須 4 項目目（user-level config の更新要否）にも関わる。

- **反映案:** フェーズ 1 に「user-level config の更新（`gdr-docs.md` の整理観点、`CLAUDE.md` に外部資料の参照規則と『推測しない』）— リポジトリ外配備」を追加する。あわせて 4.4 の「推測しない」を GDR-META-035 の**決定**に移す（現状は影響の括弧書きと §4.4 にしかなく、決定として読めない）

### A-7. 対象の境界が曖昧（`~/` 始まりのパスなど）

GDR-META-035 は「ホームディレクトリを含む絶対パス」を禁じるが、このリポジトリの仕様・ガイドは `~/.claude/CLAUDE.md` のような書き方を多用している。`~/` 始まりのパスや、ツールが決めている既定の場所（`~/.claude/` 等）は、どの環境でも同じ意味になるので禁止の対象外のはずだが、決定からは読み取れない。

- **反映案:** 決定に「対象は、特定の利用者・端末でしか成り立たないパス。`~/` 始まりのパスと、ツールが定める既定の場所は対象外」と 1 文で明記する

## B. 実装中に決めて良い項目

1. **対応表の既定ファイル名（§5-2）** — `LOCAL_PATHS.local.md` は "LOCAL" と "local" が重なる。`PATHS.local.md` などで足りる。除外パターン `*.local.md` は Claude Code の `CLAUDE.local.md` も含むので都合がよい
2. **除外対象のファイルを読まない AI ツール** — 検索やファイル一覧で `.gitignore` の対象を既定で飛ばすツールがある。05 の実装例に「明示的にパスを指定して読ませる」注意を 1 行入れる
3. **外部資料の版** — 「ガイド §2.4」のような節番号の参照は、外部資料が改訂されるとずれる。009 / 010 が扱った陳腐化と同じ問題である。節番号まで指す場合に限り、T1 の論理名一覧へ参照時点（コミットか日付）を任意で書ける欄を設けるかを決める。必須にはしない
4. **検出パターンの誤検出** — `/home/[^/]+/` は URL のパス（`https://example.com/home/docs/`）にも一致する。行頭・空白・引用符の直後に限るなどの絞り込みを、実装時に試して決める

## C. 完了時に再評価する項目

1. **対応表を実際に作る手間** — 新しい端末で対応表を作り直す運用が実際に回るか。起点の導入先で、2 台目の端末での作業が発生した時点で確認する
2. **論理名の衝突** — リポジトリ名だけの論理名で足りているか（GDR-META-035 の再検討条件どおり）
3. **検出の頻度** — 文書整理のたびに検索する運用が、実際に混入を拾ったか。拾わないまま数か月続くなら、タイミングを参照変更時だけに絞る

## D. 過剰 / 削れる候補

起点は「1 つの導入先で、1 つのガイドを絶対パスで参照していた」という 1 件である。それに対して GDR 2 件・T1 の新しい節・検出スクリプト・既定ファイル名の規定は多い。

1. **GDR-META-036 を独立させず、035 に統合する** — 036 の中身は「035 を守れているかを検索で確かめる」という確認手順で、単独で見直す場面が想定しにくい。再検討条件も 035 の運用の話である。035 の決定に「確認は追跡対象ファイルの検索（`git grep`）で行い、文書整理の観点に加える」の 1 文を足せば足りる。**推奨: 統合**
2. **検出スクリプト（タスク 1.4）は作らない** — `git grep -nE` の 1 行で済む。`scripts/` に置くと保守対象が増え、`check-links.sh` への統合はリンク検証と目的が違う。**推奨: 削除**（コマンド例をガイドに載せるだけにする）
3. **T1 の「外部資料」節は任意にする** — 大半のプロジェクトは外部資料を参照しない。T1 に常設の節を足すと、空の節が全導入先に配られる。**推奨:** T1 には載せず、03 初回プロンプトガイドに「外部資料を参照する場合は前提定義書に次の表を追加する」として示す
4. **pre-commit hook（036 の代替案 A）** — 「部分採用」としているが、実態は「導入先が任意でやってよい」であり、採用した要素がない。「却下（導入先の任意）」と書く方が正確

D-1〜D-3 を採ると、成果物は「GDR 1 件 + 03 と 05 への追記 + user-level config の更新」になり、01 と T1 は変更しない。

## G. 全体評価

- **採る価値:** あり。絶対パスの混入は AI がファイルを開いた直後に起きやすく、書いた環境では不具合にならないので、規則がないと繰り返す。「論理名と場所の分離」は道具に依存せず、ユーザーの要望（Claude 特化を避ける）にも沿っている
- **主な弱点:** 検出手順が実行確認されないまま書かれていた（A-1 / A-2）。規則の本体より周辺の成果物が大きい（D）
- **判定:** **条件付きで合意可**。D の採否を決め、A の 7 項目を反映すれば `Accepted` に進める。D-1〜D-3 を採った場合、01 と T1 を変えないので、版は MINOR で問題ない
