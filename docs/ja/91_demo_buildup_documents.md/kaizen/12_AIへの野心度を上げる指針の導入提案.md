## 1. GDR（General Decision Record）

**GDR-META-037: 「目標は上げてから検討し、縮めるのは明示的な判断としてだけ」を AI への依頼の指針とする。目標を上げるプロンプトを 04 に `最適解を` と対で追加し、02 に AI の振る舞いと留意点を 1 行ずつ足す**

- **status:** Proposed
- **scope:** meta, pol
- **決定:**
  - **指針:** AI への依頼では、**目標（何を達成するか）を上げてから検討し、手段（どう達成するか）を縮める**。`最適解を` / `過剰じゃない？` は手段を縮める道具である。目標を縮めること自体は禁じない（ROI の判断には目標の価値を問うことが含まれる）が、**目標を縮めるのは理由を残した明示的な判断としてだけ行い、手段の圧縮の副作用として判断を経ずに縮めない**
  - **04 プロンプトガイド:** §2「構造化・深掘り」の導入文を「判断の**精度**と依頼の**大きさ**を上げるための深掘り」に広げ、その下に「2.1. 目標を上げる」を追加する。載せるプロンプトは 3 系統 5 個（§4.1）
    - **高度（Altitude）** — 目の前のタスクではなく、その先の成果や、作業を生む仕組みを判断の対象にする
    - **深さ（Depth）** — 第一人者が使う手法・元データを求め、前提を反証させ、外部の検証手段を決めさせる
    - **幅（Range）** — 課題を「何をするか」で言い換え、他分野の職能が**やること**を借りる
    - 適用場面（成果の定義がはっきりした作業に向く）と、目標を上げると先に AI へ渡すデータ・環境の準備が要ること（前提定義書に残す）を注記する
  - **04 §7 使い方のコツ:** 「上げてから縮める」組み合わせ例を 1 項目追加する（§4.3）
  - **02 §6 AI に求められる振る舞い:** 行「目標の引き上げ」を追加する（§4.2）
  - **02 §3.3 デメリット・留意点:** 行「目標の縮小」を追加する — 手段の圧縮が判断を経ずに目標まで縮める副作用と、その緩和策（§4.2）
  - **野心的な目標を GDR にするとき:** 撤退の基準を**再検討条件**に、検証手段を**影響**に書く。届かなかった挑戦は `Accepted → Rejected`（01 §2 の「合意後の撤回」）にし、却下理由に実装で届かなかった旨を書いて「採らない理由」として残す（書式は変えず、04 §2.1 の注記として載せる）
  - **user-level config:** `~/.claude/CLAUDE.md` §4 の「過剰設計の検出」の記述に、圧縮は手段に向け、目標を縮めるときは明示的な判断として理由を残す旨を 1 文足す
  - **出典:** 3 系統の分け方は Felix Rieseberg「How to Be More Ambitious: A Tutorial for Humans with Models」（<https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/>、参照 2026-10-16）による。04 §2.1 に出典として示し、本文は考え方の要約にとどめて転載しない
- **理由:** 現行の GDR ビルドアップには、提案を**縮める**道具（`最適解を` / `過剰じゃない？` / 02 §6「過剰設計の抑止」）は揃っているが、**依頼そのものを大きくする**道具がない（§2-1）。モデルの能力は短い周期で伸びており、人間が依頼を小さく見積もること自体が成果の上限になる — 出典記事の主張であり、記事が引く目標設定の研究（具体的で難しい目標は「最善を尽くせ」より成果が高い）とも合う。縮める道具だけを持つと、手段の圧縮が目標の圧縮にすり替わりやすい（§2-2）。両者は対立せず、扱う層が違う: 目標を上げてから手段を縮めれば両立する。目標を縮めることを禁じないのは、既存の ROI 判断（例: 02 §6「数十 ms の最適化のために数百行の改修」の指摘）が目標の価値を問う判断を含むためで、問題は縮めること自体ではなく、判断を経ずに縮むことにある。さらに GDR は野心的な目標の安全網になる — 再検討条件が撤退の基準を先に決め、`Rejected` が届かなかった挑戦を資産に変え、理由の出所が「解けるはず」という強気を根拠のない断定にしない（§2-3）。変更を 04 と 02 の追記に絞るのは、指針は書式や status の意味を変えず、プロンプトと振る舞いの追加で足りるため
  - **代替案 A:** 02 に第 4 の原則（例「目標は高く」）を追加する → 3 原則はサイクルの構造（対話・積層・検証）を述べており、依頼の姿勢は層が違う。§6 の振る舞い 1 行と §3.3 の留意点 1 行で足りる。却下
  - **代替案 B:** 04 に独立した節（§3 の前に「目標を上げる」）を新設する → §3 以降が繰り下がり、05 から 04 §6 への見出しリンクが切れる。§2 の下位節にし、§2 の導入文を 1 行広げれば番号は動かず趣旨も通る。却下
  - **代替案 C:** 02 §3.2「AI の既知の失敗モード」の表に人間側の失敗「依頼が小さすぎる」を追加する → 表は AI の失敗モードと GDR の抑止の対応表であり、人間側の失敗を混ぜると表の意味が変わる。GDR 自身の副作用として §3.3 に置くほうが正確。却下
  - **代替案 D:** 短縮キーワード（例 `野心：[課題]`）として定義する → キーワードは文書生成などの定型操作のためのもので（04 §6）、プロンプトの言い回しとは役割が違う。まずプロンプトとして載せ、定型化の需要が出たら再検討する。却下
  - **代替案 E:** 記事の再利用プロンプトを全文訳して載せる → 転載になる。問いの骨子（一流ならやること / 元データ / 手法と道具 / 自分とモデル以外の検証手段）を自分の言葉で書けば足りる。却下
  - **代替案 F:** 記事の「無理な目標を妥当なものとして示し、渋ったら解けると言い張る」をそのまま採る → 目標の提示としては採るが、AI に結果を断定させる指示にはしない。届かなければ届かないと報告させ、`Rejected` として残す（02 §3.2 の自信過剰の抑止と両立させる）。部分採用
  - **代替案 G:** 「目標は縮めない」を絶対則にする（起票時の案）→ 既存の ROI 判断と矛盾する（02 §6 の同じ表の中で「ROI で目標を疑え」と「目標は縮めるな」が並ぶ）。レビュー（A-1）で「明示的な判断としてだけ縮める」に修正。却下
- **影響:**
  - 04 §2 の導入文を 1 行広げ、§2.1（新設の下位節）と §7 に追記する。§番号の繰り下がりはない
  - 02 §6 の表と §3.3 の表にそれぞれ 1 行追加する

  - 版: 既存の GDR の書式・解釈は変わらないが、user-level config の更新を伴う（CHANGELOG の定義で config は GDR 仕様の範囲）。v2.1 と同じ扱いで **MINOR（v2.2）**、移行項目は「任意: config の更新」の見込み。§6 の 2.1 で確定する

## 2. 現状

1. **依頼を大きくする道具がない** — 04 プロンプトガイドの深掘り（§2）は判断の精度を上げる問い（代替案・scope・定量化）であり、目標そのものを引き上げる問いはない。02 §6 の定量化の例も「ファイルサイズ、行数、実行時間」にとどまり、第一人者が使う手法や外部の検証手段を求める観点がない
2. **縮める道具が目標まで縮めうる** — `最適解を` は「最小限の手段で目的を達成する案」を求める圧縮指示と定義されている（02 §3.1-4 / 04 §3）。定義上は手段の圧縮だが、目的と手段を分けて書く規則がないため、圧縮のたびに目的も判断を経ずに小さく言い直されうる。02 §3.3 のデメリット表にこの副作用の記載はない
3. **野心的な目標を記録する書き方が示されていない** — 再検討条件・`Rejected`・理由の出所は、届くか分からない目標に挑むときの安全網として働く（撤退基準・失敗の資産化・断定の抑止）が、その使い方はどこにも書かれていない

## 4. 詳細セクション

### 4.1. 04 §2 導入文と §2.1「目標を上げる」の文案

§2 導入文（既存「AI の初期提案に対して、判断の精度を上げるための深掘り。」を置き換え）:

```markdown
AI の初期提案に対して、判断の**精度**と依頼の**大きさ**を上げるための深掘り。本体の表は精度を、§2.1 は大きさを上げる。
```

§2.1（新設）:

```markdown
### 2.1. 目標を上げる

目標（何を達成するか）を先に上げ、手段（どう達成するか）は §3 の `最適解を` で縮める。順序は「上げる → 縮める」。
目標を縮めること自体は構わないが、理由を残した明示的な判断として行い、手段の圧縮の副作用で縮めない。

| 系統 | プロンプト | 効果 |
|---|---|---|
| 高度 | `その先の成果は？` | 目の前のタスクではなく、その先の成果を対象に依頼を組み直させる（例: 個々の不具合を直す → 不具合が出ない状態を保つ）。作業の結果だけでなく、その作業を生む手順・会議・レビューの設計も対象にできる |
| 深さ | `一流ならどうする？` | その分野の第一人者が、まだ頼んでいないのに必ずやること / 最初に当たる元データ / 使う手法と道具 — を挙げさせ、それを満たす依頼文に書き直させる。元データに当たってこちらの思い込み（「原因は X のはず」）を反証する方向で検証させる |
| 深さ | `外部の審判は？` | AI 自身の自己評価ではなく、テスト・計測・実データ・別のレビュアーなど、自分と AI 以外で結果を判定できる手段を決めさせる |
| 幅 | `動詞で言い換えて` | 成果物の名前（名詞）ではなく、それが果たす働き（動詞）で課題を言い直させ、別の解き方を探させる |
| 幅 | `[職能] がやることをやって` | 他分野の職能（セキュリティ監査人・編集者・空売り投資家など）の**作業**を借りる。「[職能] になりきって」とは頼まない — 振る舞いの演技は成果を上げないことが多い |

> **適用場面:** 高度の問いは、成果の定義がはっきりした作業（普段なら会議や調整を要するもの）に向く。文体や表現を決める作業では効きにくい。
> 目標を上げると、AI に渡すデータ・環境・検証手段の準備が先に要ることが多い。何を渡したかは前提定義書に残す（外部資料は [03 §2.4](/01_GDR/guide/03_FIRST_PROMPT_GUIDE.md) の論理名で）。

> **野心的な目標を GDR にするとき:** 撤退の基準を**再検討条件**に（「N 週で X に届かなければ縮小」）、判定の手段を**影響**に書く。
> 届かなかった挑戦は削除せず `Rejected`（合意後の撤回）にし、却下理由に「実装で届かなかった」旨と次に採らない理由を残す。
> 目標は強く提示してよいが、結果を断定させない — 届かなければ届かないと報告させる。

> 出典: 3 系統の分け方は Felix Rieseberg「How to Be More Ambitious: A Tutorial for Humans with Models」
> （https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/ 、参照 2026-10-16）による。
```

### 4.5. 「目標」と「手段」の切り分けの例

| 依頼 | 目標（上げる） | 手段（縮める） |
|---|---|---|
| クラッシュの修正 | 個別の修正 → 「クラッシュが出ない状態を保つ」 | 監視と再現環境は既存の CI を使い、新しい基盤は作らない |

## 5. 検討課題

1. **プロンプトの数**
   - 起票時は 7 個。04 §2 は 6 個、§3 は 5 個で、新節としては最多になるうえ、`一流ならどうする？` と `外部の審判は？` で検証手段が重複していた
   - → **確定:** 5 個。`仕組みごと見直して` は `その先の成果は？` の効果欄に、`前提を疑って` は `一流ならどうする？` の効果欄に吸収。`外部の審判は？` は 02 §5.3 と直結するため残す（レビュー D-1）
2. **プロンプトの名前**
   - `高度を上げて` は出典の訳語で、日本語で単独では意味が取りにくい
   - → **確定:** `その先の成果は？`。04 §2 の既存プロンプト（`scope は？` `影響範囲は？`）と疑問形で揃う。系統名「高度」は表の 1 列目に残し、出典との対応を保つ（レビュー D-2）
3. **user-level config への反映**
   - → **確定:** 足す（§4.4）。config の更新を伴うため版は MINOR（v2.2）の見込み（レビュー D-3）
4. **外部の審判と別モデルのレビュー**
   - 「AI 自身に自分の成果を採点させない」は、05 セットアップのモデル分担（レビュアーを別モデルにする運用）と同じ考え方。05 から 04 §2.1 へ相互参照を張るか
   - 解決策: 05 はツール固有のガイドなので、今回は張らない。必要が出たら再検討
