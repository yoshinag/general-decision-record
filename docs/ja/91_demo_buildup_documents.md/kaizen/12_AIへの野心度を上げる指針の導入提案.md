## 1. GDR（General Decision Record）

**GDR-META-037: 「目標は上げ、手段は縮める」を AI への依頼の指針とする。目標を上げるプロンプトを 04 に、`最適解を` と対で追加し、02 に AI の振る舞いと留意点を 1 行ずつ足す**

- **status:** Proposed
- **scope:** meta, pol
- **決定:**
  - **指針:** AI への依頼では、**目標（何を達成するか）は上げ、手段（どう達成するか）は縮める**。既存の `最適解を` / `過剰じゃない？` は手段を縮める道具であり、目標を縮めるためには使わない。順序は「目標を上げる → 手段を縮める」
  - **04 プロンプトガイド:** §2「構造化・深掘り」の下に「2.1. 目標を上げる」を追加し、次の 3 系統のプロンプトを載せる（§4.1）
    - **高度（Altitude）** — 目の前のタスクではなく、その先の成果や仕組みを判断の対象にする
    - **深さ（Depth）** — 第一人者が使う手法・元データ・検証手段を求め、前提を疑わせる
    - **幅（Range）** — 課題を「何をするか」で言い換え、他分野の職能が**やること**を借りる
  - **04 §7 使い方のコツ:** 「上げてから縮める」組み合わせ例を 1 項目追加する
  - **02 §6 AI に求められる振る舞い:** 行「目標の引き上げ」を追加する（§4.2）
  - **02 §3.3 デメリット・留意点:** 行「目標の縮小」を追加する — `最適解を` の圧縮が手段を越えて目標まで縮める危険と、その緩和策（§4.2）
  - **野心的な目標を GDR にするとき:** 撤退の基準を**再検討条件**に、検証手段を**影響**に書く。届かなかった挑戦は `Rejected` にして「採らない理由」として残す（§4.3。書式は変えず、04 §2.1 の注記として載せる）
  - **出典:** 3 系統の分け方は Felix Rieseberg「How to Be More Ambitious: A Tutorial for Humans with Models」（<https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/>、参照 2026-10-16）による。04 §2.1 に出典として示し、本文は考え方の要約にとどめて転載しない
- **理由:** 現行の GDR ビルドアップには、提案を**縮める**道具（`最適解を` / `過剰じゃない？` / 02 §6「過剰設計の抑止」）は揃っているが、**依頼そのものを大きくする**道具がない（§2-1）。モデルの能力は短い周期で伸びており、人間が依頼を小さく見積もること自体が成果の上限になる — 出典記事の主張であり、目標設定の研究（具体的で難しい目標は「最善を尽くせ」より成果が高い）とも合う。縮める道具だけを持つと、手段の圧縮が目標の圧縮にすり替わりやすい（§2-2）。両者は対立せず、扱う層が違う: 目標を上げ、手段を縮めれば両立する。さらに GDR は野心的な目標の安全網になる — 再検討条件が撤退の基準を先に決め、`Rejected` が届かなかった挑戦を資産に変え、理由の出所が「解けるはず」という強気を根拠のない断定にしない（§2-3）。変更を 04 と 02 の追記に絞るのは、指針は書式や status の意味を変えず、プロンプトと振る舞いの追加で足りるため
  - **代替案 A:** 02 に第 4 の原則（例「目標は高く」）を追加する → 3 原則はサイクルの構造（対話・積層・検証）を述べており、依頼の姿勢は層が違う。§6 の振る舞い 1 行と §3.3 の留意点 1 行で足りる。却下
  - **代替案 B:** 04 に独立した節（§3 の前に「目標を上げる」）を新設する → §3 以降が繰り下がり、05 から 04 §6 への見出しリンクが切れる。§2 の下位節にすれば番号は動かない。却下
  - **代替案 C:** 02 §3.2「AI の既知の失敗モード」の表に人間側の失敗「依頼が小さすぎる」を追加する → 表は AI の失敗モードと GDR の抑止の対応表であり、人間側の失敗を混ぜると表の意味が変わる。GDR 自身の副作用として §3.3 に置くほうが正確。却下
  - **代替案 D:** 短縮キーワード（例 `野心：[課題]`）として定義する → キーワードは文書生成などの定型操作のためのもので（04 §6）、プロンプトの言い回しとは役割が違う。まずプロンプトとして載せ、定型化の需要が出たら再検討する。却下
  - **代替案 E:** 記事の再利用プロンプトを全文訳して載せる → 転載になる。問いの骨子（一流ならやること / 元データ / 手法と道具 / 自分とモデル以外の検証手段）を自分の言葉で書けば足りる。却下
  - **代替案 F:** 記事の「無理な目標を妥当なものとして示し、渋ったら解けると言い張る」をそのまま採る → 目標の提示としては採るが、AI に結果を断定させる指示にはしない。届かなければ届かないと報告させ、`Rejected` として残す（02 §3.2 の自信過剰の抑止と両立させる）。部分採用
- **影響:**
  - 04 §2.1（新設の下位節）と §7 に追記する。§番号の繰り下がりはない
  - 02 §6 の表と §3.3 の表にそれぞれ 1 行追加する
  - 01 GDR 仕様・T0〜T2 テンプレート・短縮キーワードは変更しない
  - user-level config（`~/.claude/CLAUDE.md`）の「過剰設計の検出」の記述（AI 側も最初から ROI を意識）に「目標は縮めない」旨を 1 文足すかを、版の判定と合わせて決める（§5-3）
  - 版: 新しいプロンプトと指針の追加のみで、既存の GDR の書式・解釈は変わらない。MINOR（v2.2）か、版を上げない文言追加かを §6 の 2.1 で判定する
- **再検討条件:**
  - 導入先で「目標を上げる」プロンプトを使った結果、過剰設計の差し戻し（`過剰じゃない？` / `最適解を`）が明らかに増える → 「上げる → 縮める」の順序の説明を強めるか、§2.1 の適用場面を絞る
  - 3 系統のうち使われない系統が続く → その系統を削る
  - 特定のプロンプトが定型操作として繰り返し使われる → 短縮キーワード化を検討（代替案 D）
  - 出典記事が改訂・削除される → 出典の参照時点を明記したまま、要約が自立しているかを確認する

## 2. 現状

1. **依頼を大きくする道具がない** — 04 プロンプトガイドの深掘り（§2）は判断の精度を上げる問い（代替案・scope・定量化）であり、目標そのものを引き上げる問いはない。02 §6 の定量化の例も「ファイルサイズ、行数、実行時間」にとどまり、第一人者が使う手法や外部の検証手段を求める観点がない
2. **縮める道具が目標まで縮めうる** — `最適解を` は「最小限の手段で目的を達成する案」を求める圧縮指示と定義されている（02 §3.1-4 / 04 §3）。定義上は手段の圧縮だが、目的と手段を分けて書く規則がないため、圧縮のたびに目的も小さく言い直されうる。02 §3.3 のデメリット表にこの副作用の記載はない
3. **野心的な目標を記録する書き方が示されていない** — 再検討条件・`Rejected`・理由の出所は、届くか分からない目標に挑むときの安全網として働く（撤退基準・失敗の資産化・断定の抑止）が、その使い方はどこにも書かれていない

## 4. 詳細セクション

### 4.1. 04 §2.1「目標を上げる」の文案

```markdown
### 2.1. 目標を上げる

§2 の問いが判断の**精度**を上げるのに対し、ここでの問いは依頼の**大きさ**を上げる。
目標（何を達成するか）は上げ、手段（どう達成するか）は §3 の `最適解を` で縮める。順序は「上げる → 縮める」。

| 系統 | プロンプト | 効果 |
|---|---|---|
| 高度 | `高度を上げて` | 目の前のタスクではなく、その先の成果を対象に依頼を組み直させる（例: 個々の不具合を直す → 不具合が出ない状態を保つ） |
| 高度 | `仕組みごと見直して` | 作業の結果ではなく、その作業を生む手順・会議・レビューの設計を対象にさせる。新旧を並行で回して比べる形で提案させる |
| 深さ | `一流ならどうする？` | その分野の第一人者が、まだ頼んでいないのに必ずやること / 最初に当たる元データ / 使う手法と道具 / 自分と AI 以外の検証手段 — を挙げさせ、それを満たす依頼文に書き直させる |
| 深さ | `前提を疑って` | 元データに当たり、こちらの思い込み（「原因は X のはず」）を反証する方向で検証させる |
| 深さ | `外部の審判は？` | AI 自身の自己評価ではなく、テスト・計測・実データ・別のレビュアーなど、外から結果を判定できる手段を決めさせる |
| 幅 | `動詞で言い換えて` | 成果物の名前（名詞）ではなく、それが果たす働き（動詞）で課題を言い直させ、別の解き方を探させる |
| 幅 | `[職能] がやることをやって` | 他分野の職能（編集者・空売り投資家・法廷会計士など）の**作業**を借りる。「[職能] になりきって」とは頼まない — 振る舞いの演技は成果を上げない |

> **野心的な目標を GDR にするとき:** 撤退の基準を**再検討条件**に（「N 週で X に届かなければ縮小」）、
> 判定の手段を**影響**に書く。届かなかった挑戦は削除せず `Rejected` にし、却下理由を「次に採らない理由」として残す。
> 目標は強く提示してよいが、結果を断定させない — 届かなければ届かないと報告させる。

> 出典: 3 系統の分け方は Felix Rieseberg「How to Be More Ambitious: A Tutorial for Humans with Models」
> （https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/ 、参照 2026-10-16）による。
```

### 4.3. 04 §7 使い方のコツへの追記の文案

```markdown
6. **上げてから縮める** — `高度を上げて` / `一流ならどうする？` で目標を上げてから、`過剰じゃない？` / `最適解を` で手段を縮める。逆順にすると、縮めた手段に合わせて目標まで小さくなる
```

### 4.4. 「目標」と「手段」の切り分けの例

| 依頼 | 目標（上げる） | 手段（縮める） |
|---|---|---|
| クラッシュの修正 | 個別の修正 → 「クラッシュが出ない状態を保つ」 | 監視と再現環境は既存の CI を使い、新しい基盤は作らない |
| 解約分析 | 集計表 → 「未知の早期シグナルを見つけ、保留データで検証する」 | 手法は統計モデル 1 種から始め、ダッシュボードは作らない |
| GDR の導入 | 1 プロジェクトへの導入 → 「判断の再検討が文書から自動で起きる」 | 書式とサイクルだけで始め、可視化・横断検索は後回し |

## 5. 検討課題

1. **プロンプトの数**
   - §4.1 は 7 個。04 §2 の 6 個と同程度だが、系統ごとに 1 個に絞る案（`高度を上げて` / `一流ならどうする？` / `動詞で言い換えて`）もある
   - 解決策: レビューで決める。絞る場合も `外部の審判は？` は残す候補（GDR の §5.3「実装が判断を検証する」と直結するため）
2. **プロンプトの名前**
   - `高度を上げて` は日本語として意味が取りにくい可能性がある。代案: `一段上の目標で` / `その先の成果は？`
   - 解決策: レビューで決める
3. **user-level config への反映**
   - `~/.claude/CLAUDE.md` §4 の「過剰設計の検出」の行に「圧縮は手段に対して行い、目標は縮めない」を 1 文足すか
   - 解決策: 足す方向で検討。版の判定（§6 の 2.1）で user-level config の更新要否として記録する
4. **外部の審判と別モデルのレビュー**
   - 「AI 自身に自分の成果を採点させない」は、05 セットアップのモデル分担（レビュアーを別モデルにする運用）と同じ考え方。05 から 04 §2.1 へ相互参照を張るか
   - 解決策: 05 はツール固有のガイドなので、今回は張らない。必要が出たら再検討
