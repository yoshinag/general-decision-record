## 結論（先に）

**置換（`Superseded`）の経路は、仕様・ガイド・config の間で一貫して入っており、そのまま発行できる水準にある。** 初回レビューの A-1〜A-7 は本文に正しく反映されている（3 段の時点・不変条件・遷移の限定・処置の選択肢・入れ先・自身の「関連」）。

ただし、**合意後の撤回（`Accepted → Rejected`）の経路が、提案の決定にはあるのに仕様の本文から落ちている**。その結果、01 の二段保管の表（`Rejected` は確定時点で退避）と新しい不変条件がぶつかる。加えて、決定した「版によらず適用（v1.x の読み替え）」がどこにも書かれていない。この 2 点（A-1・A-2）と、手作業の退避が不変条件を素通りする点（A-3）を直せば、v2.3 として発行してよい。

導入先での試行（実行計画 2.1）を発行の前提にするかどうかは、G で判断材料を示す。

## A. 発行前に反映が必要

### A-1. 撤回の経路が仕様の本文にない — 01 二段保管の表と不変条件が衝突する【重大】

提案の決定は、撤回について時点を明記している（① 撤回を諮る時点 / ② `Rejected` の確定時 / ③ 旧の退避前）。しかし仕様に入った文言は**置換の時点しか書いていない**。

- 01 §3: 「置換の起票時に列挙し、合意時に人間が判定し、**新が `Implemented` になった時点で**『関連』を付け替える」— 撤回には「新」も `Implemented` もない
- 02 §5.2: 見出しで「置換（または合意後の撤回）」と言いながら、① は「新の起票〜レビュー時」、③ は「新の `Implemented` 時」で、撤回のときにいつ何をするかが読み取れない
- **01 §3 二段保管の表は `Rejected` の退避を「確定時点」のまま**にしている。撤回された GDR を前提にしている有効な GDR があれば、不変条件は「退避しない」と言い、表は「確定時点で退避」と言う。02 §5.2「失効後の二段保管」の文も同じ

具体例: `GDR-ARCH-009`（`Accepted`）を前提に `GDR-ARCH-010`（`Proposed`, `depends-on GDR-ARCH-009`）が起票された後、ARCH-009 が実装段階で撤回される。表に従えば ARCH-009 は確定時点で退避され、ARCH-010 は退避済みの GDR を前提にしたまま残る。

**修正案:**

1. 01 §3 の波及チェックの項に撤回の場合を 1 文足す: 「合意後の撤回では、撤回を諮る時点で列挙し、`Rejected` の確定時に判定し、退避の前に付け替える」
2. 02 §5.2 の ①〜③ にそれぞれ「（撤回: …）」を括弧で添える（提案の決定の表どおり）
3. 01 §3 の二段保管の表の「退避のタイミング」と 02 §5.2「失効後の二段保管」に、「いずれも、退避する GDR を `depends-on` / `refines` で指す有効な GDR が残っていないこと（波及チェックの不変条件）」を 1 句足す
4. 撤回の判定結果の記録先を決める。撤回された GDR の「影響」に書けば、不変条件が満たされるまで退避されないので、解決までは読まれ続ける（提案の現状の記述で足りる。仕様側にも「撤回では撤回された GDR の影響に記録」と書く）

### A-2. 「版によらず適用（v1.x の読み替え）」がどこにも書かれていない

提案の決定は「解釈版によらず適用し、v1.x では②を新 GDR の発行時と読み替える」と定めた。しかし:

- 仕様（01 / 02）にも、`~/.claude/CLAUDE.md` §6 の互換モードの表にも、読み替えの記述がない
- `gdr-docs.md` の版条件（「v1.x の導入先では…旧 GDR の退避は Superseded 化時点」）は、v1.x では**退避が置換と同時**であることを示している。v1.x では ②（判定）と ③（付け替え）が同じ時点になり、そこで不変条件を満たせなければ退避を待つ必要がある — この帰結もどこにもない
- `gdr-flow.md` の版条件は「フェーズ 4 / 5 / 7 の status 操作は v2.0 以上の規則」としているが、フェーズ 4・7 に足した波及チェックが版によらないことは書いていない。v1.x の導入先で AI が「フェーズ 4 は v2.0 以上の規則だから波及チェックも不要」と読む余地がある

**修正案:** 本文を増やさず、次の 3 か所に 1 句ずつ足す。

1. CHANGELOG v2.3 の互換性欄: 「解釈版によらず適用。v1.x では ② 判定と ③ 付け替えを新 GDR の発行時（旧を `Superseded` にする時点）にまとめて行う」
2. `gdr-flow.md` / `gdr-docs.md` の版条件: 「波及チェックは版によらず適用（v1.x では判定・付け替え・退避の条件を置換時点にまとめる）」
3. 02 §5.2 の波及チェックの項の末尾に同じ 1 文（上流文書だけを読む導入先のため）

### A-3. 手作業の退避（`アーカイブ：` / `/gdr-archive`）が不変条件を素通りする

不変条件を確認するのは `gdr-flow.md` フェーズ 7 と `gdr-docs.md` だけで、退避そのものを行う `gdr-archive.md` は何も確認しない。仕様は退避の手段として `アーカイブ：` / `/gdr-archive` を直接案内している（02 §5.2）ので、ユーザーが失効 GDR を手で退避すると、検出の仕組み（「失効 GDR を指す有効な GDR」）が退避済みの側を指す状態で残る。退避先は AI の既定の読み込み対象外なので、後から気づきにくい。

**修正案（どちらか）:**

- **(a) 推奨:** `gdr-archive.md` に確認を 1 段足す — 対象が GDR 本文（`notes/91_gdr/gdr/` 配下、または `**GDR-` レコードを含むファイル）なら、そのファイル内の GDR ID を `depends-on` / `refines` で指す有効な GDR を検索し、あれば一覧を示して AskUserQuestion で続行を確認する（止めはしない — 退避の発火主体はユーザーという既存方針を保つ）
- (b) 最小: 04 §5 の `波及チェック`（引数なし）の説明に「退避済みの GDR を指す有効な GDR も列挙する（INDEX の archived 行と突き合わせる）」を足し、事後検出だけ保証する

(a) は config の変更が 1 ファイル増えるが、05 の `gdr-archive.md` の行にも 1 句の同期が要る。(b) は文言だけで済む。発行を急ぐなら (b)、手順として閉じるなら (a)。

## B. 運用しながら決めて良い

1. **② の時点で列挙をやり直す。** ① と ② の間（新が `Proposed` の間）に、旧を `depends-on` する GDR が新たに起票されうる。② の冒頭で列挙を取り直し、差分を判定に加える、と 02 §5.2 に 1 句添えるとよい（費用は逆引き 1 回）
2. **「波及候補」と「波及チェック」の行の関係。** ① で「影響」に書いた「波及候補」の行を、② で「波及チェック」の行に**置き換える**のか**併記する**のかが未定。置き換えれば「影響」が短く保てる
3. **`relates-to` に弱める場合の向き先。** 旧に向けたまま弱めると、退避後に退避済み GDR を指す `relates-to` が残る（不変条件の対象外なので合法）。新へ向けるのが自然だが、どちらでもよいことを明記すると迷いが減る
4. **ずっと `Proposed` のまま放置された GDR が退避を止める。** 不変条件は `Proposed` も有効に数えるので、放置された提案が旧の退避を無期限に止めうる。再検討条件 2（退避待ちが 3 件以上・1 か月以上）で拾えるので、当面は観察でよい
5. **1 ファイルに複数の GDR がある場合の退避。** 退避はファイル単位なので、同じファイルの一部の GDR だけが不変条件を満たさないと、ファイル全体の退避が止まる。既存の二段保管にもある問題で、本提案が悪化させるものではないが、導入先の試行で発生頻度を見る

**発行判断: A-1〜A-3 を反映すれば v2.3（MINOR）として発行してよい。** 必須の移行項目はなく、既存の GDR の解釈も変わらないので、MINOR の判定は正しい。

**導入先での試行（実行計画 2.1）を発行の前提にするかは、ユーザーの判断事項。** 判断材料:

- **前提にする場合:** 上流には実際の置換の履歴がなく（`Superseded` は説明用サンプル 1 件）、手順が現場で重すぎないかを確かめないまま配布することになるのを避けられる。代わりに、導入先で置換が起きるまで発行が止まる（いつになるか分からない）
- **前提にしない場合:** 変更は手順と振る舞いの追加だけで、導入先は `/gdr-upgrade` で採否を選べる。重すぎれば再検討条件と次の MINOR で緩められる。試行は「発行後の観察」（C-1〜C-3）に移す
- **レビュアーの推奨:** 前提にしない。理由は、A-1〜A-3 を直した後に残るリスクが「手間が想定より重い」という運用コストの種類で、版を出してから観察しても取り返しがつくため。ただし、試行を発行の条件にしたのは合意済みの実行計画なので、変える場合は提案の §6 にその判断と理由を残す
