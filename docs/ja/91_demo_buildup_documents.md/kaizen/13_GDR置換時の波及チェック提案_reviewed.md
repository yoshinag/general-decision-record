## 結論（先に）

**穴の指摘は正しく、起票の価値はある。** 現行の参照の規律は前向きだけで、失効した GDR を前提にしている後続を見直す手順は実際にない。列挙の基準を scope でなく依存の辺にしたこと、判定を人間に残したこと、新しいフィールドを作らないことも妥当。

ただし **手順を「新の `Accepted` 時点」の 1 点に全部載せたこと**が、既存のライフサイクル（失効は `Accepted`、退避は `Implemented`、その間は撤回で旧が復帰しうる）と噛み合っていない。A-1 を直すと A-2・A-3 の大半は一緒に解ける。合意前に A-1〜A-6 の反映が必要。

## A. 実装着手前に反映が必要

### A-1. 列挙・判定・付け替えを 1 時点にまとめたことが、既存の 2 段階（失効 / 退避）と衝突する【重大】

提案は、新が `Accepted` になった時点で「列挙 → 判定 → 関連の付け替え → 記録」を全部行う。これは次の 3 点で既存の規則と合わない。

1. **合意が盲目になる。** 列挙は合意の**後**なので、人間は「この置換で後続が何件崩れるか」を知らずに合意する。後続の一覧はまさに新 GDR の「影響」に書くべき内容で、列挙自体は機械的で安い（「関連」の逆引き 1 回）。代替案 B は「新が却下されれば無駄になる」として起票時の列挙を退けているが、無駄になるコストがほぼないので理由として弱い
2. **付け替えが早すぎる。** 新が `Accepted` の間、実装はまだ旧に従っている（02 §6 参照の規律「`Accepted (supersedes X)` を根拠にするときは、実装はまだ X に従っていることを前提に置く」）。この時点で後続の「関連」を新へ付け替えると、後続は「まだ実装されていない判断」を前提にしていると表明することになる
3. **撤回時の復帰と噛み合わない。** 新が `Accepted → Rejected` で撤回されると旧が復帰する（01 §3）。すでに付け替えた「関連」は `Rejected` の新を指したままになり、元に戻す手順が要る。提案の「撤回の場合は付け替え先がないため参照を外す」は、このケースでは誤り（付け替え先は復帰した旧）

**修正案:** 既存のライフサイクルに沿って 3 段に分ける。

| 段階 | 時点 | 行うこと |
|---|---|---|
| 列挙 | 置換する新 GDR の**起票〜レビュー時**（`Proposed`） | 旧を `depends-on` / `refines` している GDR を列挙し、新 GDR の「影響」に「波及候補」として書く。合意の判断材料にする |
| 判定 | **合意時**（新が `Accepted`、旧が `Superseded`） | 人間が 1 件ずつ判定。「影響あり」は置換の起票へ。結果を「影響」に記録 |
| 付け替え | **新が `Implemented` になった時点**（旧の退避と同時） | 「影響なし」と判定した GDR の「関連」を旧から新へ付け替える。旧を退避する前に済ませる |

こうすると、撤回時は「関連」がまだ旧を指しているので戻す作業が要らず、旧の退避後に失効 GDR を指す「関連」が残らない（退避先は AI の既定の読み込み対象外なので、残ると辿れなくなる）。代替案 B は「部分採用」から「採用（列挙は起票時）」に改める。

### A-2. 契機 (b) が、仕様にない遷移を前提にしている

決定の契機 (b) は「`Accepted` / `Implemented` だった GDR が `Rejected`（合意後の撤回）になったとき」。しかし 01 §3 の遷移表にあるのは `Accepted → Rejected` だけで、**`Implemented → Rejected` は定義されていない**（`Implemented` から出る遷移は `Superseded` のみ）。この提案は、手順の追加だけと言いながら status の遷移を 1 つ黙って増やしている。

**修正案:** (b) を `Accepted → Rejected` に限る。実装済みの判断をやめる場合は、否定形の決定を持つ新 GDR で置換する（01 §3「X はしない」規則）ので、契機 (a) に含まれる。§4.1 の文案「`Accepted` / `Implemented` からの撤回時点」も同じく直す。

### A-3. 撤回で記録と保留が AI の視界から消える

契機 (b) では、結果を「撤回された GDR の影響」に記録するとしている。しかし `Rejected` は**確定時点で退避**される（01 §3 二段保管）。退避先は AI の既定の読み込み対象外なので、判定結果も「保留」も読まれなくなる。置換の場合も、保留は新 GDR の「影響」の 1 行に埋もれ、後から拾う経路がない（§5-2 は認識しているが先送り）。

**修正案:** 「保留」を専用の状態にせず、**「関連」が失効 GDR を指したままであること自体を未解決の印にする**。

- 規則を不変条件として書く: 「有効な GDR は、退避済みの失効 GDR を `depends-on` / `refines` で指したままにしない」
- 判定が済まない GDR は「関連」を旧に向けたまま残る → いつでも機械的に検出できる（`整合性チェック` で拾える）
- これで §5-2（保留の置き場所）と §5-3（導入済みへの遡り適用）が同時に片づく。手順を通らずに status を手で書き換えた場合の取りこぼしも、後から検出できる
- 判定の選択肢は「影響なし / 影響あり」の 2 つに減らせる（→ D-2）

### A-4. 「影響なし → 新へ付け替え」が、成り立たない依存を作りうる

「影響なし」には中身の違う 2 つの場合がある。

- (i) 後続が依存していたのは旧のうち**新でも変わらない部分** → 新へ付け替えてよい
- (ii) 後続は旧の変わった部分に依存していなかった、または新の下では**依存そのものがなくなった** → 新を `depends-on` と書くと、ない依存を表明することになる

特に `refines`（親決定の細分化）は、親の判断の本質が変わったのに子が「影響なし」という判定自体が疑わしい。§4.6 の例（`GDR-UI-007` を `refines GDR-ARCH-009` へ付け替え）は、ログイン画面の決定が「Redis 保持」の細分化になるかを説明していない。

**修正案:** 「影響なし」の処置を「付け替える / 外す / `relates-to` に弱める」から選ぶ形にし、記録の 1 行に**判定の根拠を一言**添える（例: `GDR-UI-007（影響なし・再ログイン導線は保持方式によらない → 関連を外す）`）。§4.6 の例も根拠付きに直す。

### A-5. 入れ先の指定に事実誤認と漏れがある

1. **04 の節番号が違う。** §4.3 と代替案 E は `整合性チェック` を「04 §6」としているが、実際は **§5「ふりかえり・検証」**（§6 は短縮キーワードの節）。`波及チェック` を §5 の表に入れるのか、§6 のキーワードにするのかも決める必要がある（プロンプトなら §5）
2. **01 に「置換と失効の規則」という見出しはない。** 実際は §3 の中の「置換（supersede）の記法と切替時点」という段落。入れ先を実在の名前で書く
3. **05 が入れ先から漏れている。** 05 は user-level config の仕様で、`gdr-flow.md` のフェーズ 4 の動作（「合意時に `Proposed → Accepted`…置換対象の旧を `Superseded`」）と不可侵ルールの一覧を書き写している。`gdr-flow.md` と `CLAUDE.md` §4 を変えるなら 05 も同時に直さないと、仕様と配備物がずれる
4. **完了処理の側が漏れている。** A-1 のとおり付け替えを `Implemented` 時点に置くなら、`gdr-flow.md` フェーズ 7 と `gdr-docs.md`（完了処理のショートカット）にも手順が要る
5. **`CLAUDE.md` §6 の現行版表記**（v2.2 → v2.3）の更新が §4.5 にない（012 では CHANGELOG 側に書いていた。実行計画 2.1 に含めるなら明記する）

### A-6. 版による読み替えが決まっていない

提案は「MINOR（v2.3）」とするが、**どの解釈版の導入先に適用するか**を書いていない。契機は「新が `Accepted` になった時点」で、これは v2.0 以上の概念（v1.x には `Accepted` がなく、旧は新 GDR の発行時に `Superseded` になる）。`CLAUDE.md` §6 の互換モードの表に行を足すのか、v2.1 の絶対パスの規則のように「既存の GDR の解釈を変えないので版によらず適用」とするのかを決める。

**修正案:** 版によらず適用とし、v1.x では契機を「新 GDR の発行時」と読み替える旨を 1 文添える（既存の GDR の解釈は変わらないため。表に行を足すほどではない）。

### A-7. この GDR 自身の「関連」が、自分の規則に照らして不足している

`関連: derived-from §2-1, derived-from §2-2, refines GDR-META-029` となっているが、

- 038 は 029（前向きの参照規律）を細分化したものではなく、逆向きを**足す**もの。`refines` より `relates-to` が正確
- 038 が実際に前提にしているのは、「関連」の型の語彙（**GDR-META-025**）と、失効の切替時点（**GDR-META-028**）。どちらも `depends-on` として書かれていない

このため、025 や 028 が将来置換されても、038 は自分の定めた「必須の列挙」に載らない（再検討条件 4 項目目が手書きで補っているだけ）。提案の最初の適用例として、自分の「関連」を正しく書く。

## B. 実装中に決めて良い

1. **分割による置換** — 旧が複数の新に置換された場合（02 §5.2「最初の GDR が後から別の GDR に分割される」）、付け替え先は人間が選ぶ、と 1 文添える
2. **本文の ID 言及を探す範囲** — GDR レコード（6 フィールドのブロック）の中だけに限る。この repo では仕様書やガイドが経緯として GDR-META の ID を多数引いており、文書全体を探すと雑音が多い
3. **付け替えと「理由の出所」** — 「関連」の付け替えはリンクの訂正で、理由は変わらないので出所は変えない、と明記する（「AI が更新する GDR には必須」の規則が、出所のない古い GDR への付け替えで問題になるのを避ける）
4. **記録の 1 行が長くなる場合** — 対象が多いときは「影響」配下のサブ箇条書きにしてよい
5. **`波及チェック: 対象なし` の扱い** — 0 件でも書かせる現案でよい（「確認した」と「忘れた」を区別できる）
6. **T2 テンプレート** — 「影響」の記入例に波及候補の行を足すかどうか

## D. 過剰 / 削れる候補

1. **`relates-to` の参考列挙** — `relates-to` は定義上「依存はしないが関連する」（06 §2）。依存しないと宣言したものを波及の候補に挙げるのは語彙と矛盾し、雑音になる。削る。本文の ID 言及は「関連」の記入漏れを拾えるので残す
2. **「保留」という第 3 の判定** — A-3 の形にすれば不要（未判定は「関連」が旧を指したまま、で表せる）
3. **06 §5 への追記** — `/gdr-map GDR-ID` の近傍ビューはすでに逆向きの辺を含む。1 行の注記は害はないが、入れ先が 7 か所（01 / 02×2 / 04 / 06 / gdr-flow / CLAUDE.md、A-5 で 05・gdr-docs が加わる）に広がっているので、削る第一候補
4. **再検討条件 3 項目目（再帰が 3 段以上）** — 事例がないうちの想定。残してもよいが、優先度は低い
