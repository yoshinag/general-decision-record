## 結論（先に）

**決定の骨格（独立した文脈のレビュアーに委ねる / 確認を外す代わりに記録・止まる条件・印をそろえる）は筋が通っており、代替案 A〜D の却下理由も本文・実績と合っている。作り直しは不要。** 版の判定（MINOR / v2.5）と理由の出所（`ai`、合意時に `ai-reviewed`）も妥当。

直すべき点は「決めた規則が上流の文書に届ききっていない」ことに集まっている。

1. 反映の規則の正本を user-level config に置いているが、導入先はそのファイルを受け取らない（05 の仕様から生成する）。05 の文案は見出し語だけで、規則の中身を運べていない（A-1）
2. 入れ先に漏れがある。とくに 00 の配置プロンプトに `agents/gdr-reviewer.md` が無く、新規の導入先では毎回「代替で自分がレビューして止まる」になる（A-2）
3. 02 §5.2 の文案が、理由の挙げる 4 つの役割のうち「レビュアーの誤りを止める」の代わりを運んでいない（A-3）
4. 確定済み GDR への指摘の扱いが、提案・config・02 の既存の規則で食い違っている（A-4）
5. 版の適用範囲（v1.x の導入先でどう動くか）が書かれていない（A-5）

【要ユーザー判断】は 3 件（A-4・A-5・A-6）。

### A-3. 02 §5.2 の文案が「レビュアーの誤りを止める」の代わりを運んでいない。原則が決定ではなく影響に置かれている【そのまま反映可】

**該当:** §4.1 の文案、§1 理由（4 つの役割）、§1 影響「Claude Code 以外のツールでは…原則とし」

**根拠:**

- 理由は、外す確認が (1) レビュアーの誤りを止める、(2) 判断が要る指摘を人に回す、(3) 記録を残す、(4) 現在地を示す、の 4 つを兼ねていたとし、(1) の代わりを「読み直し・止まる条件・事実誤認の除外」とする
- §4.1 の文案が挙げるのは、記録と取り消し / 確定済み GDR・編集禁止の領域・コードへの指摘を回す / 合意との境界、の 3 つ。**全文を読む・作り直しの勧告なら反映しない・独立した文脈で書けなかったら反映しない・事実誤認の除外が無い。** 02 だけを読んでワンセットを組むツール（05 を使わない導入先）では、(1) の代わりが抜ける
- 「合意を聞く前に、レビューで何が変わったかを示す」も文案に無い。人が `_reviewed` を読まなくなった後で、01 §3.1 の `ai-reviewed`（「AI が起案し**人間が**レビュー・合意で確認」L95）の意味を支えるのはこの 1 点なので、ツールに依存しない原則の側に要る
- ツールに依存しない原則（「独立した文脈・レビュアーのモデルで書く」「確認を外すなら記録・止まる条件・印をそろえる」）は影響の 1 項目として書かれ、決定の本文は Claude Code の用語（コマンド名・frontmatter・AskUserQuestion）で書かれている。再検討条件 3（Claude Code の仕組みが変わる）が起きても残るのは原則の方

**直し方:**

1. §1 決定の先頭に「原則（ツールに依存しない）」を 1 項目立て、影響にある原則の文をそこへ移す。以下の委任・ワンセット・表は「Claude Code での実装」と位置づける
2. §4.1 の文案を次の形にする（(3) の確定済み GDR の書き方は A-4 の結果に合わせる）:

   > - **レビューと反映（推奨）:** レビューは、起票した文脈から独立した文脈で、レビュアーのモデルに書かせる。ツールが対応していれば、レビューと反映を続けて行ってよい（ワンセット）。その場合、人の確認は「判断が要ると印の付いた指摘への回答」と「合意」に移る。確認を外す代わりに次をそろえる。(1) 記録と取り消し — `_reviewed` をバージョン管理に記録してから反映し、反映は別の単位で記録する。記録できない環境では続けて反映しない。(2) 止める — 反映の前にレビューの全文を読む。レビューが作り直し・取り下げを勧めるとき、独立した文脈で書けなかったときは反映しない。事実誤認と判断した指摘は反映せず報告する。(3) 対象を絞る — 確定済み GDR・編集禁止の領域・コードへの指摘は反映せず報告に回す。(4) 合意と分ける — 反映時の回答は合意とみなさず、status と理由の出所を変えない。合意を聞く前に、レビューで何が変わったかを示す（経緯: 014 提案 GDR-META-039）

### A-4. 確定済み GDR への指摘の扱いが、提案・config・02 の既存の規則で食い違う【要ユーザー判断】

**該当:** §1 の表「止まる条件」、§4.1 の文案 (2)、§4.5 の例の手順 4

**根拠:**

- 提案の表: 確定済み GDR の本文への指摘は「反映せず報告（置換 GDR の起票候補として）」。例外なし
- 手元の `gdr-apply-review.md`（共通の振る舞い 3）: 「**軽微な訂正を除き**、置換 GDR の起票候補として報告する」
- 02 §5.2（L119）: 「軽微な追記・誤りの修正は元の GDR を直接編集してよい」
- 実績: 提案 13 の発行前の再レビュー（0.1c）は、`Accepted` の GDR-META-038 に A-1〜A-3 を「決定の補足」として反映している（13 の理由の出所の注記）。提案の表のとおりに運用すると、この型の再レビューの指摘はすべて置換 GDR の候補になる

**選択肢:**

- (a) 軽微な訂正は確認なしで反映してよい（config の現状。報告に明記する）
- (b) 軽微な訂正に当たると AI が判断した指摘は【要ユーザー判断】として聞いてから反映し、それ以外は置換 GDR の起票候補として報告する
- (c) 一律に反映しない（提案の表の現状）

**推奨: (b)。** 軽微か本質かの線引きは「判断の本質が変わる更新は元 GDR を直接編集しない」という規則の中心で、確認を外した後の歯止めをここで AI の単独判断に任せると、止まる条件の意味が薄れる。確定済み GDR への指摘は頻度が低く、聞く負担は小さい。(c) は 02 L119 と実績の両方に合わない。

**どれを選んでもそのまま直せる点:** 表の「確定済み GDR（`Accepted` 以降）」は、`Proposed → Rejected` の GDR を含むかが読み取れない。config と同じく「`Proposed` 以外（`Accepted` / `Implemented` / `Superseded` / `Rejected`）」と書く。提案の表・§4.1 の文案・config の 3 か所を同じ文言にそろえる。

### A-5. 版の適用範囲と v1.x の読み替えが書かれていない【要ユーザー判断】

**該当:** §1 影響「版: MINOR（v2.5）。必須の移行なし」、タスク 2.1

**根拠:**

- user-level config は全導入先に即時に届く。提案 10 §2-6 とバグレポート 02 は、新しい規則が旧版の導入先に先に届いて壊した実例で、その対策が GDR-META-034（版依存の規則は宣言版に従って解釈する）と 05「上流で版を発行する手順」の 2。提案 13 は決定に「版:」の項を立てて「解釈版によらず適用」と v1.x の読み替えを書いた。提案 14 にはこの項が無く、手元の config も版の条件なしで配備されている
- 新しい規則のうち版に依存する箇所:
  - 止まる条件「確定済み GDR」— v1.x には `Accepted` が無く、`Proposed` に合意済みのものが含まれうる（user-level `CLAUDE.md` §6 の表）。status からは合意済みかどうか分からないので、**合意済みの GDR の本文を確認なしで書き換えうる**
  - 「合意（`Proposed → Accepted`）」「status と理由の出所は変えない」「合意時に `ai → ai-reviewed`」— v1.x には遷移も理由の出所も無い

**選択肢:**

- (a) 解釈版によらず適用し、v1.x の読み替えを 1 行足す: 「v1.x の導入先で、対象に `Proposed` の GDR があるときは、反映の前に合意済みかどうかを 1 回確かめる。合意済みなら確定済みと同じ扱いにする」
- (b) 委任は解釈版によらず適用し、ワンセット（確認なしの反映）は v2.0 以上に限る。v1.x の導入先では既定を「レビューのみ」にする

**推奨: (a)。** 挙動が版で分かれず、互換モードの表に行を増やさずに済む。v1.x で質問が 1 つ増えるが、起票直後のレビューなら「未合意」と答えるだけで済む。観察して煩わしければ (b) に切り替える（再検討条件に足す）。

**どちらでも要る反映:** §1 決定に「版:」の項を足す / CHANGELOG の互換性欄に適用範囲を書く / `gdr-apply-review.md` に版の条件を入れる（タスク 1.5）/ 「関連」に `relates-to GDR-META-034` を足す。

### A-6. 引数なし（自動特定）とワンセットの組み合わせで、誤特定の影響が広がる【要ユーザー判断】

**該当:** §4.3「モード B の誤特定時のロールバック」の文案、05 L77・L113

**根拠:**

- 05 L77 は「AI が『自動特定』する内容が曖昧になりうるコマンド（破壊的操作 / 引数依存度が高い操作）は 1 モードに留める」とする。`/gdr-review` の引数なしが許されていたのは、誤特定しても `_reviewed.md` が 1 つ生成されるだけだったため
- ワンセットでは、誤特定した対象に対して (1) そのファイルの未コミット変更のコミット、(2) `_reviewed.md` のコミット、(3) 本体の編集と削除のコミット、まで確認なしで進む。手元の `gdr-review.md` は「候補が 1 件 → そのままレビュー対象に」
- 05 L113 の前提「いずれのコマンドも 1 コミット単位で完結しているため `git revert HEAD` で戻せる」は、`/gdr-apply-review` だけでなく `/gdr-review` でも成り立たなくなる。§4.3 の文案は `/gdr-apply-review` の句しか直していない

**選択肢:**

- (a) 挙動は現状のまま。委任の前に、特定した対象を 1 行で示す（確認は待たない）。ロールバックの節を `/gdr-review` も含めて書き直す
- (b) 引数なしで自動特定したときは、候補が 1 件でも対象を示して確認してから委任する（引数ありは確認なし）
- (c) 引数なしのときは「レビューのみ」で止める

**推奨: (a)。** 往復を減らすという提案の目的に合い、誤特定しても 3 つのコミットで戻せる。誤特定による取り消しが起きたら (b) に切り替える、を再検討条件に足す。

**どれを選んでもそのまま直せる点:** ロールバックの節の文案に次を入れる。「`/gdr-review`（ワンセット）と `/gdr-apply-review` は最大 3 コミットに分かれる。反映だけを戻すときは最後のコミットを `git revert` する。対象の誤特定を戻すときは、反映のコミット → `_reviewed.md` のコミットの順に `git revert` する（未コミット変更のコミットは、対象ファイルの元の変更なので残す）」。

### A-7. 確かめていない仕組みを決定に書いており、確認が合意の後になっている【そのまま反映可】

**該当:** §1 決定「モデルの指定は 1 か所」（`effort:`、プロジェクトの `.claude/agents/` の同名定義）、§5-6、タスク 1.1（依存: 0.2 合意）

**根拠:** §5-6 は「`effort:` が効いているか」「プロジェクトの定義がユーザー定義より優先されるか」を未確認とするが、決定はどちらも事実として書き、確認（1.1）は合意（0.2）の後に置かれている。合意の対象に未確認の前提が入る。提案 11 のふりかえり 3（「文書に書く手順は、書く前に実行する」）と同じ型。

**直し方:** タスク 1.1 をフェーズ 0 に移し、0.2 合意の前に置く。結果を §5-6 に書く。確かめられなかった項目は、決定から外すか「未確認」と添える。

**参考（このレビューの実行で分かったこと）:**

- このレビューは `gdr-reviewer` 経由で動いた。システムが表示したモデルは、定義の `model:` のエイリアスが指す系統のものだった。`model:` は効いているとみてよいが、メインのモデルはこちらから見えないので、継承ではないことまでは断定できない
- `effort:` が効いているかは、サブエージェントの内側からは確認できない
- サブエージェントに渡された user-level `CLAUDE.md` は**編集前の版**だった（モデルの役割分担が「3 層構成・2026-10-01 時点」で、`/gdr-review` は frontmatter でモデルを切り替えると書かれた版。ディスク上は「4 層構成・2026-11-26 時点」）。エージェント定義は現行の内容だった。セッション開始後に `CLAUDE.md` を直しても、そのセッションから呼ぶサブエージェントには古い版が渡る。タスク 1.1 の確認項目と、05 の再起動の節（A-2）に足すとよい

### A-8. コミットを前提にした規則と、コミットに確認が要る導入先の関係が無い【そのまま反映可】

**該当:** §1 の表「記録と取り消し」

**根拠:** 00 Step 5「よくある運用ルール」（L173）は、commit を「明示指示を待たずに実施してよい / 必ず確認を取る」のどちらにするかを導入先に委ねている。記録と取り消しは 3 つのコミットが前提で、しかも 1 つ目は利用者の未コミットの作業を自動でコミットする。「必ず確認を取る」を選んだ導入先での動きが決まっていない。

**直し方:** 表の「記録と取り消し」に 1 句足す: 「コミットの可否はプロジェクトの運用ルールに従う。確認が要るプロジェクトでは聞いてからコミットし、コミットできないときは反映に進まず `_reviewed` を残して止める」。05 の節（A-1）と `gdr-apply-review.md`（タスク 1.5）にも同じ句を入れる。
