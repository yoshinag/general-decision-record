## A. 実装着手前に反映が必要

### A-1. GDR-META-040 を「系譜」と「`uid`」の 2 件に分けるか【要ユーザー判断】

- **該当:** 見出し（L9・L15）、決定（L20〜L46 が系譜、L47〜L60 が `uid`）、理由（L63 の後半）、再検討条件（L89〜L95）、§6.1 の「対象 GDR」列
- **根拠:**
  - 提案自身が理由で「UUID v7 は親子を表さないので系譜の手段にはならない」（L63）と書いている。`uid` は系譜の決定とは別の判断で、目的（同一性・プロジェクトをまたぐ参照）も、出どころ（系譜は AI の起案とユーザーの選択、`uid` はユーザーの判断「補助的にuuid v7を持たせる」）も、再検討条件（L91・L92 は `uid` だけのもの）も独立している
  - 1 件にまとめたままだと、再検討条件「`uid` の使われ方」（L92: 6 か月使われなければ推奨を外す）が成り立ったとき、GDR-META-040 全体を置換する新しい GDR が要り、変わらない系譜の決定をそこに書き写すことになる（01 §3: 判断の本質が変わる更新は置換）。分けてあれば `uid` の側だけ置換すれば済む
  - 決定欄が約 40 行、見出しが 5 文になっている。INDEX や `系譜` の出力に載る 1 行の要約として長い
- **選択肢:**
  - (a) 分ける。GDR-META-040 = 系譜（定義・不変条件・たどる手段・起票時の親と日時の推奨）、GDR-META-041 = `uid`（任意フィールド・生成の手段・使いみち・採番の衝突の扱い）。041 の「関連」は `refines GDR-META-025, relates-to GDR-META-040, relates-to GDR-META-020`。改善提案の文書は 1 本のまま、版も v2.6 の 1 回で出す
  - (b) 1 件のままにする（直す量は少ない。`uid` だけを見直すときは 040 ごと置換する）
- **推奨:** (a)。代替案 B・I〜M と再検討条件 L89〜L92 は 041 に、代替案 A・C〜H は 040 に（代替案 A「GDR ID を UUID v7 にする」は 041 にも「採らない理由」として 1 行で引く）。041 の「理由の出所」は、核心がユーザーの判断なので引用つきで書ける（細部が AI の起案なので値は `ai` のまま）
- **補足（どちらを選んでも）:** L96 の日時（2026-11-26T12:48:57+09:00）は `uid` を決定に加える前の時刻。分けるなら 041 には起票した時刻を書く

### A-2. 採番の衝突で「`uid` の時刻が新しい方を採番しなおす」という基準【要ユーザー判断】

- **該当:** 決定 L57、影響 L79、§4.1 の `uid` の行（L148）と採番ルールの文案（L150）、再検討条件 L90
- **根拠:**
  - **基準が費用と合わない場面がある。** ブランチ A で月曜に GDR-X-010 を起票し（`uid` が古い）、ブランチ B で火曜に GDR-X-010 を起票して水曜に main へ入れ、ほかの GDR やコミットが GDR-X-010（B）を指し始めたとする。木曜に A を合流すると、規則どおりなら main にある B（`uid` が新しい）を採番しなおすことになり、すでに共有された参照を書き換える。A の側を採番しなおせば、書き換えるのは A のブランチの中だけで済む。起票の先後は、採番しなおしの費用（どちらがすでに共有されているか、どちらが多く指されているか、status がどちらが進んでいるか）と関係がない
  - **書き換えられない参照が、別の GDR を指すようになる。** コミットメッセージや他リポジトリの文書にある「GDR-X-010」は書き換えられない。共有済みの側を採番しなおすと、それらは番号を保った別の GDR を指してしまう。`uid` は GDR の本文にしか無いので、これは防げない。退避済みの GDR の本文にある `Superseded by GDR-X-010` も同じで（`notes/_archive/` は読まない・直さない領域）、参照の規律で後継をたどるときに誤った先へ行く
  - **`uid` が無いときの扱いが無い。** `uid` は任意フィールドで、人が起票した GDR や既存の GDR には無い。どちらか（または両方）に無いときにどう決めるかが書かれていない
  - **観察されていない出来事への規則。** §2-4 のとおり、このリポジトリで採番の衝突は 1 回も起きていない。01 の採番ルールに規範の 1 文を足すだけの実例がまだ無い（再検討条件 L90 は 2 回起きたら見直すとしている）
  - 先後は `uid` の文字列の辞書順で比べられる（UUID v7 は先頭 48 ビットが時刻なので、文字列の大小が時刻の順になる。E-1 で確認）。AI が 16 進数を手で時刻に直す必要は無いが、提案にはその旨が無い
- **選択肢:**
  - (a) 現案のまま（`uid` の時刻が新しい方）。`uid` が無いときの扱いだけ足す
  - (b) 基準を「共有されていない側を採番しなおす」にし、`uid` の時刻は決め手が無いときの最後の基準にする。文案: 「並行して起票された GDR の番号が重なったときは、まだ共有されていない側（合流する側）を採番しなおす。どちらも共有済みなら、status が進んでいない方、指されている数が少ない方の順で選び、決まらなければ `uid`（無ければ日時）の新しい方にする。採番しなおしても `uid` は変えず、採番しなおした GDR に旧番号を注記する（例: `旧番号: GDR-X-010（採番の衝突により 2026-12-01 に採番しなおし）`）」
  - (c) 01 の採番ルールには「採番しなおしても `uid` は変えない」だけを書き、どちらを採番しなおすかは決めない（実例が出てから決める。再検討条件 L90 に寄せる）
- **推奨:** (b)。`uid` の「採番しなおしても同じ GDR だと分かる」という価値は残り、費用の高い側を採番しなおさせる規則にはならない。文が長すぎるなら (c)
- **あわせて直す（どれを選んでも）:** `uid` の先後は文字列の辞書順で比べられることを 1 文足す。採番しなおしは判断の内容を変えないので、`Accepted` / `Implemented` の GDR でも軽微な訂正として扱う旨を足す（01 §3 の撤回時の復帰と同じ扱い）

### A-3. 「起票時刻の補い」（日時の無い端を `uid` の時刻で代える）【要ユーザー判断】

- **該当:** 決定 L59、§4.1 の `uid` の行（L148）、理由 L63（「日時の無い GDR にも起票の時刻が残る」）、代替案 K（L68）、再検討条件 L92
- **根拠:**
  - **不変条件の定義と食い違う。** L40 と §4.1 の文案（L142）は「両端に日時があるとき、親の日時 ≤ 子の日時」、L43 は「日時が読めない端では日時を比べない」、§4.3 の `系譜` の文案（L160）にも `uid` で補う話が無い。L59 だけが「日時が無い端は `uid` の時刻で代える」と書いている。01 に入る文案をそのまま実装すると、この使いみちは働かない
  - **当てはまる場面がほぼ無い。** AI が起票するときは日時と `uid` を同時に書く（L46・L55 の推奨）。人が起票するときはどちらも書かないのが普通。「日時は無いが `uid` はある」のは、ほぼ「既存の GDR に遡って `uid` を付けた」（L55 で任意としている）場合だけになる
  - **その場合は時刻が誤り。** 遡って付けた `uid` の時刻は付けた時点のもので、起票の時刻ではない。これを親の時刻として使うと、古い親が子より新しく見え、置換・派生の不変条件で誤った警告が出る
  - 日時（ISO 8601）と `uid` の時刻（16 進数）を混ぜて比べるには復号が要る。AI が手で計算すると誤りやすく、「生成はツールで行う。AI が値を手で書かない」（L50）と同じ理由で、読む側にもツールが要ることになる
- **選択肢:**
  - (a) この使いみちを削る。L59 と L148 の該当部分、理由の「日時の無い GDR にも起票の時刻が残る」、代替案 K の「起票時刻の補いができない」、再検討条件 L92 の「時刻の補い」を外す。日時の順は日時だけで確かめる（初回レビュー後の姿のまま）
  - (b) 残す。その場合は L40・L43・§4.1（L142）・§4.3（L160）に `uid` で補う規則を書き足し、「遡って付けた `uid` の時刻は使わない」ことと見分け方（遡って付けるときは日時を日付だけでも併記し、日時を優先する）、復号の手段（スクリプトに復号の機能を足すか、1 行のコマンドを示す）を決める
- **推奨:** (a)。`uid` の役目は同一性とプロジェクトをまたぐ参照で足りる。時刻の順は「日時」が担い、AI 起票時の記入の推奨（初回レビュー A-13 の結論）で手当て済み
- **あわせて直す（どちらを選んでも）:** L55 に「遡って付けた `uid` の時刻は付けた時点のもので、起票の時刻ではない。遡って付けることは判断の内容を変えないので、軽微な追記として扱う」を足す

### A-5. `uid` が何の識別子かを明確にする（置換・写し・コピー・重複）【そのまま反映可】

- **該当:** 決定 L49、§4.1 の `uid` の行（L148）
- **根拠:** L49 の「status の遷移・置換・採番しなおし・退避・ファイルの移動でも同じ値を保つ」は、次の 3 点が読み取れない
  1. **置換する新しい GDR は別の `uid` を持つ。** 系譜の表（L24）が置換を「同じ判断の更新」と呼んでいるので、「置換でも同じ値」を「後継が旧の `uid` を引き継ぐ」と読める。`uid` は判断の識別子ではなく、GDR レコード 1 件の識別子。再提案（`derived-from`）の新しい GDR も同じ
  2. **同じ GDR の写しは同じ `uid` を持つ。** 導入先では、GDR はまず改善提案の文書に `Proposed` で書かれ、合意後に `notes/91_gdr/gdr/` へ起票される（`gdr-flow.md` フェーズ 5）。`uid` はフェーズ 1 で生成し、フェーズ 5 ではそのまま写す。L49 の「起票したときに 1 回だけ」はどちらの時点とも読める
  3. **別の GDR に同じ `uid` を付けない。** AI は既存の GDR を雛形にして書くので、`uid` の行ごと写す、または仕様の例の値（L49 の `01a2160a-…`。復号すると 2026-11-26T13:08:47+09:00 に生成された実在の値）をそのまま使うおそれがある。重複を検出する手段が提案に無い
- **直し方:**
  - L49 と §4.1 の行に足す: 「`uid` は GDR レコード 1 件の識別子。置換・再提案で起票する新しい GDR には新しい `uid` を生成する（旧の値を引き継がない）。同じ GDR の写し（改善提案の文書と `notes/91_gdr/gdr/` の記録）は同じ値を持つ。既存の GDR や仕様の例から値を写さない」
  - `系譜`（引数なし）の出力（L42・§4.3）に「異なる GDR ID に同じ `uid` が付いているもの」を警告として足す（不変条件の違反と同じ扱いで、書式違反にはしない）
  - `gdr-flow.md` フェーズ 5 の行（§4.4・§4.5）に「`uid` は改善提案の値をそのまま写す（生成しなおさない）」を足す

### A-6. レビューで確かめる中身を、確かめられる形にする【そのまま反映可】

- **該当:** §4.4 の `gdr-reviewer.md` の観点（L171: 「`uid` の形式（UUID v7 か、手で書いた疑いがないか）」）
- **根拠:** 「手で書いた疑い」は見ただけでは判定できない。もっともらしい値は形式を満たす。レビュアーが実際に確かめられるのは次の項目
- **直し方:** 観点を次に置き換える: 「`uid` があるとき — (1) 小文字の 8-4-4-4-12 か、(2) 3 つ目の区切りの先頭が `7`（version）で、4 つ目の区切りの先頭が `8`・`9`・`a`・`b` のどれか（variant）か、(3) 同じ文書・同じプロジェクトの別の GDR と重複していないか、(4) 仕様の例の値と同じでないか」。時刻の確認（`uid` の時刻が日時やコミットの時刻と大きくずれていないか）は、復号にツールが要るので任意とする

### A-8. 前提の連鎖に `refines` を含めるか（初回レビューの反映分）【要ユーザー判断】

- **該当:** 決定 L29（「前提の連鎖（`depends-on` を推移的にたどった前提・被前提）」）、L34（「`refines` は前提であることを含む」）、§4.3（L160）、§4.6 の `系譜 GDR-META-039` の例（L206〜L208）
- **根拠:**
  - L34 は「`refines` は前提であることを含むので、`depends-on` と重ねない」と書く。波及チェック（02 §5.2、01 §3）も `depends-on` と `refines` の両方を「前提にしている」リンクとして扱う。ところが L29 と §4.3 の前提の連鎖は `depends-on` だけをたどる。同じ仕様の中で「前提」の範囲が 2 通りになる
  - 型をまたぐ経路の扱いが決まっていない。§4.6 の 039 の例は、前提の段の GDR-META-030 に「親: GDR-META-025（refines）」と添えている。`depends-on` だけをたどるなら 030 の先は出ないはずで、例は定義に無い動きをしている（この例では 025 は 028 経由でも出るので結果は同じだが、一般には変わる）
  - 実害が出る場面: X が Y に `depends-on`、Z が Y を `refines` しているとき、`系譜 X` の被前提にも子孫にも Z は出ない。Y を置換するときの波及チェックでは Z も波及候補になるので、`系譜` と `波及チェック` で「Y に乗っている GDR」の範囲が食い違う
- **選択肢:**
  - (a) 前提の連鎖を「`depends-on` と `refines` を推移的にたどったもの」にする（波及チェックと同じ範囲）。`refines` の親は、先祖の段と前提の段の両方に出る
  - (b) 前提の連鎖は `depends-on` だけのままにし、型をまたぐ経路はたどらないと明記する。§4.6 の 039 の例から「親: GDR-META-025（refines）」を外す。L34 の「前提であることを含む」は「前提でもあるが、系譜の段に出す」と書き直す
- **推奨:** (a)。「前提」の意味が仕様の中で 1 つになり、`系譜` の前提・被前提の段が波及チェックの範囲と一致する。出力は少し重なるが、種類つきで出すので区別できる
- **補足:** これは `uid` の追加で出た矛盾ではなく、初回レビュー A-1 の反映（前提の段を足した）で残った隙間

### E-4. 理由・代替案・再検討条件の整合（`uid` を足した分）

1. **理由 L63「置換や退避で置き場所も変わる」**【そのまま反映可】 — 置換でも退避でも GDR ID は変わらないので、`uid` が要る理由にならない。GDR ID が変わるのは採番しなおしだけ。この句を外し、「GDR ID は PREFIX 内の採番で、衝突すれば採番しなおす。プロジェクトの外では一意でない」とする
2. **代替案 B（L65）「起票時に 1 行足すだけで済む」**【そのまま反映可】 — 実際の費用は、起票ごとのツールの実行、生成の手段の配布、レビューの観点、入れ先の追加。「GDR 1 件あたりは 1 行と 1 回のツールの実行で済む（配る費用は影響のとおり）」と書き直す。あわせて、初回の版にあった事実（採番の衝突もプロジェクトをまたぐ参照も、いまは起きていない。§2-4）が理由から消えているので、「いまは起きていないが、起きてから付けると遡れない」と、起きていないことを明記する
3. **代替案 K（L68）**【そのまま反映可】 — UUID v4 の側の利点が書かれていない。v4 なら macOS・Linux の `uuidgen` で作れ、生成の手段を配る必要が無い。却下の理由も「衝突時の先後の判定と起票時刻の補いができない」だが、先後は日時でも分かる（AI は日時と `uid` を同時に書く）。公正に書くなら「v4 なら `uuidgen` で足り、配るものが無い。時刻は日時でも残せる。それでも v7 にするのは、ユーザーの判断（『補助的にuuid v7を持たせる』）と、日時が無くても起票の順に並ぶため」。A-3 で (a) を選ぶなら「起票時刻の補い」の句は外す
4. **再検討条件 L92「同一性の確認・プロジェクトをまたぐ参照・時刻の補いのどれにも使われない」** — A-3 で (a) を選ぶなら「時刻の補い」を外す（A-3 に含む）
5. **不変条件（L40・L43）と L59 の食い違い** — A-3
6. **L46「決定の日時は『日時』で残す（`uid` の時刻は起票の時刻で、決定の日時とは限らない）」** — OK。GDR-META-025 の日時の定義（決定日時）と合う

## G. 全体評価

- **作り直し・取り下げは勧めない。** 反映してから合意に進める
- **`uid` の中心の設計は妥当。** 人が読む ID を変えず、リンクの対象にもせず、必須にもしない。変えない・ツールで生成する・手で書かない、という 3 つの性質は、任意フィールドの方針（GDR-META-025）と前例（GDR-META-030）に沿っている。既存の規則との矛盾は見つからなかった
- **過剰なのは中心ではなく周辺。** (1) 時刻を使う 2 つの使いみち（採番の衝突の先後、日時の無い端の補い）は、AI が日時と `uid` を同時に書く以上、日時で足りるか、当てはまる場面が無い。`uid` に残る固有の価値は「採番しなおしても同じ GDR だと分かる」と「プロジェクトの外でも一意」の 2 つで、これは時刻に頼らない。(2) スクリプトのファイルとしての配布は、1 行のコマンドで置き換えられ、その方が届く範囲が広い
- **スクリプトは正しい。** 2 つの版の Python で動かし、RFC 9562 の UUID v7 として合っていることを確かめた
- **版の判定は正しい。** MINOR v2.6。CHANGELOG に書く中身は `uid` を足す前のままなので、タスク 2.1 を直す
- **まだ確かめていないこと:** 導入先（上流以外のリポジトリ）での `_reference/` の実際の構成と、旧慣行の導入先の数は見ていない。A-4 の「取り直していない導入先で `uid` が付かない」は、config と `gdr-upgrade.md` の手順からの推論で、実際の導入先で試してはいない。1 行のコマンドは 3.9.6 と 3.15.2 でだけ確かめた（3.7・3.8 では動かしていない）
