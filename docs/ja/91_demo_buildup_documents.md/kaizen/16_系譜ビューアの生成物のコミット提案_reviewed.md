## A. 実装着手前に反映が必要

### A-1. 「生成時刻だけの差分」の判定が成り立たず、実行のたびにコミットになる 【そのまま反映可】

- **該当:** §1 決定「コミットの仕方」の 2 つ目（L25「先頭のヘッダ行の生成時刻を除くと、コミット済みの HTML と同じ」）、§2-3（L66）、§4.1 の手順 3（L95）
- **根拠（確認済み）:** HTML には生成時刻のほかに、読む範囲の `git rev-parse --short HEAD` が 2 か所に入る。ヘッダ行（`データ: general-decision-record@6b995f3`）と、データの中（`"commit": "6b995f3"`。スクリプト L336・L340〜342）。HTML をコミットすると HEAD が進むので、文書を 1 字も変えずに再生成しても `"commit"` が変わり、「生成時刻を除くと同じ」には決してならない。使い捨てリポジトリで、コミット直後の再生成が 1 行目以外でも差分になること（`"commit": "98b73ab"` → `"014a106"`）を確かめた
- **起きること:** `/gdr-lineage` を実行するたびに 1 コミット増える。データは 1 行（このリポジトリで 59 万字）なので、毎回ファイル全体が差分になる。決定が抑えたい「意味のない差分」がそのまま出る
- **直し方:** 判定を「文書が変わっていない（ヘッダ行と、データの中の対応するコミットを除くと、コミット済みの HTML と同じ）」に改める。L25・L66・L95 と目次・見出しの要約（「生成時刻だけの差分のとき」）を同じ言い方にそろえる。次の形で意図どおり動くことを確かめた（コミット済みの HTML が無い初回は比較を飛ばす）:

  ```bash
  norm() { sed -e 1d -e 's/"commit": "[0-9a-f]*"/"commit": ""/g'; }
  [ "$(git show HEAD:notes/tools/gdr_lineage.html | norm | shasum)" = "$(norm < notes/tools/gdr_lineage.html | shasum)" ]
  ```

### A-2. 未コミットの判定が、導入先では常に「ある」になり、`.gitignore` した文書は見落とす 【そのまま反映可】

- **該当:** §1 決定「コミットの仕方」の 1 つ目（L24 `git status --porcelain -- <読む範囲>`）、理由「埋め込みによる漏れ」（L35）、§3 の図（Q1 が生成の後）、§4.1 手順 3（L94）
- **根拠 1（確認済み）— 導入先では決してコミットされない:** 導入先の読む範囲は `notes` で、出力先 `notes/tools/gdr_lineage.html` はその中にある。生成の後に `git status --porcelain -- notes` を見ると、初回は `?? notes/tools/`、2 回目以降は ` M notes/tools/gdr_lineage.html` が必ず出る。上流（読む範囲が `docs/ja/.../kaizen`）でだけ動き、導入先では常に「コミットしない」に落ちる
- **根拠 2（確認済み）— 決定が防ぐと書いている漏れを防げない:** L24 は「`.gitignore` した文書（ローカル対応表など）の中身が履歴に入るのを防ぐ」と書くが、`git status --porcelain` は `--ignored` を付けないと除外されたファイルを出さない。`*.local.md` を除外したリポジトリで、GDR を書いた `notes/20_kaizen/draft.local.md` を置くと、判定は空（＝コミットしてよい）になり、生成した HTML にはその本文が入った
- **直し方:** 判定の対象を「読む範囲の `*.md`」に絞り、除外されたファイルも含める。判定は生成の前に行う（A-3）。次の形で、HTML 自身や `.DS_Store` は出ず、変更した `.md`・追跡外の `.md`・除外された `.md` が出ることを確かめた:

  ```bash
  git status --porcelain --ignored --untracked-files=all -- ':(glob)<読む範囲>/**/*.md'
  ```

  L24 の括弧書き、L94、§4.2 の 06 の文案（L101 は「未コミットの変更があるとき」だけで「追跡外・除外された文書」が落ちている）をそろえる
- **残る制約（B-8 へ）:** 読む範囲に、恒久的に `.gitignore` した `.md` を置いている導入先では、いつまでもコミットされない。安全側の動きなのでこのままでよいが、報告の文に「恒久的に除外した文書があるとコミットされない」を足す

### A-3. コミットしないとき、追跡中の HTML を書き換えたまま残す 【要ユーザー判断】

- **該当:** §1 決定 L23「次のときはコミットせず、理由を報告する（HTML は置いたまま）」、§3 の図（R1）
- **根拠:** 読む範囲に未コミットの変更があるとき、下書きや除外された文書の本文を埋め込んだ HTML が、追跡中のファイル `notes/tools/gdr_lineage.html` の未コミットの変更として作業ツリーに残る。系譜を見るのは作業の途中（改善提案を書いている最中）が多いので、これがふだんの状態になる
  - 後続の `git add -A` / `git commit -a`（人でも AI でも）で、止めたはずの HTML がそのままコミットされる。A-2 の判定を素通りする経路になる
  - `git status` に常に出るので、`レビュー：` の対象の自動特定（`git status` modified を見る）や未コミット差分を見る `一気通貫：` の現在地の判定に混ざる
- **選択肢:**
  1. **コミットできないときは、追跡中のファイルに書かない（推奨）** — 判定（A-2）を生成の前に行い、当たったら `/tmp/gdr_lineage_<リポジトリ名>.html` に出して開く（決定 L22 の「読む範囲を引数で変えたとき」と同じ扱い）。`notes/tools/gdr_lineage.html` は常に「コミット済みの文書と一致する写し」のままになり、漏れの経路が残らない。手順の分岐は増えない（出力先が 2 つあるのは今の案も同じ）
  2. 本案どおり置いたままにする — 手順は単純だが、上の 2 点が残る。採るなら、報告で「未コミットの HTML に下書きの本文が入っている」と明示する
- **推奨:** 1

### A-4. 既定でコミットするか、明示したときだけコミットするか（代替案に無い） 【要ユーザー判断】

- **該当:** §1 決定の全体、理由の代替案 A〜E（L36〜41）、「GDR-META-026 との関係」（L28）
- **根拠:** 026 の原則は「生成物の永続化は明示指定時のみ」（06 §1-2）で、`/gdr-map` は `save` を付けたときだけ保存して 1 コミットする（`commands/gdr-map.md` 手順 4、05 の `gdr-map.md` の行）。同じ形（`/gdr-lineage save` のときだけ `notes/tools/` に置いてコミット）にすれば、041 は 026 の例外にならず、改めるのは 040 の「コミットしない」だけで済む。この案が代替案に無く、比べた記録が残っていない
- **選択肢:**
  1. **既定でコミット（本案）** — ユーザーの指示「生成したHTMLもコミットするに修正」の文言どおり。ほかに再生成の契機を持たない（§5-2）ので、見るたびに写しが新しくなる利点がある。費用: 見るためのコマンドがコミットを作る（履歴に `regenerate` のコミットが混ざり、`git log -3` / `-10` を見るキーワードの対象特定の枠を使う）。026 の例外が 2 つになる
  2. **明示したときだけコミット（`save`）** — 026 の原則と `/gdr-map save` にそろい、例外にしなくてよい。共有する時点で意図して保存する形になる。費用: 保存を忘れると写しが古いまま残る。指示の文言より控えめな読みになる
- **推奨:** 1（指示の文言と、写しの新しさを優先）。ただし 2 を代替案 F として理由に書き、再検討条件の 4 つ目（L53「コミットしない場面が多く、運用の手間になる」）の行き先に「明示したときだけコミットする形に切り替える」を足す。ユーザーの意図が「共有する時点で残したい」なら 2 のほうが合う
- **A-3 との関係:** どちらを選んでも、コミットしない実行では追跡中のファイルに書かない（A-3 の 1）が要る

### A-5. GDR-META-040 の改め方（§5-1） 【要ユーザー判断】

- **該当:** §1 決定「GDR-META-040 との関係」（L27）、代替案 E（L41）、「関連」（L56）、§5-1（L108）

  - **置換（案 E）は過剰。** 040 の記録は 100 行近くあり、全体を写し直して波及チェック（040 を `refines` する GDR は 041 自身）まで回す費用に見合わない

  4. **注記を足す時点と戻し方を決める。** 置換の切替時点（02 §5.2: 旧の失効は新の `Accepted` 時点）にそろえ、注記は 041 の合意時に足す。041 が撤回されたら注記を外す。`Implemented` の GDR への追記なので、反映の規則（05「対象の絞り込み」）どおりユーザーに確かめてから足す
- **選択肢:** (1) `refines` + 注記（本案。上の 1〜4 を直す）/ (2) 040 を置換 / (3) 注記なし
- **推奨:** 1

### A-8. 大きさの見積もりが実際の 15 分の 1 【そのまま反映可】

- **該当:** 理由「差分が大きい — 1 回の生成で約 40KB 以上（見本で 40KB…）」（L34）、再検討条件「1 ファイルが 1MB を超える」（L52）
- **根拠（確認済み）:** このリポジトリの読む範囲（改善提案 16 本・GDR 40 件）で生成すると **623,201 バイト**（406 行。うちデータの 1 行が 593,703 字。gzip で約 184KB）。見本（架空 17 件）は 45,099 バイト。本文を埋め込む文書が 1 字でも変わると、差分はこの 1 行の全体になる
- **直し方:** L34 を実測に置き換える（例: 「見本で約 45KB、このリポジトリで約 620KB。データは 1 行なので、文書が変わるたびに全体が差分になる」）。L52 の 1MB は、上流では起票の時点で 6 割に達している（推測: 改善提案 1 本あたり平均 37KB ほど増えるので、あと 10 本前後で超える）。閾値は再検討の契機なのでそのままでよいが、「上流では近いうちに当たる」ことを書いておく

### A-9. 手順の抜け: 旧い `.gitignore`・`git add` の失敗・ステージ済みの他の変更 【そのまま反映可】

- **該当:** §4.1 手順 2〜3（L92〜95）、§1 影響「既存の導入先」（L46）、決定 L23「他の変更を巻き込まない」
- **根拠（いずれも確認済み）:**
  1. **旧い `.gitignore` があると `git add` が失敗する。** 65b8be9 以降の `/gdr-lineage` は `notes/tools/.gitignore`（`*` と `!.gitignore`）を自分で作る。これが残っていると `git add notes/tools/gdr_lineage.html` は「The following paths are ignored」で終了コード 1 になる。影響は「導入先があれば外す」と書くだけで、手順に扱いが無い。この環境の `~/_works/git/*/notes/tools/.gitignore` は上流の 1 つだけだった（L46 の「配っていない見込み」は、この環境については裏づけられた）
  2. **`git add` → `git commit` は、すでにステージされている無関係な変更も一緒にコミットする。** 読む範囲の判定は読む範囲しか見ないので、ほかの場所のステージ済みの変更は止まらない
- **直し方:** 手順に次を足す
  - 生成の前に `git check-ignore -q notes/tools/gdr_lineage.html` を見る。除外されていて、原因が旧い `/gdr-lineage` の作った `notes/tools/.gitignore`（1 行目が既定のコメント）なら、それを削除して HTML と同じコミットに含める。それ以外（プロジェクトの `.gitignore` が `*.html` を除外している等）は、`-f` を使わずコミットを止めて報告する
  - コミットは `git add notes/tools/gdr_lineage.html && git commit -m "…" -- notes/tools/gdr_lineage.html` のように対象のパスを指定する（ステージ済みの他の変更は残り、HTML だけがコミットされることを確かめた）
  - git リポジトリでない場所ではコミットの手順を飛ばす
