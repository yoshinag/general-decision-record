# バグレポート: status 5 値化（009）の配備で旧版の導入先の GDR 運用が壊れた

## 概要

kaizen 009（GDR-META-028〜030: status 5 値化 / 参照の規律 / 理由の出所）の実装で user-level config（`~/.claude/CLAUDE.md` / `~/.claude/commands/gdr-*.md`）を更新した結果、**まだ 3 値 status で運用している既存の導入先プロジェクト**で、完了処理と GDR 参照の振る舞いが意図せず変わった。kaizen 010 のセルフレビューで検出し、同日中に暫定対処した。

## 発生状況

- **発生日:** 2026-09-28（009 の実装フェーズ 3 — user-level config の更新時点から）
- **検出:** 同日、kaizen 010 のセルフレビュー（A-1）。実害の報告より前に、レビューで検出した
- **影響範囲:** user-level config を読み込むすべての導入先プロジェクト（前提定義書に版の宣言がない = 3 値運用のもの全部）
- **症状:**

| 対象 | 更新後の規則 | 3 値運用の導入先で起きること |
|---|---|---|
| `/gdr-docs`（完了処理） | 対応 GDR が `Proposed` なら更新せず「合意漏れ」と警告 | 3 値運用では「合意済み・実装済み」の GDR も `Proposed → Implemented` が正規の流れ。**完了処理が毎回止まる** |
| 参照の規律（`CLAUDE.md` / `gdr-flow` / `gdr-kaizen`） | `Proposed` は未確定として前提にしない | 3 値運用の `Proposed` には合意済みの GDR が含まれる。**合意済みの判断を AI が根拠にしなくなる** |
| `/gdr-flow` / `/gdr-kaizen` | AI 起票時に「理由の出所」必須、合意時に `Accepted` へ更新 | 3 値運用の導入先に存在しない値（`Accepted`）や、前提定義書・テンプレートにない任意フィールドを書き込む |

## 原因

### 原因 1: `Proposed` の意味の変更（書式は互換、意味は非互換）

009 は既存レコードの書式を壊さない変更として設計された（3 値のままでも書式違反にならない）。しかし `Proposed` の意味は、旧仕様の実運用（合意済み・未実装も含む — 完了処理まで `Proposed` のまま）から、新仕様の「合意に至っていない」に**狭まっていた**。既存レコードを書き換えないと、新しい規則の下で誤って解釈される。009 の 2 回のセルフレビューは、この変更をフレームワーク内部の整合性の観点でのみ検証した。

### 原因 2: user-level config は全導入先に即時に届く

user-level config は全プロジェクトの起動時に読み込まれる。上流の仕様（`docs/ja/01_GDR/`）の変更は、導入先が `_reference/` を取り直すまで届かないが、user-level config の変更は**導入先の同意なしに次のセッションから全導入先に適用される**。009 の実行計画は user-level config の更新を「リポジトリ外配備」として 1 タスクで扱い、既存の導入先への影響を検証する工程がなかった。

### 原因 3: 導入先の版を判定する手段がない

導入先がどの版の仕様で運用しているかを示す情報（前提定義書の版の宣言等）が存在せず、規則を導入先ごとに切り替えることができなかった。これは kaizen 010 が扱っている課題そのものである（009 の実装時点で 010 は起票済み・未合意）。

## 対応

| # | 対応内容 | コミット |
|---|---|---|
| 1 | kaizen 010 のセルフレビューで検出（A-1）。互換性区分の定義の不備（A-2）もあわせて指摘 | `3494268` |
| 2 | **暫定対処（ユーザー判断「今すぐ暫定対処」）:** user-level config に「旧版互換」規則を追加。5 値 status・参照の規律・理由の出所は、前提定義書に `GDR 仕様: v2.0` 以上の宣言があるプロジェクトと上流リポジトリ自身にのみ適用し、それ以外は 3 値の従来運用で扱う。対象: `~/.claude/CLAUDE.md` / `gdr-docs` / `gdr-flow` / `gdr-kaizen` | リポジトリ外（`~/.claude/` 配下） |
| 3 | **恒久対処の設計:** kaizen 010 に GDR-META-034（互換モード — user-level の版依存の規則を導入先の宣言版で解釈、未宣言は v1.0）を追加。版の桁の定義を「必須移行があれば MAJOR」に改め、009 + 010 を v2.0 として発行する方針に変更 | `94bc886` |
| 4 | 恒久対処の実装（暫定規則を版条件の書式に置き換え） | 未実施 — kaizen 010 タスク 2.1 |

**暫定対処後の状態:** 現時点で `v2.0` を宣言している導入先はないため、上流リポジトリ以外の全導入先は 009 以前の動作に戻っている。暫定対処はリポジトリ外の変更のため、Claude Code の新しいセッションから有効（既存セッションは再起動が必要）。

## 再発防止

- **フレームワーク自身の変更では、影響範囲に「すでに導入済みの利用者」を含める。** user-level config を変更する kaizen は、実行計画に「3 値運用など旧版の導入先での振る舞いの確認」をタスクとして持つ
- **互換性は書式だけでなく意味で判定する。** 既存の値の意味を変える変更は、書式が互換でも MAJOR（採用時に必須の移行がある）として扱う（kaizen 010 GDR-META-031）
- **版依存の規則には版条件を付ける。** user-level config の規則は導入先の宣言版で切り替え、旧版の規則を直前の MAJOR まで保持する（kaizen 010 GDR-META-034）
- 恒久対処（kaizen 010 タスク 2.1）の完了まで、暫定の「旧版互換」規則を削除しない
